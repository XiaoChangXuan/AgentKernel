# V0.6 Capability Final Architecture Review

Status: final validation review for V0.6 Capability.

Branch: `review/v0.6-capability-final-validation`

Decision: `READY_FOR_V0.6_COMPLETION`

This review validates the implemented V0.6 capability core and its current
Kernel enforcement boundaries. It intentionally does not introduce delegation,
revocation, namespace machinery, RBAC, IAM, a policy engine, or any V0.7
process scheduler behavior.

## 1. Architecture Coverage

The implemented capability path is now present across the three runtime
boundaries introduced before V0.7:

| Runtime area | Current enforcement | Result |
|---|---|---|
| Tool execution | `ToolRegistry.model_schemas()` hides unauthorized tools. `ToolRegistry.resolve_for_execution()` checks again before invocation. | The LLM only sees authorized tools and execution is still guarded if it fabricates a hidden tool call. |
| Resource access | `ResourceService.stat()` and `ResourceService.read()` resolve ownership first, then evaluate `resource.stat` or `resource.read` before range validation and store access. | Resource authority remains in the Kernel service layer; `ResourceStore` stays a replaceable driver. |
| Durable side effect | `DurableToolExecutor.execute()` checks before `tool/prepare`; `_dispatch()` checks again before `tool/dispatch` and external handler invocation. | Unauthorized mutation cannot enter dispatch, and dispatch-time denial aborts the prepared operation before external effect. |
| Recovery | `analyze_recovery()` validates authorization metadata shape and checks prepare/dispatch authorization identity consistency when metadata exists. | WAL replay preserves durable facts and detects changed authorization metadata between prepare and dispatch. |

The current architecture still follows the intended boundary:

```text
LLM = untrusted proposer
Kernel = authority
Drivers = replaceable execution/storage adapters
```

## 2. Implementation Review

`agentkernel/capabilities.py` provides a deliberately small positive-grant
model:

- `CapabilityGrant(subject, action, resource_scope, constraints)`
- `AuthorizationRequest(agent_id, action, resource)`
- `AuthorizationDecision(allowed, reason, matched_grant)`
- `CapabilityEvaluator.authorize()` with exact action matching and exact or
  `/**` resource prefix matching.

This is sufficient for the Phase 2 enforcement surface. It is not yet a
complete policy language. Constraints are immutable metadata only; no constraint
semantics are evaluated in V0.6.

`agentkernel/tools.py` preserves legacy `required_capability` strings by mapping
them to:

```text
action: tool.execute
resource: tool://<required_capability>
```

Structured tools use `required_action` and `required_resource`. A default tool
without either legacy or structured requirements remains executable, preserving
the existing V0.1-V0.5 compatibility behavior.

`agentkernel/resources/service.py` keeps authorization above storage. The
service parses an opaque `artifact://res_*` URI, confirms the owner, evaluates
the capability request if an evaluator is present, validates read bounds, then
calls the store. This keeps `ResourceStore` outside the trusted authorization
decision.

`agentkernel/durable_tools.py` records authorization at prepare and dispatch.
Prepare creates the durable operation only after authorization succeeds.
Dispatch performs a second check immediately before the external side effect.

`agentkernel/recovery.py` keeps older WAL records compatible while validating
new authorization metadata. When both prepare and dispatch contain
authorization metadata, replay requires `agent_id`, `action`, and
`resource_scope` to match.

## 3. Threat Model

| Threat | Impact | Current mitigation | Remaining risk |
|---|---|---|---|
| LLM self-generates capability | A model could try to call hidden tools or claim a grant in arguments. | Capabilities are stored on `AgentControlBlock`, not in model messages. `ToolRegistry.resolve_for_execution()` checks the Kernel-held evaluator before invocation. | Host code must not translate model text into grants without a trusted control path. |
| Tool bypasses Kernel | A handler could directly perform host actions outside AgentKernel. | AgentKernel enforces only calls entering through `ToolRegistry`, `ResourceService`, and `DurableToolExecutor`. | Host integrations must keep sensitive APIs behind Kernel-owned tools and services. |
| Resource overreach | An agent with one artifact handle could request another artifact. | `ResourceService` performs owner check and capability check before reading the store. Unauthorized reads return `EACCES` and do not increment read metrics. | Current artifact scopes are opaque handle URIs; richer logical resource namespaces remain future work. |
| WAL bypasses authorization | A durable mutation could be prepared or dispatched without authority. | `DurableToolExecutor` checks before prepare and again before dispatch. Denied dispatch records `authorization/denied`, aborts with `EACCES`, and does not call the handler. | Manual event construction can still create invalid histories; replay validates shape but cannot prove a historical grant existed outside the event facts. |
| Recovery replay overreach | Restart could re-execute an external side effect under broader or changed authority. | Recovery classification separates prepared-before-dispatch from dispatched operations. Reconcile is required after dispatch for reconcilable mutations, and prepare/dispatch authorization metadata must match. | Future revocation needs an explicit rule for whether recovery uses original authority, current authority, or a dedicated recovery capability. |
| Authorization metadata loss | Missing or malformed metadata could make audit and recovery ambiguous. | New durable records include authorization context; malformed context corrupts replay. Old records without metadata remain loadable for compatibility. | Legacy records are auditable only through surrounding tool and agent data, not through embedded authorization context. |

## 4. Benchmark Result

The final runtime benchmark was run offline through
`benchmarks/capability_runtime_benchmark.py` and wrote
`benchmarks/results/capability_runtime.json`.

| Case | Expected | Observed |
|---|---|---|
| Unauthorized Tool | `DENY` | Tool execution returned `EACCES`; unauthorized tool was not model-visible. |
| Unauthorized Resource Read | `DENY` | Resource read returned `EACCES`; no store read was recorded. |
| Unauthorized Payment Dispatch | `DENY` | Dispatch authorization was denied; no external payment handler ran. |
| Crash After Prepare | Recovery without duplicate | Prepared operation replayed as `safe_to_retry`; retry created one external effect and completed the session. |
| Legacy Tool | Backward compatible | Legacy `required_capability` tool remained visible and executable with the matching string capability. |

The benchmark is synthetic and offline. It validates runtime mechanics, not
model intelligence, prompt quality, or production integration behavior.

## 5. Architecture Decision

V0.6 capability enforcement is correctly placed at Kernel boundaries:

- Tool visibility and execution authorization belong in `ToolRegistry`.
- Resource handle authorization belongs in `ResourceService`.
- Mutation authorization and authorization audit facts belong around WAL
  prepare and dispatch in `DurableToolExecutor`.
- Replay validation belongs in `recovery.py`.

This is enough to complete V0.6 without adding a full namespace system or
delegation model. Those concepts should remain deferred until their owning
runtime features exist.

## 6. Remaining Risks

| Risk | Severity | Next treatment |
|---|---|---|
| Constraint semantics are placeholders. | Medium | Define a narrow constraint evaluator only when a real constraint is needed. |
| Revocation semantics are undefined for in-flight durable operations. | High | Freeze a recovery-specific rule before implementing revocation. |
| Namespace normalization is not implemented. | Medium | Add canonicalization before accepting user-shaped logical namespaces. |
| Authorization audit is minimal. | Medium | Keep current events as facts; design query/report tooling later. |
| Multi-agent ownership is not modeled. | Medium | Introduce delegation and ownership transfer with V0.8 multi-agent design, not now. |
| Default unrestricted tools remain supported for compatibility. | Medium | Future hosts should prefer explicit grants for sensitive tools. |

## 7. Final Decision

`READY_FOR_V0.6_COMPLETION`

The V0.6 capability implementation validates the intended OS-inspired Kernel
principle: untrusted agent output proposes actions, while Kernel-owned services
decide authorization at tool, resource, durable side-effect, and recovery
boundaries.
