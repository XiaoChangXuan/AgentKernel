# V0.6 Capability / Namespace Architecture Design

## 1. Motivation

AgentKernel already treats the model as an untrusted proposer. The model may
ask to call a tool, read a resource handle, compact context, or eventually spawn
another agent, but it must not be the authority that decides whether the action
is allowed.

V0.6 needs a capability architecture because V0.1-V0.5 have created real kernel
objects:

- `AgentControlBlock` gives each agent identity, lifecycle state, budgets, and
  a bounded string capability set.
- `ToolRegistry` controls the model-visible tool surface and rechecks tool
  authorization before execution.
- `DurableToolExecutor` journals mutation intent before dispatch and must avoid
  unauthorized side effects before or after crash recovery.
- `Context VM` creates a bounded working set, but context pages are not an
  authority source.
- `ResourceService` creates durable artifact handles and checks owner, URI, byte
  range, and read limits before reaching storage.

The current mechanism is intentionally small. It is enough for V0.5, but it is
not expressive enough for future AgentKernel versions:

- V0.7 Process / Scheduler needs per-agent authority that survives scheduling,
  pausing, resuming, and recovery.
- V0.8 IPC / Multi-agent needs delegation and isolation between parent and
  child agents.
- V0.9 Memory needs scoped reads and writes to memory objects, not only tool
  execution.
- External side effects need action-specific permission, auditability, and
  revocation semantics around WAL recovery.

The goal of V0.6 is therefore not "more strings". The goal is a small,
Kernel-owned authorization model that can answer:

```text
subject:    Which agent is acting?
action:     What operation is requested?
object:     Which tool, resource, agent, or external namespace is targeted?
constraints What contextual bounds must hold?
decision:   Allow, deny, or require policy/approval.
```

## 2. Current State Review

### 2.1 Current Model

The current implementation is centered on exact string membership.

In `agentkernel/agent.py`:

- `AgentControlBlock.agent_id`
- `AgentControlBlock.session_id`
- `AgentControlBlock.parent_agent_id`
- `AgentControlBlock.capabilities: frozenset[str]`
- `AgentControlBlock.capability_bounding_set: frozenset[str]`
- `AgentControlBlock.has_capability(capability: str) -> bool`

In `agentkernel/tools.py`:

- `ToolDefinition.required_capability: str | None`
- `ToolRegistry.model_schemas(agent)`
- `ToolRegistry.resolve_for_execution(call, agent)`

In `agentkernel/durable_tools.py`:

- `DurableToolExecutor.execute()` calls `resolve_for_execution()` before
  appending `tool/prepare`.
- `retry()` and `reconcile()` re-resolve the prepared operation through the
  registry before another action.

In `agentkernel/resources/`:

- `resource_tool_definitions()` registers `resource_stat` and `resource_read`
  with `required_capability="resource.read"` by default.
- `ToolExecutionContext` supplies trusted `agent_id` and `session_id`.
- `ResourceService` checks URI shape, exact owner, offset, limit, and maximum
  read size before reading bytes from the `ResourceStore`.

Current authorization shape:

```text
ToolDefinition.required_capability
  -> exact string membership in AgentControlBlock.capabilities
  -> optional ResourceService owner/range check for resource tools
```

### 2.2 What Works

The current model has several important properties that V0.6 should preserve:

- Tool schema projection and tool execution both enforce the same capability
  gate.
- The model never receives handlers, credentials, runtime identities, timeouts,
  or the capability set itself.
- Effective capabilities are frozen on the ACB and cannot exceed the bounding
  set at construction time.
- Mutation tools cannot append `tool/prepare` before authorization succeeds.
- Durable retry and reconcile cannot bypass the registry.
- Resource handles are opaque model-facing references, not store paths.
- Resource reads are checked by a second trusted service after tool
  authorization.
- Context VM is a projection mechanism, not a permission store.

### 2.3 What Is Missing

Exact string capabilities do not express:

- action-specific authority such as read, write, execute, dispatch, reconcile,
  delegate, spawn, or revoke;
- resource scopes such as one artifact, one session, one project subtree, one
  dataset prefix, or one external account;
- constraints such as maximum bytes, maximum calls, expiration time, required
  approval, or no-network execution;
- delegation chains from parent agent to child agent;
- revocation of one grant without replacing the whole ACB;
- audit-friendly authorization decisions;
- partial authority over one tool, such as "may call payment.quote but may not
  dispatch payment.charge";
- durable operation rules after a crash, especially when a grant is revoked
  between `tool/dispatch` and restart.

### 2.4 Design Conclusion

The current model is a safe V0.5 scaffold but must not become the long-term
permission language.

V0.6 should keep compatibility with existing exact strings, then add a
structured authorization layer that treats old strings as legacy grant aliases.
No V0.1-V0.5 public behavior must be overturned to do this.

## 3. Capability Model

### 3.1 Kernel Objects

V0.6 should define the following conceptual objects. Names are design terms, not
an implementation mandate.

```text
AgentIdentity
CapabilityGrant
Action
ResourceScope
Constraint
AuthorizationRequest
AuthorizationDecision
CapabilityPolicy
```

### 3.2 Agent Identity

`AgentIdentity` is the subject of authorization.

Required fields:

| Field | Meaning |
|---|---|
| `agent_id` | Stable Kernel identity for the acting agent. |
| `session_id` | Session whose event log and recovery state the agent is using. |
| `parent_agent_id` | Optional parent identity for delegation lineage. |
| `root_agent_id` | Top-level task identity, useful for audit and subtree revocation. |
| `generation` | Optional incarnation counter after fork/restart. |
| `delegation_depth` | Optional maximum or current delegation depth. |

Current `AgentControlBlock` already has `agent_id`, `session_id`, and
`parent_agent_id`. V0.6 can derive an `AgentIdentity` view without changing core
code during the design phase.

### 3.3 Capability

A capability should be a Kernel-owned grant, not just a string.

Proposed logical shape:

```text
CapabilityGrant
  grant_id: stable kernel id
  subject: AgentIdentity or agent_id
  actions: set[Action]
  scope: ResourceScope
  constraints: set[Constraint]
  issuer: "kernel" | parent_agent_id | host_policy_id
  parent_grant_id: optional grant id
  issued_at: timestamp or event seq
  expires_at: optional timestamp
  revocation_epoch: optional integer
  audit_label: optional string
```

Important properties:

- Grants are positive authority only. Absence means deny.
- A grant can only be narrowed during delegation.
- The Kernel owns grant evaluation.
- Policy code may issue grants, but policy code does not bypass Kernel checks.
- Legacy capability strings remain representable as grant aliases.

Legacy mapping:

| V0.5 string | V0.6 compatibility grant |
|---|---|
| `math.add` | `execute` on `tool://math.add` |
| `payments.charge` | `execute` on `tool://payments.charge` |
| `resource.read` | `read, stat` on `artifact://session/<session_id>/**` |

This mapping should be conservative. It should preserve existing behavior first,
then allow hosts to opt into narrower grants.

### 3.4 Action

Actions should be verbs with Kernel meaning. They should not be arbitrary tool
names.

Core action vocabulary:

| Action | Meaning |
|---|---|
| `tool.execute` | Invoke a registered tool handler. |
| `tool.prepare` | Create durable mutation intent. |
| `tool.dispatch` | Dispatch an external side effect. |
| `tool.reconcile` | Observe external operation state after recovery. |
| `resource.stat` | Read safe metadata for a resource handle. |
| `resource.read` | Read resource bytes or decoded content. |
| `resource.write` | Create or modify a resource. |
| `resource.delete` | Delete or expire a resource. |
| `agent.spawn` | Create a child agent. |
| `agent.signal` | Pause, resume, cancel, or otherwise signal an agent. |
| `agent.delegate` | Delegate a subset of grants to another agent. |
| `ipc.send` | Send a message to another agent or process. |
| `ipc.receive` | Receive from another agent or process. |
| `memory.read` | Read durable memory. |
| `memory.write` | Write durable memory. |

The action list should stay small. Tool-specific detail belongs in scope and
constraints.

### 3.5 Resource Scope

`ResourceScope` names the object space. It should use URI-like identifiers so
Tools, Resources, Agents, Memory, and external systems can share one
authorization request shape.

Proposed scope grammar:

```text
<scheme>://<authority>/<path>
```

Initial schemes:

| Scheme | Examples | Meaning |
|---|---|---|
| `tool://` | `tool://math.add`, `tool://payments.charge` | Registered tool namespace. |
| `artifact://` | `artifact://session/s1/res_abc`, `artifact://agent/a1/**` | V0.5 artifact resources. |
| `agent://` | `agent://a1`, `agent://root/r1/**` | Agent identities and subtrees. |
| `session://` | `session://s1/events`, `session://s1/context/**` | Session-local kernel objects. |
| `memory://` | `memory://project/p1/**`, `memory://agent/a1/profile` | Future V0.9 memory. |
| `dataset://` | `dataset://sales-readonly/**` | Future dataset resources. |
| `database://` | `database://orders/prod/table/orders/**` | External structured stores. |
| `network://` | `network://api.stripe.com/**` | External network boundary. |
| `model://` | `model://openai/gpt-*` | Optional model/provider authority. |

Wildcards should be suffix-only at first:

```text
artifact://session/s1/**
tool://payments.*
database://orders/prod/table/orders/**
```

Avoid arbitrary regex in V0.6. Regex scopes are powerful but difficult to audit.

### 3.6 Constraint

Constraints narrow a grant beyond action and scope.

Recommended initial constraint types:

| Constraint | Example | Purpose |
|---|---|---|
| `expires_at` | `2026-08-25T20:00:00Z` | Time-bound authority. |
| `max_calls` | `10` | Prevent runaway repeated use. |
| `max_bytes` | `65536` | Bound resource reads. |
| `max_resource_bytes` | `134217728` | Bound writes/externalization. |
| `effect_kind` | `READ_ONLY`, `IDEMPOTENT_MUTATION` | Align with durable tool semantics. |
| `requires_approval` | `true` | Escalate to host/human policy. |
| `allowed_args` | JSON predicate profile | Narrow one tool by argument shape. |
| `deny_network` | `true` | Prevent network-capable execution. |
| `namespace_root` | `artifact://session/s1/**` | Bind child views to a subtree. |
| `recovery_only` | `true` | Allow reconcile/finish but not new dispatch. |

V0.6 should implement only the minimal set required by the first capability
release. The design should reserve the vocabulary without requiring every
constraint on day one.

### 3.7 Ownership

Capability should belong to the Kernel as a grant record.

The relationship should be:

| Object | Owns |
|---|---|
| Kernel | Grant semantics, evaluation, audit, revocation state. |
| Agent | Receives effective grants through its ACB or an attached grant set. |
| Tool | Declares required actions/scopes/effect metadata. |
| Resource | Carries identity, owner, kind, and metadata used during checks. |
| Policy layer | Decides which grants to issue, request, approve, revoke, or renew. |

This avoids three failure modes:

- If Agent owns capability, a compromised loop may mutate its own authority.
- If Tool owns capability, authorization becomes plugin-local and inconsistent.
- If Resource owns capability alone, tool execution and external side effects
  remain underspecified.

## 4. Namespace Model

### 4.1 Principles

Namespaces should make authority legible before any driver is touched.

Design principles:

- Model-facing handles are not backend paths.
- Scope strings name Kernel resources, not arbitrary host filesystem paths.
- Each namespace has one Kernel service or registry responsible for resolution.
- A namespace can be projected differently to parent and child agents.
- Authorization evaluates the requested namespace path before driver dispatch.

### 4.2 Resource Namespace

Current V0.5 has:

```text
artifact://<resource_id>
```

The future resource namespace should make owner and sharing semantics explicit
inside Kernel metadata, while keeping the model-facing handle opaque.

Proposed internal authority patterns:

```text
artifact://session/<session_id>/<resource_id>
artifact://agent/<agent_id>/<resource_id>
artifact://project/<project_id>/<path>
dataset://<dataset_id>/<path>
file://workspace/<workspace_id>/<path>
memory://agent/<agent_id>/<key>
memory://project/<project_id>/<key>
```

V0.6 does not need to change existing V0.5 artifact URIs immediately. The
authorization adapter can resolve `artifact://res_x` to host-only metadata and
then evaluate it as an internal scoped object.

### 4.3 Tool Namespace

Current tool names are simple strings such as `math.add`, `orders.create`, and
`resource_read`.

Recommended V0.6 namespace:

```text
tool://<tool-name>
tool://<package>/<tool-name>
tool://resource/resource_read
tool://payments/charge
```

The first implementation can map existing names directly:

```text
math.add          -> tool://math.add
resource_read     -> tool://resource_read
payments.charge   -> tool://payments.charge
```

Later versions can add package-qualified names without breaking old tools.

Tool definitions should eventually declare:

```text
required_actions:
  - tool.execute
scope:
  - tool://payments.charge
effect_kind:
  - RECONCILABLE_MUTATION
```

### 4.4 Agent Namespace

Future subagents need identity and scope.

Proposed namespace:

```text
agent://<agent_id>
agent://root/<root_agent_id>/**
agent://parent/<parent_agent_id>/child/<child_agent_id>
```

This namespace supports:

- spawn authorization;
- signaling child processes;
- IPC channels;
- delegation lineage;
- subtree revocation.

The current `parent_agent_id` field is enough for design compatibility, but
future V0.7/V0.8 should persist parent-child creation facts in the event log or
a process table.

## 5. Authorization Flow

### 5.1 Common Request Shape

Every Kernel-controlled action should become an authorization request:

```text
AuthorizationRequest
  subject: AgentIdentity
  action: Action
  scope: ResourceScope
  constraints: requested operation facts
  session_id: current session
  turn: optional turn
  step: optional step
  operation_id: optional durable operation id
  tool_call_id: optional model tool call id
  reason: "schema_projection" | "tool_execute" | "resource_read" | "recovery"
```

The evaluator returns:

```text
AuthorizationDecision
  status: ALLOW | DENY | NEEDS_APPROVAL
  matched_grant_ids: tuple[str, ...]
  reason_code: stable machine code
  message: safe diagnostic
  constraints_applied: tuple[Constraint, ...]
```

Stable denial codes matter because model loops and tests should not depend on
provider-specific exception text.

### 5.2 Tool Authorization

Tool schema projection:

```text
for each ToolDefinition:
  request = AuthorizationRequest(
    subject=agent,
    action=tool.execute,
    scope=tool://<tool_name>,
    reason=schema_projection,
  )
  include schema only if ALLOW
```

Tool execution:

```text
model proposes ToolCall
Kernel appends tool/call
Kernel authorizes tool.execute on tool://<tool_name>
if DENY:
  append tool/result EACCES
if ALLOW and READ_ONLY:
  invoke handler
if ALLOW and MUTATION:
  continue into durable side-effect flow
```

The runtime check is mandatory even if the schema was hidden. A model or
provider may emit an unadvertised tool call.

### 5.3 Resource Access

Resource access should require both:

1. tool authorization for the model-facing syscall, and
2. resource authorization for the object being resolved.

Example:

```text
ToolRegistry:
  allow tool.execute on tool://resource_read

ResourceService:
  allow resource.read on artifact://session/s1/res_abc
  enforce owner, offset, limit, max_read_bytes
```

This two-layer shape should remain. The model does not need direct access to
`ResourceStore`, and a capability to call `resource_read` should not imply read
access to every resource in every session.

### 5.4 External Side Effect Permission

Durable mutation tools need a stricter flow than read-only tools:

```text
model proposes mutation ToolCall
authorize tool.execute on tool://payments.charge
authorize tool.prepare on tool://payments.charge
append tool/prepare
flush
authorize tool.dispatch on external scope
append tool/dispatch
flush
call external system with operation_id
append tool/commit or tool/abort
flush
append tool/result
```

In many cases `tool.execute` and `tool.dispatch` can be satisfied by the same
grant. The split still matters because V0.6 must distinguish:

- permission to ask for a tool;
- permission to create a durable mutation intent;
- permission to dispatch an external side effect;
- permission to reconcile an ambiguous external operation after restart.

### 5.5 Recovery Authorization

Recovery must not accidentally amplify authority.

Rules:

- Retrying a prepared but undispatched operation requires current
  `tool.dispatch` authority.
- Reconciling an operation after `tool/dispatch` may use a narrower
  `tool.reconcile` grant.
- If a side effect may already have occurred, revocation should not erase the
  Kernel's ability to record a safe observation or final classification.
- A revoked grant should prevent new dispatches, but a `recovery_only`
  constraint may allow reconcile/abort/commit bookkeeping for already prepared
  operations.

This keeps revocation useful without corrupting WAL recovery.

### 5.6 Audit

V0.6 should plan for authorization audit events, but implementation can defer
them until the evaluator exists.

Candidate event:

```text
authz/decision
  turn
  step
  subject_agent_id
  action
  scope
  status
  reason_code
  matched_grant_ids
  operation_id?
  tool_call_id?
```

If persisted, audit events must not expose secrets, raw credentials, or full
tool arguments unless the host explicitly opts in.

## 6. Delegation Model

### 6.1 Parent Agent

A parent agent may create a child only if it has `agent.spawn` authority for the
target agent namespace.

The parent may delegate only a subset of its own effective authority:

```text
child_grants <= parent_effective_grants
child_grants <= parent_bounding_set
child_grants <= requested_child_bounding_set
```

The parent can add restrictions:

- narrower scope;
- fewer actions;
- lower budgets;
- shorter expiration;
- smaller byte limits;
- approval-required constraints;
- lower delegation depth.

The parent cannot remove restrictions inherited from its own grants.

### 6.2 Child Agent

A child agent should start with:

- its own `agent_id`;
- the same or a forked `session_id`, depending on scheduler design;
- a `parent_agent_id`;
- a grant set derived from parent grants;
- a bounding set that cannot exceed the parent-delegated grants;
- an optional namespace root such as `artifact://agent/<child_id>/**`.

The child should not receive parent credentials, parent handles, or parent tool
authority unless delegated explicitly.

### 6.3 Capability Inheritance

Inheritance should be explicit, not ambient.

Bad model:

```text
child.capabilities = parent.capabilities
```

Better model:

```text
for each requested child grant:
  verify parent can delegate matching grant
  intersect action/scope/constraints
  create child grant with parent_grant_id
```

This creates an audit trail and gives revocation a concrete chain to walk.

### 6.4 Restriction

Restriction is intersection:

```text
parent grant:
  actions = {resource.read, resource.stat}
  scope = artifact://project/p1/**
  max_bytes = 65536

child request:
  actions = {resource.read}
  scope = artifact://project/p1/logs/**
  max_bytes = 8192

child grant:
  actions = {resource.read}
  scope = artifact://project/p1/logs/**
  max_bytes = 8192
```

If intersection is empty, deny delegation.

### 6.5 Revocation

Revocation should support:

| Revocation target | Effect |
|---|---|
| grant id | Disable one grant. |
| grant subtree | Disable delegated descendants. |
| agent id | Disable all grants issued to one agent. |
| agent subtree | Disable a parent and all children. |
| namespace scope | Disable future access to one resource/tool subtree. |

Revocation does not undo completed external effects. It only affects future
authorization decisions and recovery actions according to the recovery rules
above.

### 6.6 ACB Impact

Current `AgentControlBlock` does not need a design-time change. Future
implementation likely needs either:

1. an attached immutable `grants` field on ACB, or
2. a Kernel-owned grant store keyed by `agent_id`.

Recommended implementation direction:

```text
ACB keeps identity and lifecycle.
CapabilityStore owns grant records and revocation state.
AuthorizationService evaluates ACB identity + grant store + request facts.
```

This avoids turning ACB into a large policy database and keeps future process
scheduler state cleaner.

## 7. Reference Comparison

### 7.1 Linux File Permissions

Linux file permissions separate subject categories and actions: owner, group,
other, and read/write/execute bits. The lesson for AgentKernel is that a small
verb vocabulary is useful and auditable.

What AgentKernel should not copy:

- global ambient user identity as the only authority source;
- filesystem-specific assumptions;
- permission bits that cannot express tool effects, resource ranges, or
  delegated subagents.

AgentKernel should copy the discipline of simple verbs, not the exact UNIX file
mode model.

Reference:

- https://www.man7.org/linux/man-pages/man2/chmod.2.html

### 7.2 Linux Capabilities

Linux capabilities split superuser power into smaller per-process privileges and
include bounding concepts. The closest AgentKernel analogue is the current ACB
capability bounding set.

Useful lessons:

- avoid all-powerful root-style grants;
- make effective authority bounded;
- make privilege changes explicit;
- keep a clear distinction between potential and effective authority.

Limits for AgentKernel:

- Linux capabilities are mostly operation classes, not fine-grained object
  grants;
- they do not by themselves describe resource scopes such as one artifact
  handle, one dataset prefix, or one external account;
- AgentKernel needs delegation and revocation chains for subagents.

Reference:

- https://www.man7.org/linux/man-pages/man7/capabilities.7.html

### 7.3 Linux Namespaces

Linux namespaces make selected global resources appear isolated to processes in
one namespace. AgentKernel should adopt the idea of distinct views over shared
resource spaces.

Useful lessons:

- isolation is not only "deny"; it can also be "this subject sees a different
  root";
- namespaces are natural for future child agents, IPC, memory, and resources;
- namespaces should be resolved by trusted services, not by model text.

Limits for AgentKernel:

- AgentKernel namespaces are logical runtime namespaces, not OS namespaces;
- the Kernel may still rely on OS sandboxes below it for host safety;
- namespace membership must combine with action grants.

Reference:

- https://www.man7.org/linux/man-pages/man7/namespaces.7.html

### 7.4 Capsicum

Capsicum is a strong conceptual match because it shifts authority from ambient
global lookup to explicit object capabilities. A file descriptor-like handle
with refined rights is close to what AgentKernel wants for `ResourceHandle`.

Useful lessons:

- handles should carry or resolve to rights;
- global namespaces should be restricted after entering a sandboxed mode;
- least privilege works better when components receive only the objects they
  need;
- capability mode and object handles can coexist with existing UNIX APIs.

Limits for AgentKernel:

- AgentKernel cannot rely only on unforgeable in-process object references,
  because model-visible handles are strings and must be validated;
- AgentKernel must record enough authority decisions for replay and audit.

References:

- https://www.cl.cam.ac.uk/research/security/capsicum/
- https://www.usenix.org/legacy/events/sec10/tech/full_papers/Watson.pdf

### 7.5 Kubernetes RBAC

Kubernetes RBAC models authorization as subjects, verbs, resources, API groups,
namespaces, roles, and bindings. This is structurally close to the desired
AgentKernel request shape.

Useful lessons:

- separate identity from policy binding;
- evaluate request attributes, not only subject labels;
- make verbs and resource scopes explicit;
- keep least privilege and privilege-escalation concerns visible.

Limits for AgentKernel:

- Kubernetes RBAC is cluster/API-server oriented and can become heavy;
- AgentKernel should avoid YAML-style policy sprawl in V0.6;
- constraints such as byte limits, operation IDs, and recovery-only authority
  are agent-runtime-specific.

References:

- https://kubernetes.io/docs/reference/access-authn-authz/authorization/
- https://kubernetes.io/docs/reference/access-authn-authz/rbac/
- https://kubernetes.io/docs/concepts/security/rbac-good-practices/

### 7.6 Codex Sandbox

Codex is relevant as a coding-agent runtime reference: sandboxing, approvals,
network policy, managed configuration, and telemetry are treated as operational
boundaries around model-directed action.

Useful lessons:

- approvals are constraints on actions, not a substitute for authorization;
- network access deserves its own policy surface;
- sandboxing and audit are runtime controls, not prompt instructions;
- local OS boundaries and logical agent capabilities should complement each
  other.

Limits for AgentKernel:

- AgentKernel is an embeddable library, not a full Codex product surface;
- V0.6 should design logical capability checks first and leave OS sandbox
  drivers as a lower layer;
- model intelligence and permission safety must remain separate concerns.

References:

- https://openai.com/index/running-codex-safely/
- https://openai.com/index/building-codex-windows-sandbox/
- https://developers.openai.com/api/docs/guides/agents/sandboxes

### 7.7 OpenHands

OpenHands is relevant for workspace isolation and action confirmation. Its
workspace abstraction separates local execution from container/remote execution,
and its security layer evaluates action risk before execution.

Useful lessons:

- the execution workspace is a major security boundary;
- local and remote execution should share an abstraction but not the same risk;
- confirmation policy is a policy layer around lower-level authority;
- mounted read-write workspace data remains writable by the agent and must be
  treated as part of the permission boundary.

Limits for AgentKernel:

- AgentKernel should not become a workspace product in V0.6;
- Docker/remote workspace isolation belongs below or beside the Kernel as a
  driver/policy layer;
- Kernel authorization should still happen even inside an isolated workspace.

References:

- https://docs.openhands.dev/openhands/usage/sandboxes/overview
- https://docs.openhands.dev/openhands/usage/sandboxes/docker
- https://docs.openhands.dev/sdk/arch/workspace
- https://docs.openhands.dev/sdk/arch/security

### 7.8 DeepSeek Harness

DeepSeek Harness is relevant because it treats models, tools, sessions,
sandboxes, storage, loops, scheduling, and UI as swappable plugin-provided
capabilities, with append-only session traceability.

Useful lessons:

- capability seams should be explicit extension points;
- session/surface separation is important for context and audit;
- compaction and tool-result pruning can be optional services rather than loop
  core;
- subagent capability families should be designed before multi-agent execution
  becomes complex.

Limits for AgentKernel:

- AgentKernel intentionally keeps a smaller trusted core;
- plugins should not own core authorization semantics;
- V0.6 should define Kernel invariants before adding broad plugin composition.

References:

- https://www.deepseek.com/harness/en/
- https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/compaction.md
- https://github.com/deepseek-ai/deepseek-harness/tree/master/docs/subsystems

## 8. Compatibility With V0.1-V0.5

### 8.1 V0.1 Execution Kernel

No required change.

V0.1 has a clean tool syscall boundary:

```text
LLM proposes ToolCall
Kernel resolves and authorizes
Tool handler executes under ToolExecutionContext
ToolResult returns to Session
```

V0.6 can replace exact string checks inside this boundary without changing the
public turn/step loop semantics.

### 8.2 V0.2 Persistence / Recovery

No required change before V0.6 implementation.

Authorization decisions may later become audit events, but the Session Event Log
does not need to be rewritten. Recovery can continue to analyze the existing
tool and durable operation events. If `authz/decision` is added later, it should
be additive and ignored by old semantic recovery rules where possible.

### 8.3 V0.3 Durable Tool Execution

No required change now.

V0.3 already has the correct ordering:

```text
authorize before prepare
prepare before dispatch
dispatch before commit/abort
re-resolve during retry/reconcile
```

V0.6 should attach structured authorization to this flow. The main design work
is deciding whether a prepared operation captures the grant used at prepare time
or only re-evaluates current grants at retry/reconcile time.

Recommended rule:

- new dispatch requires current authority;
- reconcile of already-dispatched work may use recovery-only authority;
- commit/abort bookkeeping may proceed when it records observed truth rather
  than causing a new external effect.

### 8.4 V0.4 Context VM

No required change.

Context Pages are model-working-set objects. They should not become authority
objects. They may carry provenance and trust labels, but capability checks
should happen at tool/resource/agent boundaries.

Future context-related permissions can be expressed as actions:

- `session.read_context`
- `session.pin_context`
- `context.compact`
- `memory.inject`

These should remain Kernel actions, not prompt policy.

### 8.5 V0.5 Resource Layer

No required change.

V0.5 already separates:

```text
ResourceHandle      model-safe projection
ResourceMetadata    host-only identity and owner facts
ResourceService     trusted URI/owner/range enforcement
ResourceStore       replaceable byte driver
```

V0.6 can place structured resource authorization in `ResourceService` without
changing the handle format immediately. Existing `resource.read` remains a
legacy grant alias.

### 8.6 Compatibility Matrix

| Area | V0.6 impact | Reason |
|---|---|---|
| `AgentControlBlock.capabilities` | Compatible legacy field | Exact strings can become grant aliases. |
| `capability_bounding_set` | Compatible concept | Maps to maximum delegable/effective grant set. |
| `ToolDefinition.required_capability` | Compatible legacy declaration | Can compile to `tool.execute` on `tool://name`. |
| `ToolRegistry.model_schemas()` | Same boundary | Replace predicate internals later. |
| `ToolRegistry.resolve_for_execution()` | Same boundary | Becomes common authorization call. |
| `DurableToolExecutor` | Same ordering | Add action-specific checks around prepare/dispatch/reconcile. |
| `Session` | Additive at most | Optional audit events should not rewrite existing events. |
| `Context VM` | No direct change | Context remains projection, not authority. |
| `ResourceHandle` | No immediate change | Resolve old URI to internal scoped object. |
| `ResourceService` | Medium extension later | Add structured resource-scope checks after owner/range validation design. |

## 9. Implementation Roadmap

### 9.1 V0.6 Design

Deliverables:

- freeze action vocabulary for V0.6 minimum viable capability;
- freeze scope URI grammar and wildcard rules;
- define `AuthorizationRequest` and `AuthorizationDecision`;
- define legacy string mapping;
- define delegation and revocation semantics;
- define recovery-specific authorization rules;
- decide whether audit events are V0.6 implementation or V0.7 additive work;
- write denial and compatibility test matrix.

No runtime code changes are required for this design document.

### 9.2 V0.6 Implementation

Recommended implementation slices:

1. Add structured capability data types behind a compatibility adapter.
2. Add `AuthorizationService` or `CapabilityPolicy` with allow/deny decisions.
3. Convert `AgentControlBlock.capabilities` strings into compatibility grants.
4. Route `ToolRegistry.model_schemas()` through the evaluator.
5. Route `ToolRegistry.resolve_for_execution()` through the evaluator.
6. Add resource-scope checks to `ResourceService` while preserving current
   owner/range checks.
7. Add durable mutation action checks:
   `tool.prepare`, `tool.dispatch`, `tool.reconcile`.
8. Add optional audit events if they do not complicate recovery.
9. Add delegation APIs only after the single-agent evaluator is stable.

Implementation must preserve:

- existing tests using `required_capability`;
- existing resource tool behavior under `resource.read`;
- existing WAL ordering;
- existing model schema projection behavior;
- deterministic EACCES for unauthorized tool calls.

### 9.3 V0.6 Benchmark

Benchmark goals:

- show authorization overhead is small compared with tool/model latency;
- show hidden schemas and runtime denial agree;
- show resource-scope checks prevent cross-session handle reads;
- show mutation prepare does not occur when authorization fails;
- show retry/reconcile obey revocation and recovery-only rules;
- show child delegation cannot exceed parent authority.

Candidate benchmark cases:

| Benchmark | Scenario | Metric |
|---|---|---|
| Tool projection | 1,000 registered tools, 100 grants | schema projection latency |
| Runtime denial | model emits hidden tool call | stable EACCES, no handler invocation |
| Resource scope | read own vs foreign artifact | allow/deny correctness |
| WAL auth | unauthorized payment charge | no `tool/prepare`, no external call |
| Revocation | revoke after prepare before dispatch | no new dispatch |
| Recovery-only | revoke after dispatch then restart | reconcile allowed, duplicate dispatch denied |
| Delegation | child requests broader grant | denied amplification |
| Namespace wildcard | prefix grant over many resources | matching latency and correctness |

## 10. Open Design Decisions

The following decisions should be resolved before implementation:

| Question | Recommended answer |
|---|---|
| Should capability grants be persisted in Session? | No for global grant store; yes for delegation/audit facts if they affect replay. |
| Should resources carry grants in metadata? | No. Resources carry owner/identity; grants remain Kernel policy objects. |
| Should ToolDefinition own required actions? | It may declare requirements, but Kernel evaluates them. |
| Should denial be visible to the model? | Yes as stable ToolResult failure, without leaking policy internals. |
| Should revocation cancel in-flight work? | It should prevent new actions; already-dispatched side effects require recovery classification. |
| Should Context Pages carry capabilities? | No. They may carry provenance/trust labels, not authority. |
| Should V0.6 include approval UI? | No. Represent `NEEDS_APPROVAL`; host policy/UI can implement approval later. |

## 11. Final Recommendation

Proceed with V0.6 as a structured, Kernel-owned authorization layer that
preserves current string capabilities as compatibility aliases.

Do not modify V0.1-V0.5 APIs before implementation begins. The current Kernel
boundaries are sufficient:

```text
Agent identity:       AgentControlBlock
Tool boundary:        ToolRegistry
Side-effect WAL:      DurableToolExecutor
Resource boundary:    ResourceService
Context projection:   Context VM
Recovery source:      Session Event Log
```

V0.6 should add a common evaluator at these existing boundaries rather than
moving authority into prompts, tools, resources, or context pages.
