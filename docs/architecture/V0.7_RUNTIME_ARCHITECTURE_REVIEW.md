# V0.7 Runtime Architecture Review

Status: architecture review after V0.7 Process Core, Cooperative Scheduler, and Resource Accounting.

Scope:

- Review the current Process Runtime boundary.
- Verify compatibility with V0.1-V0.6 mechanisms.
- Do not design or implement V0.8 IPC, multi-agent runtime, namespace, or delegation.
- Do not modify `agentkernel/` core code.

## 1. Executive Summary

The current V0.7 runtime boundary is coherent and still follows the AgentKernel
OS-inspired split:

```text
Agent   = capability principal
Process = runtime identity and schedulable execution state
Session = durable journal and replay source of truth
```

`ProcessControlBlock`, `ProcessManager`, `CooperativeScheduler`, and
`UsageCollector` add runtime control without replacing Session recovery or moving
capability authority away from the Agent. The scheduler is a Kernel mechanism:
it owns lifecycle transitions, READY/WAITING/BLOCKED registries, cooperative safe
points, pause/cancel signals, and budget blocking. It does not decide business
policy.

Accounting is correctly modeled as runtime observation, not durable truth.
Runtime usage can block a process, but the authoritative replay facts remain in
the Session event log and durable Tool WAL.

Final review decision:

```text
V0.7_RUNTIME_BOUNDARY_STABLE
```

No Phase 4 or V0.8 implementation is required before freezing this boundary.

## 2. Agent / Process / Session Relationship

Current relationship:

| Layer | Current owner | Durable? | Primary responsibility |
| --- | --- | --- | --- |
| Agent | `AgentControlBlock` | No, except referenced by Session id | Capability principal, legacy lifecycle compatibility, budget source |
| Process | `ProcessControlBlock` | No | Runtime identity, lifecycle state, scheduler inputs, pause/cancel flags |
| Session | `Session` | Yes | Append-only event log, model history projection, recovery analysis |

The split is valid.

`AgentControlBlock` still owns `agent_id`, legacy capability strings, bounding
set, structured `CapabilityGrant` values, and `AgentBudget`. `ProcessControlBlock`
copies only an immutable `CapabilitySnapshot` for runtime attribution and sanity
checking. The snapshot does not make `process_id` an authorization subject.

`ProcessControlBlock` stores `process_id`, `agent_id`, `session_id`, lifecycle
state, parent-process placeholder, priority, budget, wait/block reasons,
pause/cancel flags, capability snapshot, and exit status. This is live runtime
state. It is not written as a new Session event stream.

`Session` remains the only durable journal. Recovery uses `Session.recovery_analysis`
and `analyze_recovery()` to rebuild semantic facts, then
`ProcessControlBlock.from_recovery()` maps those facts into `READY`, `BLOCKED`,
or `EXITED`.

Review result:

```text
PASS
```

The three-layer split is stable for V0.7.

## 3. Scheduler Boundary

The scheduler remains a Kernel mechanism.

Kernel-owned mechanisms:

| Mechanism | Current implementation |
| --- | --- |
| Live process table | `ProcessManager` |
| READY queue | `CooperativeScheduler._ready` |
| WAITING registry | `CooperativeScheduler._waiting` |
| BLOCKED registry | `CooperativeScheduler._blocked` |
| Dispatch | `dispatch()` moves READY to RUNNING |
| Cooperative yield | `yield_process()` moves RUNNING to READY/WAITING/BLOCKED |
| Wake/unblock | `wake()` and `unblock()` return processes to READY |
| Pause/cancel signal | `request_pause()`, `request_cancel()`, `safe_point()` |
| Budget blocking | `safe_point()` checks `UsageCollector` and blocks on exceeded quota |

Policy left outside the scheduler:

| Policy decision | Current owner |
| --- | --- |
| Which model to use | Host / provider integration |
| Whether to increase budget | Host policy |
| Whether to resume or terminate a blocked process | Host policy |
| Retry or reconciliation policy after durable recovery | Host policy over recovery facts |
| Context reclaim strategy | Context VM policy |
| Capability grant assignment | Host / Agent construction |

`DefaultAgentLoop` only calls scheduler safe points around existing boundaries:
turn start, step start, LLM call, Tool call, and durable dispatch. This is the
right integration depth. The loop remains the single-agent execution driver,
while scheduler control is optional.

Review result:

```text
PASS
```

The scheduler has not absorbed policy, tool authorization, resource
authorization, durable WAL ownership, or Context VM policy.

## 4. Accounting Boundary

Accounting remains runtime observation rather than durable truth.

`ProcessUsageSnapshot` captures process-local observations:

- provider-reported token usage;
- host-supplied model cost;
- observed Tool call count;
- sampled ResourceService metrics;
- monotonic wall time.

`UsageCollector` is in-memory and process-local. It does not append Session
events, does not change recovery analysis, does not authorize resources, and does
not own ResourceService or ResourceStore.

Budget enforcement is a runtime stop condition:

```text
UsageCollector snapshot
      |
CooperativeScheduler.safe_point()
      |
RUNNING -> BLOCKED
blocked_reason = budget_exceeded:<limit>
```

The Session may contain a `TURN_END` reason such as
`resource_budget_exceeded`, but the usage counters themselves are not durable
facts. This distinction is important: replay must reconstruct what happened, not
recreate live quota counters as if they were canonical history.

Review result:

```text
PASS_WITH_KNOWN_LIMITATION
```

The boundary is correct. The known limitation is that budget recovery semantics
depend on host policy because counters are intentionally not a durable ledger.

## 5. Capability Ownership

Capability authority remains Agent-owned.

Current enforcement path:

```text
AgentControlBlock
      |
CapabilityEvaluator.from_agent_capabilities()
      |
ToolRegistry / ResourceService / DurableToolExecutor
```

`ProcessControlBlock.capability_snapshot` is only a point-in-time Agent-derived
view. Tests enforce that grant subjects match `agent_id`, not `process_id`.

The scheduler does not create, grant, revoke, or evaluate capabilities. It may
block a process for budget or lifecycle reasons, but that is not authorization.

Review result:

```text
PASS
```

V0.7 preserves the V0.6 rule: Agent is the authority principal; Process is the
runtime identity.

## 6. Context VM Ownership

Context VM ownership remains separate from Process ownership.

Current ownership:

| Context concern | Owner |
| --- | --- |
| Event projection into Context Pages | `ContextProjector` / `ContextManager` |
| Working-set selection | `ContextManager` and `ContextPolicy` |
| Context budget and reclaim | Context VM |
| Durable compaction facts | Session events validated by recovery |
| Runtime WAITING state during context work | Scheduler |

The scheduler marks a process `WAITING` while context preparation or reclaim is
awaited, but it does not select pages, compact context, assign page priority, or
choose reclaim policy.

If recovery detects an active context compaction, `ProcessControlBlock.from_recovery()`
maps the process to:

```text
BLOCKED
blocked_reason = context_compaction_recovery
```

That is appropriate: the durable compaction state is a Session/recovery fact,
while the BLOCKED process state is the live runtime consequence.

Review result:

```text
PASS
```

Context VM remains the owner of memory-management semantics.

## 7. Resource Ownership

Resource ownership remains Resource Layer-owned, with Agent/session identity as
the access boundary.

Current ownership:

| Resource concern | Owner |
| --- | --- |
| Handle projection | `ResourceHandle` |
| Host metadata | `ResourceMetadata` |
| Owner identity | `ResourceOwner(agent_id, session_id)` |
| Authorization check | `ResourceService` using `CapabilityEvaluator` |
| Byte persistence | `ResourceStore` |
| Metrics | `ResourceMetrics` sampled by `UsageCollector` |

`ResourceService` checks owner before capability and range validation. This keeps
the store replaceable and untrusted for authorization. `ResourceStore` remains a
driver and does not make access decisions.

Accounting integration samples `ResourceMetrics` externally. That means Resource
metrics are runtime observations, not Session facts. The tradeoff is acceptable
for V0.7, but shared ResourceService attribution must be revisited before
multi-process or multi-agent scheduling.

Review result:

```text
PASS_WITH_FUTURE_ATTRIBUTION_RISK
```

Resource authority did not move into Process or Scheduler.

## 8. Durable Tool WAL Compatibility

Durable Tool WAL compatibility is preserved.

Current mutation order:

```text
Tool authorization at execution boundary
      |
AUTHORIZATION_GRANTED / AUTHORIZATION_DENIED audit event
      |
TOOL_PREPARE
      |
dispatch authorization
      |
TOOL_DISPATCH
      |
external effect
      |
TOOL_COMMIT or TOOL_ABORT
```

Scheduler safe points wrap durable execution but do not change WAL event schema
or operation ids. The durable executor still owns prepare, dispatch, commit,
abort, authorization metadata, retry, and reconciliation.

Recovery validates authorization context carried by prepare/dispatch records and
requires dispatch authorization to match prepare authorization for the same
operation. This protects the binding between `operation_id` and authorization
context.

Review result:

```text
PASS
```

V0.7 scheduling and accounting do not weaken V0.3/V0.6 durable side-effect
semantics.

## 9. Recovery After Process Crash

Process crash recovery is currently derived from Session replay, not from a
persisted process table.

Recovery mapping:

| Recovery fact | Process state |
| --- | --- |
| Completed Session | `EXITED`, `exit_status="completed"` |
| Corrupted Session | `EXITED`, `exit_status="corrupted"` |
| Active context compaction | `BLOCKED`, `blocked_reason="context_compaction_recovery"` |
| Durable operation requires reconcile/manual handling | `BLOCKED`, `blocked_reason="durable_operation_recovery"` |
| Ordinary interrupted prefix | `READY` |

This is the correct default for V0.7 because the Session is the durable truth.
The process table and scheduler registries are live runtime state and can be
reconstructed.

Important limitation:

Process pause/cancel requests and runtime accounting counters are not replayed
after a crash. That is acceptable in V0.7 because they are runtime controls, not
durable external facts. A future persisted process table may be useful, but it
must not supersede Session replay.

Review result:

```text
PASS_WITH_LIMITATIONS
```

Recovery after process crash is safe for durable facts and external effects.
Runtime controls may reset unless the host persists them separately.

## 11. Risks And Follow-Ups

| Risk | Severity | Required before V0.8? | Notes |
| --- | --- | --- | --- |
| Process table is not durable | Medium | No | Acceptable while Session replay remains authoritative; future multi-process recovery may need host process reconstruction. |
| Runtime usage counters reset after crash | Medium | No | Correct for observation-only accounting, but billing-grade accounting would require a separate durable ledger. |
| Shared ResourceMetrics attribution | Medium | Yes, before multi-process/multi-agent | Current sampling works for single-process integration but can blur attribution when services are shared. |
| AgentState and ProcessState coexist | Low | No | Compatibility bridge is acceptable, but future cleanup should avoid double lifecycle authority. |
| Pause/cancel request durability | Low | No | Runtime control can reset after crash unless host policy persists intent. |
| Budget unblock policy | Low | No | Host decides reset/increase/cancel; Kernel should not encode this policy. |
| Parent process field has no semantics yet | Low | No | Reserved for future process tree/cancellation rules. |

## 12. Final Decision

The V0.7 runtime architecture is stable.

Decision:

```text
V0.7_RUNTIME_BOUNDARY_STABLE
```

The implementation preserves these boundaries:

- Agent owns capability authority.
- Process owns runtime identity and scheduler-visible lifecycle state.
- Session owns durable truth and replay.
- Scheduler owns cooperative runtime mechanism, not policy.
- Accounting observes runtime usage, not durable facts.
- Context VM owns context projection/reclaim.
- Resource Layer owns handles, owner checks, authorization, and store isolation.
- Durable Tool WAL remains compatible with recovery and authorization metadata.

Stop here. Do not begin V0.8 or implement additional V0.7 Phase 4 behavior from
this review.
