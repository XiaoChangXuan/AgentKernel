# AgentKernel V0.5 Virtual Resource / Artifact Handle

## Outcome

V0.5 adds a minimal durable Resource layer for Tool outputs that are too large
to keep in every model request. The full bytes move to a replaceable durable
store; Session and Context contain a bounded preview plus an opaque handle:

```text
Tool handler returns large result
        ↓
ToolResultExternalizer (replaceable policy)
        ↓
ResourceService.create_artifact()
        ↓ durable commit
ResourceStore / LocalResourceStore
        ↓
ToolResult { preview, artifact://res_..., safe metadata }
        ↓
mutation commit + Session tool/result → Context projection
```

This is a Resource abstraction, not a filesystem. The only V0.5 scheme and
kind is `artifact://<resource_id>`. There are no model-visible paths, mounts,
directories, rename/delete, search, glob, remote driver, or document parser.

## Boundaries

### Identity and projection

- `ResourceId` (`res_...`) is Kernel-generated object identity.
- `HandleId` (`hdl_...`) is Kernel-generated reference identity.
- `tool_call_id` remains model protocol identity.
- `operation_id` remains durable external-operation identity.

They are separate concepts. `ResourceHandle` is the safe model projection:
handle ID, URI, kind, size, media type, and checksum. `ResourceMetadata` is
host-only and additionally includes owner, encoding, creation time, source Tool
and call/operation identities. Store root and payload path are never projected.

### Store and service

`ResourceStore` is a small driver Protocol:

```text
commit(metadata, bytes)
stat(resource_id)
read(resource_id, offset, limit)
list_metadata()
```

`LocalResourceStore` writes payload and metadata into a staging directory,
fsyncs both files, then atomically publishes the final resource directory. A
handle is returned only after publication. Temporary directories are ignored by
lookup/listing and cleaned on ordinary failures. The configured root makes
handles resolvable by a new process instance.

`ResourceService` owns the semantics above the driver:

- identity creation and strict `artifact://` parsing;
- maximum resource and maximum per-read byte enforcement;
- offset/limit/size validation;
- exact `(agent_id, session_id)` owner authorization;
- model-safe handle projection;
- resource creation/read metrics;
- orphan identification by comparing durable metadata with committed Session
  `tool/result` references.

The model never calls a driver. `resource_stat` and `resource_read` are normal
ToolDefinitions whose handlers call ResourceService with trusted
`ToolExecutionContext` identities. The default capability is `resource.read`.

## Tool Result integration

`DurableToolExecutor` accepts a replaceable `ToolResultProcessor`.
`ToolResultExternalizer` implements that seam with a replaceable
`ToolResultExternalizationPolicy`. The default threshold policy:

1. leaves failures and small results unchanged;
2. excludes `resource_read` and `resource_stat` to avoid recursive
   read/externalize/read behavior;
3. encodes strings verbatim as UTF-8 and other JSON deterministically;
4. retains deterministic UTF-8 head and tail bytes around an omission marker;
5. commits raw bytes through ResourceService;
6. returns a JSON preview and ResourceHandle.

The processor runs after handler completion but before a mutation `tool/commit`
and before the loop appends `tool/result`. Consequently neither mutation WAL nor
Session receives the externalized raw payload. `DefaultAgentLoop` remains free
of thresholds, storage paths, or resource-specific branches.

Externalization is fail-open by default for storage availability: a failed
spill leaves the original successful Tool Result intact rather than pretending
a mutation failed. Deployments can set `fail_open=False`. ResourceService's
explicit create/read APIs always reject invalid limits and storage failures.

## Relation to Context VM

V0.4 pruning and V0.5 externalization operate at different layers:

```text
V0.4: Session keeps full Tool Result → Context Page may retain head/tail
V0.5: ResourceStore keeps full bytes → Session already contains preview+handle
                                      → Context may further prune that projection
```

Context VM does not know the ResourceStore, does not load resource bytes during
ordinary projection, and cannot mutate them. Both mechanisms use the shared
deterministic head/marker/tail projection helper. The resource checksum and raw
payload remain stable if a Context Page is pruned, evicted, compacted, or rebuilt.

## Crash matrix

| Boundary | Behavior |
|---|---|
| A. Failure before LocalResourceStore publication | No final resource and no handle is returned. |
| B. Resource publication before Tool Result event | The object remains durable. Owner/source metadata plus `orphaned_resources(session)` identify it; V0.5 does not delete it. |
| C. Handle in durable Tool Result, then restart | A new LocalResourceStore/ResourceService over the same root can stat/read it. |
| D. Context preview/pruning | The raw payload and SHA-256 do not change. |

V0.5 deliberately chooses retention over unsafe automatic deletion. Complex GC,
leases, reference counting, and cross-session/fork ownership are deferred.

## Limits and errors

`ResourceLimits` defaults to 128 MiB per resource and 64 KiB per read. Both are
deployment-replaceable positive integers. Offset may equal size (an empty EOF
read) but cannot exceed it. A requested limit must be positive and cannot exceed
the hard maximum.

At the model Tool boundary:

- malformed URI/range → `EINVAL`;
- unknown handle → `ENOENT`;
- owner mismatch → `EACCES`;
- driver failure → `EIO`.

Ranges are byte ranges. V0.5 text reads decode UTF-8 with replacement if a range
splits a code point. Binary/media-native projection and parsers are future work.

## Metrics

`ResourceMetrics` exposes reconstructable, process-local counters:

- `resources_created`
- `resource_bytes_stored`
- `resource_reads`
- `resource_bytes_read`
- `tool_results_externalized`
- `preview_bytes`
- `model_visible_bytes_saved`

They are operational evidence, not Session truth, and are not persisted.

## Composition example

```python
resources = ResourceService(LocalResourceStore("state/resources"))
externalizer = ToolResultExternalizer(
    resources,
    ThresholdExternalizationPolicy(threshold_bytes=64 * 1024),
)

for definition in resource_tool_definitions(resources):
    tools.register(definition)

executor = DurableToolExecutor(tools, result_processor=externalizer)
```

The owning Agent needs `resource.read` to see and invoke the read tools. Store
and Session roots should both be deployment-controlled durable locations.

## Benchmark

`python -m benchmarks.resource_handle_benchmark --sizes-mb 10,100` compares:

- **Full:** full output in Session and model projection;
- **V0.4 Pruning:** full output in Session, bounded Context Page;
- **V0.5 Handle:** full output in ResourceStore, preview+handle in Session.

It reports model-visible bytes, estimated tokens, Session artifact bytes,
Resource artifact bytes, raw retention, restart read correctness, and bounded
read latency. The pytest companion uses a small deterministic payload; it does
not allocate 100 MiB in the default suite.

## Explicitly deferred

- full VFS semantics;
- delete/rename/list/search/glob model tools;
- remote/object/database drivers;
- automatic GC and retention policy;
- PDF/image/document parsing;
- RAG, embeddings, vector storage, and long-term memory;
- multi-agent sharing, delegation, IPC, distributed locks, and transactions.
