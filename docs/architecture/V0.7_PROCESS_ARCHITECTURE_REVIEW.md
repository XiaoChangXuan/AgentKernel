# V0.7 Process Runtime Architecture Freeze Review

Status: architecture freeze review only.

Scope:

- Review the current `Agent`, `Session`, `DefaultAgentLoop`, and
  `AgentControlBlock` relationship after V0.6 Capability validation.
- Design the Process Model required for V0.7.
- Freeze the minimum Kernel boundary before any scheduler implementation.
- Do not implement a scheduler.
- Do not modify `agentkernel/`.

Final decision: `READY_FOR_IMPLEMENTATION`

## 1. Executive Summary

AgentKernel is ready to introduce a V0.7 Process abstraction, provided the first
implementation stays narrow and cooperative.

The current runtime already has the main ingredients of a schedulable execution
unit:

- `AgentControlBlock` owns stable identity, lifecycle state, parent identity,
  capability bounds, structured grants, and hard turn budgets.
- `DefaultAgentLoop` drives state transitions and places awaitable work behind
  explicit `WAITING` transitions.
- `Session` owns the durable append-only event log and recovery projection.
- V0.6 places capability checks at Tool, Resource, Durable Tool, and Recovery
  boundaries.

The missing concept is not another Agent. The missing concept is a Kernel-owned
Process that represents a live schedulable execution instance for an Agent.

Recommended model:

```text
Agent identity        semantic principal and capability subject
Process identity      schedulable runtime instance
Session               durable local journal and model-visible fact source
Context VM            process-owned working-set view over session facts
Scheduler             Kernel mechanism that runs ready processes at safe points
```

This keeps the OS-inspired boundary intact:

```text
LLM = untrusted proposer
Agent/Process = Kernel-owned execution identity
Kernel Services = authority and durable state machines
Drivers = replaceable external execution adapters
```

V0.7 should not attempt preemptive execution, subprocess isolation, IPC, process
groups, or Linux-compatible semantics. The correct first step is a cooperative
Process runtime: one process table, explicit lifecycle states, wait/block
reasons, resource budgets, cancellation flags, and scheduler-owned dispatch at
known safe points.

Freeze findings:

| Question | Decision | Reason |
|---|---|---|
| Should Agent and Process be split? | Yes. | `Agent` is the semantic/security principal; `Process` is the live schedulable execution instance. Keeping them separate prevents scheduler state from polluting capability identity. |
| Should V0.7 add a `ProcessControlBlock`? | Yes, minimal. | A PCB is the right home for lifecycle, priority, budget, wait/block reason, pause/cancel flags, and future process audit context. |
| Should V0.7 reuse the existing `AgentState` as-is? | No. | Current states are a useful bridge, but V0.7 needs `CREATED` and `BLOCKED`, and `FAILED` should become `EXITED` metadata rather than a scheduler state. |
| Is Scheduler Kernel mechanism or Policy? | Both, separated. | The Kernel owns process table, run/wait queues, transition validation, budget enforcement, and safe-point dispatch; host policy owns priority meanings, fairness strategy, model choice, retry policy, and human approval rules. |
| Does V0.7 require changes to V0.1-V0.6 boundaries before implementation? | No major rewrite. | Existing Tool, Recovery, Durable Tool, Context VM, Resource, and Capability boundaries can be wrapped by a cooperative Process runtime. |

## 2. Current Architecture Review

### 2.1 Agent

`agentkernel/agent.py` currently defines:

- `AgentState`: `NEW`, `READY`, `RUNNING`, `WAITING`, `PAUSED`, `FAILED`,
  `EXITED`.
- `AgentBudget`: per-turn limits for steps and tool calls.
- `AgentControlBlock`: agent identity, session identity, lifecycle state,
  parent identity, legacy capability strings, capability bounding set,
  structured capability grants, and budget.
- `Agent`: a live handle combining `AgentControlBlock` and `Session`.

The ACB is already acting like a small process control block, but it also
contains Agent-principal fields. V0.7 should avoid adding more scheduler state
directly to this object until the Agent/Process split is explicit.

### 2.2 Session

`agentkernel/session.py` owns one authoritative append-only event log. It:

- assigns contiguous event sequence numbers;
- validates JSON-compatible event payloads;
- delegates durable persistence to `SessionPersistence`;
- derives provider-neutral model history from events;
- exposes recovery facts through `analyze_recovery()`.

Session is not a process. It is the durable journal used by one process to
recover and by the Context VM to project model-visible state. A future Scheduler
should not put all transient scheduling state into the Session log.

### 2.3 Loop

`agentkernel/loop.py` has a thin single-agent turn loop:

- requires the agent to be `READY`;
- transitions to `RUNNING`;
- appends `turn/start`, `user/message`, `step/start`, model output, tool calls,
  tool results, `step/end`, and `turn/end`;
- transitions through `WAITING` while awaiting context preparation, LLM calls,
  and tool execution;
- transitions back to `READY` after a completed turn;
- transitions to `FAILED` on loop failure or budget exhaustion.

This loop is compatible with a cooperative scheduler because it already has
await points and bounded per-turn execution. The important implementation change
is to let the Scheduler own admission and re-entry rather than letting callers
invoke `DefaultAgentLoop.run()` directly for every runnable unit.

### 2.4 Capability and Durable Boundaries

V0.6 added:

- `CapabilityGrant`, `AuthorizationRequest`, `AuthorizationDecision`, and
  `CapabilityEvaluator`;
- Tool visibility and execution authorization in `ToolRegistry`;
- Resource read/stat authorization in `ResourceService`;
- prepare/dispatch authorization metadata in `DurableToolExecutor`;
- replay validation for authorization metadata in `recovery.py`.

Process identity should build on this. It should not move authorization into
the Scheduler. The Scheduler decides which process may run next; Kernel services
still decide whether a proposed Tool, Resource, or Durable side effect is
authorized.

## 3. Process Abstraction

### 3.1 Definitions

| Concept | Meaning | Owner |
|---|---|---|
| Agent | Semantic actor and security principal. Owns user-facing identity and capability grants. | Kernel |
| Process | Schedulable execution instance of an Agent within a Session. Owns lifecycle, wait/block state, cancellation, and scheduling metadata. | Kernel |
| Session | Durable event log and model-visible fact source. | Kernel |
| Loop | Execution driver that advances a Process by one turn or one scheduler slice. | Kernel mechanism, replaceable implementation |
| Driver | External implementation for LLM, storage, tools, resources, or sandbox execution. | Host/driver |

V0.7 should initially support one live Process per Agent/Session pair. The model
should still be designed so V0.8 can allow child agents and multi-agent IPC
without reworking identity.

### 3.2 ProcessControlBlock

V0.7 should introduce a Process-owned structure rather than continue expanding
`AgentControlBlock`.

Candidate fields:

| Field | Purpose |
|---|---|
| `process_id` | Stable Kernel identity for a schedulable runtime instance. |
| `agent_id` | Security principal and compatibility bridge to V0.6 authorization. |
| `session_id` | Durable journal backing the process. |
| `parent_process_id` | Future process tree and cancellation propagation. |
| `parent_agent_id` | Existing delegation seed; should remain separate from runtime scheduling. |
| `state` | Process lifecycle state. |
| `priority` | Scheduler input, not authorization. |
| `budget` | Kernel-enforced resource ceilings. |
| `time_slice` | Cooperative execution quantum or maximum step budget. |
| `wait_reason` | Awaited operation category such as LLM, tool, resource, compaction, or timer. |
| `blocked_reason` | Kernel condition preventing progress, such as budget, capability, lock, or backpressure. |
| `cancel_requested` | Sticky cancellation signal checked at safe points. |
| `pause_requested` | Sticky pause signal checked at safe points. |
| `capability_snapshot` | Effective capability view used for this process execution epoch. |
| `context_owner` | Process-scoped view over the Session-backed Context VM. |
| `exit_status` | Success, failure, cancelled, or policy-stopped terminal metadata. |

The current `AgentControlBlock` can remain the compatibility identity object
while V0.7 adds a small PCB. Later versions can either keep both objects or
rename ACB once the split is stable.

### 3.3 Why Not Reuse Session as Process

Session must remain a durable journal. It should not become the scheduler's
mutable state object because:

- scheduling state changes too often for durable replay;
- a waiting process can be reconstructed from Session recovery facts after a
  crash;
- pause, priority, and cancellation are live control decisions unless they need
  audit or durability;
- V0.8 multi-agent work may need per-process local journals plus a global audit
  stream, and overloading a single Session log would make that harder.

Recommended rule:

```text
Durable facts that must survive recovery belong in Session.
Live scheduling state belongs in ProcessControlBlock.
Cross-process audit belongs in a future audit stream, not in V0.7 by default.
```

## 4. Lifecycle Model

V0.7 should use the lifecycle requested for the Process abstraction:

```text
CREATED -> READY -> RUNNING -> READY
                      |
                      +-> WAITING -> READY
                      +-> BLOCKED -> READY
                      +-> PAUSED  -> READY
                      +-> EXITED
```

### 4.1 State Semantics

| State | Meaning | Current mapping |
|---|---|---|
| `CREATED` | Process object exists but has not been admitted to a run queue. | Current `AgentState.NEW`. |
| `READY` | Runnable and eligible for scheduler selection. | Current `AgentState.READY`. |
| `RUNNING` | Currently being advanced by the loop. | Current `AgentState.RUNNING`. |
| `WAITING` | Suspended on an expected async completion, such as LLM, tool, resource, compaction, or timer. | Current `AgentState.WAITING`, currently temporary around awaits. |
| `BLOCKED` | Cannot run until a Kernel condition changes, such as resource budget, lock, backpressure, capability/policy hold, or unresolved durable recovery. | New state. |
| `PAUSED` | Explicitly paused by user, host, or scheduler policy. | Current `AgentState.PAUSED`. |
| `EXITED` | Terminal. Exit metadata records success, failure, cancellation, or policy stop. | Current `EXITED`; current `FAILED` should become exit metadata or a compatibility alias. |

### 4.2 Transition Rules

| From | Allowed next states | Reason |
|---|---|---|
| `CREATED` | `READY`, `EXITED` | Admission succeeds or process is discarded before running. |
| `READY` | `RUNNING`, `PAUSED`, `EXITED` | Scheduler dispatches it, host pauses it, or it is cancelled before dispatch. |
| `RUNNING` | `READY`, `WAITING`, `BLOCKED`, `PAUSED`, `EXITED` | A slice completes, async work starts, a Kernel condition stops progress, pause is requested, or the process terminates. |
| `WAITING` | `READY`, `PAUSED`, `EXITED` | Awaited work completes, pause wins before wake, or cancellation/error terminates. |
| `BLOCKED` | `READY`, `PAUSED`, `EXITED` | Blocking condition clears, pause wins, or process terminates. |
| `PAUSED` | `READY`, `EXITED` | Resume or terminal cancellation. |
| `EXITED` | none | Terminal state. |

`FAILED` should not be a Scheduler state in the new model. Failure is better
represented as:

```text
state: EXITED
exit_status: failed
exit_reason: <error class or kernel reason>
```

This avoids a second terminal state with unclear scheduling behavior.

### 4.3 WAITING vs BLOCKED

The distinction is important:

- `WAITING` means the process has already issued a valid async operation and
  expects a wakeup when it completes.
- `BLOCKED` means the process cannot make progress until the Kernel or host
  changes a condition.

Examples:

| Situation | State |
|---|---|
| LLM request in flight | `WAITING` |
| Tool handler in flight | `WAITING` |
| Resource read in flight | `WAITING` |
| Durable operation dispatched and recovery requires reconcile | `BLOCKED` after restart until reconcile policy acts |
| Context mandatory pages exceed budget | `BLOCKED` or `EXITED`, depending on host policy |
| User pauses process | `PAUSED` |
| Authorization denied for one tool call | Usually not `BLOCKED`; return `EACCES` as a tool result unless host policy blocks the process |
| Scheduler queue has not selected the process yet | `READY` |

## 5. Scheduler Kernel Primitives

V0.7 should implement Scheduler mechanism, not scheduling policy.

### 5.1 Required Kernel Primitives

| Primitive | Kernel role | Policy input |
|---|---|---|
| Process table | Own live process records and validate lifecycle transitions. | None. |
| Run queue | Track `READY` processes. | Priority and fairness policy choose order. |
| Wait queue | Track `WAITING` processes by wake source. | Timeout policy may wake or cancel. |
| Block registry | Track `BLOCKED` processes by blocking reason. | Host decides when policy/resource condition clears. |
| Priority | Kernel-stored scheduling hint. | Host chooses priority values. |
| Resource budget | Kernel-enforced ceilings for step count, tool count, context tokens, resource bytes, durable operations, and wall-clock time. | Host sets limits. |
| Time slice | Cooperative limit for how much work a process may advance before yielding. | Host chooses quantum. |
| Cancellation token | Sticky signal checked at safe points and propagated through drivers that support it. | User or host chooses when to cancel. |
| Pause/resume flag | Stop admission or re-entry without deleting durable state. | User or host chooses pause/resume. |
| Wait/block reason | Machine-readable reason used for diagnostics and future IPC. | Kernel sets reason; host may interpret. |

### 5.2 Cooperative First

AgentKernel should not attempt preemptive scheduling in V0.7. Python tool
handlers, LLM requests, resource stores, and user drivers do not provide a safe
preemption boundary.

The first Scheduler should yield only at safe points:

- before starting a turn;
- before starting a step;
- before an LLM request;
- before a tool call;
- before durable `prepare`;
- before durable `dispatch`;
- after a tool result;
- after context reclaim or compaction;
- before closing a turn.

Cancellation should be honored at these points. For in-flight external side
effects, cancellation cannot erase durable facts. If dispatch has happened,
recovery must reconcile rather than pretend the operation did not occur.

### 5.3 What Scheduler Must Not Own

The Scheduler must not own:

- prompt construction policy;
- model choice;
- tool implementation behavior;
- capability policy decisions;
- resource storage drivers;
- context reclaim heuristics;
- durable operation reconciliation policy.

The Scheduler owns execution order and safe lifecycle transitions. Other Kernel
services still enforce their own invariants.

## 6. Context VM Ownership

The current Context VM is Session-backed:

```text
Session Events -> Context Projection -> Context Pages -> Working Set
```

That remains correct. V0.7 should not turn `ContextPage` into a generic Kernel
object yet.

Recommended ownership:

| Object | Owner |
|---|---|
| `ContextPage` | Context VM projection from durable Session facts. |
| `ContextWorkingSet` | Process-local physical context for one model request. |
| Context budget | Process budget enforced by Kernel. |
| Reclaim strategy | Policy plugged into Context VM. |
| Summary/compaction facts | Session events, because they affect replay. |

Important implementation risk:

`ContextManager` currently stores manual pin/request state on the manager
instance. A multi-process scheduler must ensure this state is scoped by process
or session, or must instantiate a Context Manager per process. Otherwise one
process could affect another process's working set. This is a V0.7 implementation
requirement, not a reason to redesign the current Context VM.

## 7. Capability and Process Identity

V0.6 authorization is Agent-subject based:

```text
AuthorizationRequest(agent_id, action, resource)
```

V0.7 should not break this. The Agent remains the security principal. The
Process is the runtime execution identity.

Recommended model:

```text
agent_id      who is authorized
process_id    which live execution instance requested the action
session_id    which durable journal records the action
operation_id  which durable side effect instance was prepared/dispatched
```

Phase 1 compatibility can keep existing V0.6 authorization requests unchanged.
The Scheduler can carry `process_id` in the ProcessControlBlock and pass the
current ACB into Tool, Resource, and Durable Tool services.

Future-compatible extension:

- add `process_id` to audit metadata and `ToolExecutionContext`;
- keep `agent_id` as the capability subject;
- treat a process's effective grants as a snapshot or bounded view of its
  Agent's grants;
- require child processes to receive no more authority than the parent process
  or parent agent can delegate.

This avoids making Scheduler priority or process ownership a security bypass.

## 8. Resource Ownership

Current resources are owned by:

```text
ResourceOwner(agent_id, session_id)
```

That is enough for V0.7. Process identity should be added only for accounting
or audit if needed. Resource authority should remain with `ResourceService`:

```text
Resource read/stat
  -> owner check
  -> capability check
  -> range check
  -> store read
```

The Scheduler may charge the process for bytes read or handles created, but it
must not authorize storage access directly. `ResourceStore` should remain a
driver with no permission logic.

## 9. Recovery Compatibility

V0.7 must preserve the existing recovery rule:

```text
durable facts are replayed, not guessed
```

A process can be reconstructed after crash from:

- the Session header;
- the ACB or compatible Agent identity metadata;
- `RecoveryAnalysis` active turn/step facts;
- pending tool calls;
- durable operation classifications;
- context compaction state;
- authorization metadata attached to durable prepare/dispatch events.

Recovery should create a new live Process instance that resumes from the durable
facts. It should not mutate old events to repair scheduling state.

Recommended recovery behavior:

| Recovered state | Process state |
|---|---|
| completed session | `EXITED` or no live process |
| open turn with no ambiguous side effect | `READY` |
| pending LLM/tool call before dispatch | `READY` or `BLOCKED`, depending on retry policy |
| durable prepare without dispatch | `READY` for retry if classification permits |
| durable dispatch without commit/abort | `BLOCKED` until reconcile policy acts |
| active compaction | `BLOCKED` or policy-controlled retry |
| corrupted session | `EXITED` with failed/corrupted exit status |

This keeps V0.3 WAL compatible. If a process is cancelled or paused while an
external side effect is in flight, the WAL still owns the recovery semantics.

## 10. Reference Comparison

The references below are useful as design constraints, not templates to copy.

### 10.1 Linux Process Model

Useful ideas:

- process/task identity and lifecycle are Kernel-owned;
- the Scheduler chooses runnable work from queues;
- blocked/waiting states are not the same as runnable states;
- resource accounting and scheduling policy are separate concepts;
- fairness and priority need measurable runtime state.

Do not copy:

- `fork`/`exec` semantics;
- POSIX signals;
- address spaces;
- file descriptors as the universal object model;
- preemptive CPU scheduling for arbitrary Python awaitables and tool handlers.

AgentKernel equivalent:

```text
Process = cooperative schedulable agent execution
Session = journal, not address space
Context VM = model-visible working set, not virtual memory
Resource Handle = kernel-resolved object reference, not POSIX fd
```

### 10.2 seL4 Thread Model

Useful ideas:

- distinguish thread identity from capability spaces and scheduling context;
- make scheduling budget/time an explicit object rather than hidden global
  state;
- keep policy out of the small trusted mechanism when possible;
- enforce authority through capabilities, not through caller intent.

Do not copy:

- hard realtime scheduling requirements;
- low-level IPC and reply-capability details in V0.7;
- kernel object granularity that would overfit a Python agent runtime.

AgentKernel equivalent:

```text
AgentControlBlock = authority/principal seed
ProcessControlBlock = schedulable runtime state
CapabilityGrant = authority
ProcessBudget / SchedulingContext = runtime resource allowance
```

### 10.3 Kubernetes Workload Model

Useful ideas:

- separate desired specification from observed status;
- scheduler admission can use requests, limits, priority, and constraints;
- a workload can be replaced or restarted while preserving higher-level intent;
- resource pressure should be observable.

Do not copy:

- cluster node placement as the primary abstraction;
- Pod as the durable conversation unit;
- controller reconciliation loops for every Kernel state transition.

AgentKernel equivalent:

```text
ProcessSpec = requested runtime settings
ProcessStatus = current lifecycle and wait/block reason
Session = durable workload history
Scheduler = local admission and dispatch mechanism
```

### 10.4 OpenHands Agent Runtime

OpenHands is organized around conversations, workspaces, events, and sandboxed
execution environments. Its Agent Server exposes conversations and workspaces
over HTTP/WebSocket APIs, while workspace implementations abstract local,
remote, and sandboxed command/file execution.

Useful ideas:

- keep UI/client orchestration separate from execution;
- make workspace execution replaceable;
- represent conversation state and events as a first-class runtime surface;
- provide pause/terminate lifecycle controls at the conversation level.

AgentKernel difference:

- AgentKernel is designing an in-process Kernel abstraction before exposing a
  server product surface.
- Process scheduling is a Kernel primitive, not mainly an Agent Server routing
  concern.
- Resource, WAL, Context VM, and Capability boundaries are local Kernel
  services first.

### 10.5 Codex Multi-Agent Architecture

Codex product surfaces emphasize multiple isolated tasks, worktrees/cloud
environments, sandbox boundaries, and approval flows. Codex CLI also treats
sandboxing and approvals as separate controls: the sandbox defines what can be
done technically, while approval policy decides when human or automated review
is required.

Useful ideas:

- run concurrent tasks in isolated workspaces;
- keep sandbox constraints separate from approval policy;
- allow the user to supervise multiple long-running agents;
- make higher-risk actions pass through explicit review.

AgentKernel difference:

- AgentKernel is not a product command center.
- V0.7 should model local Process scheduling, not cloud task orchestration.
- Approval remains Host policy; Kernel enforces capability, lifecycle, WAL, and
  resource boundaries.

### 10.6 DeepSeek Harness Runtime

DeepSeek Harness separates durable `session/event` facts from live `agent/*`
control and status events. Its architecture also treats models, tools, sessions,
sandboxes, storage, loops, scheduling, and UI as pluggable composition points.

Useful ideas:

- do not store every live control fact as a durable transcript fact;
- keep model-visible inputs reconstructable from logged session facts;
- let live agent control APIs handle status, inbox, request, and continuation;
- make execution backends swappable without changing every tool.

AgentKernel difference:

- AgentKernel intentionally keeps a trusted Kernel boundary for lifecycle,
  authorization, event ordering, recovery, WAL, Context VM, and Resource
  handles.
- The Process model should strengthen that boundary rather than turn every
  mechanism into a plugin.

## 11. Kernel Boundary Matrix

| Component | Kernel/Policy/Driver | Reason |
|---|---|---|
| Process identity | Kernel | Required for scheduling, audit, recovery, and future IPC. |
| Agent identity | Kernel | Required for capability subject and ownership. |
| Lifecycle transition validation | Kernel | Prevents impossible runtime states. |
| Run queue and wait queue | Kernel | Determines which live process may be advanced. |
| Scheduling algorithm | Policy over Kernel mechanism | Hosts may choose FIFO, priority, fair-share, or deadline-like policies. |
| Priority value | Kernel field, policy meaning | Kernel stores and validates it; host decides values. |
| Resource budget enforcement | Kernel | Prevents unbounded steps, tools, tokens, bytes, and runtime. |
| Budget selection | Policy | Host chooses limits per workload. |
| Time slice accounting | Kernel | Needed for fair cooperative scheduling. |
| Cancellation and pause flags | Kernel mechanism | Safe lifecycle control must not depend on model cooperation. |
| Cancellation policy | Policy | Host/user decides when to cancel. |
| Capability evaluation | Kernel | LLM and tools must not self-authorize. |
| Authorization policy inputs | Host policy | Business rules such as approval requirements stay outside mechanism. |
| Session event ordering | Kernel | Recovery and context projection depend on it. |
| Session persistence backend | Driver | Storage can vary if it preserves append/load/flush semantics. |
| Durable Tool WAL | Kernel | External side effects need crash-safe facts. |
| Reconcile handler | Driver with Kernel contract | External observation is service-specific. |
| Context budget enforcement | Kernel | Process must not exceed model-visible context limits. |
| Context reclaim strategy | Policy | Reclaim quality and summarization are product choices. |
| Resource owner and scope checks | Kernel | Prevents handle overreach. |
| Resource byte store | Driver | Storage path and medium are replaceable. |
| Prompt and model choice | Policy | Should not affect Process correctness. |

## 12. Compatibility With V0.1-V0.6

| Version | Compatibility | Notes |
|---|---|---|
| V0.1 Execution Kernel | Small extension | Tool execution already has a controlled boundary. Process scheduling wraps it. |
| V0.2 Persistence / Recovery | Small extension | Session remains the durable source. Recovery can create a live Process from replay facts. |
| V0.3 Durable Tool | Small extension | WAL semantics remain authoritative for in-flight side effects. |
| V0.4 Context VM | Medium implementation care | Working-set preparation is compatible, but mutable pin/request state must become process/session scoped. |
| V0.5 Resource Layer | Small extension | ResourceService stays owner/capability/range authority. Scheduler may add accounting only. |
| V0.6 Capability | Small extension | Agent remains capability subject. Process adds execution identity and audit context. |

No major rewrite is required before V0.7. The main design requirement is to
avoid overloading `AgentControlBlock` and `Session` with every process concern.

## 13. Implementation Roadmap

### V0.7 Phase 1: Process Core

- Add `ProcessState` with `CREATED`, `READY`, `RUNNING`, `WAITING`, `BLOCKED`,
  `PAUSED`, and `EXITED`.
- Add a minimal `ProcessControlBlock`.
- Add process transition validation.
- Keep one live process per Agent/Session.
- Keep current Agent and Session APIs compatible.

### V0.7 Phase 2: Cooperative Scheduler

- Add a process table.
- Add a ready queue.
- Add wait/block registries.
- Add cooperative run slices around existing loop safe points.
- Add cancellation and pause/resume checks at safe points.

### V0.7 Phase 3: Budget and Observability

- Extend budgets beyond per-turn steps/tools to include context, resource,
  durable operation, and wall-clock accounting.
- Add scheduler metrics.
- Add process status inspection.
- Decide which process lifecycle facts need durable audit events.

### Deferred To V0.8+

- Multi-agent IPC.
- Subagent delegation semantics.
- Process groups.
- Cross-session global audit stream.
- Revocation-aware recovery policy.
- Namespace isolation beyond V0.6 resource/tool scopes.

## 14. Risks

| Risk | Impact | Required mitigation |
|---|---|---|
| ACB grows into a mixed Agent/Process object | Future child agents and scheduler changes become hard to reason about. | Introduce PCB and keep Agent identity separate. |
| Session log becomes a live scheduler log | Replay becomes noisy and multi-process ordering becomes brittle. | Keep live scheduling state in process table; log only durable facts and explicit audit events. |
| `FAILED` remains a schedulable state | Scheduler terminal behavior becomes ambiguous. | Use `EXITED` plus exit metadata in the Process model. |
| ContextManager mutable pin/request state leaks across processes | One process can influence another process's working set. | Scope pin/request state by process/session or instantiate per process. |
| Cancellation crosses durable dispatch unsafely | External side effects can be duplicated or hidden. | Check cancellation before dispatch; after dispatch require WAL recovery/reconcile. |
| Scheduler starts owning authorization policy | Capability boundary becomes inconsistent. | Scheduler only decides run order; Tool/Resource/Durable services authorize actions. |
| Time-slice expectations become preemptive | Tool handlers may be interrupted unsafely. | V0.7 is cooperative only. |
| Process identity is omitted from audit | Future IPC/debugging cannot attribute actions precisely. | Add process_id to audit context when changing runtime contexts. |

## 15. Final Decision

`READY_FOR_IMPLEMENTATION`

AgentKernel can proceed to V0.7 Process Runtime implementation after V0.6
completion. The implementation should begin with a minimal cooperative Process
Core and must preserve existing V0.1-V0.6 boundaries:

- Session remains the durable journal.
- Agent remains the capability principal.
- Process becomes the schedulable runtime instance.
- Scheduler controls lifecycle and run order.
- Tool, Resource, Durable Tool, Context VM, and Recovery keep their own Kernel
  invariants.

The only required design correction before coding is to keep Process separate
from both Agent identity and Session durability. With that boundary frozen,
V0.7 does not require redesign of V0.1-V0.6.
