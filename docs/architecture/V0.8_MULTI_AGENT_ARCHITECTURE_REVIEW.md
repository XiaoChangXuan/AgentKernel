# V0.8 Multi-Agent Runtime Architecture Review

Status: architecture review and design freeze input for V0.8.

Scope:

- Review how AgentKernel can move from the V0.7 single-agent runtime to a
  multi-agent runtime.
- Preserve V0.1-V0.7 Kernel invariants.
- Do not implement Process Tree, IPC, delegation, namespace, memory, or
  multi-agent scheduling.
- Do not modify `agentkernel/`, `benchmarks/`, `tests/`, examples, or runtime
  semantics.

Final review decision:

```text
READY_FOR_V0.8_IMPLEMENTATION
```

This decision means the architecture is frozen enough to begin a later V0.8
implementation branch. It does not mean V0.8 is implemented.

## 1. Executive Summary

AgentKernel can extend to multi-agent runtime without breaking the current
Kernel boundary if V0.8 keeps three separations intact:

```text
Agent   = capability principal and semantic actor
Process = schedulable runtime identity
Session = durable single-writer journal and replay truth
```

The core V0.8 design is therefore not "more agents chatting in one transcript."
It is a controlled runtime model where multiple agents can be created,
scheduled, isolated, and allowed to communicate only through Kernel-owned
mechanisms.

The frozen direction is:

- keep Agent Tree and Process Tree separate;
- prefer one Session per Agent;
- keep each Session single-writer;
- use Kernel IPC for cross-agent collaboration;
- record cross-session correlation identities instead of creating a global
  transcript;
- make delegation explicit, positive, narrowed, and provenance-carrying;
- treat ResourceHandle references as data, not authority;
- keep Scheduler as process mechanism, not business policy;
- keep durable facts durable even after cancellation or child failure.

The current V0.7 implementation already supports the important foundation:
`AgentControlBlock` owns capability identity, `ProcessControlBlock` owns live
runtime state, `Session` owns replay truth, `CapabilityEvaluator` authorizes
Agent-subject actions, `ResourceService` authorizes handles above the store, and
`DurableToolExecutor` binds authorization to WAL prepare/dispatch.

No architecture blocker was found that requires rewriting V0.1-V0.7 before
starting V0.8.

## 2. V0.7 Invariants That Must Survive

V0.8 must not weaken these implemented invariants:

1. LLM output is never Kernel authority.
2. All external side effects cross trusted Tool or Durable Tool boundaries.
3. Session Event Log remains the durable source of truth for one Session.
4. Model-visible Context remains a projection, not truth.
5. Mechanism and Policy remain separate.
6. Resource identity, handle, metadata, and preview are distinct concepts.
7. Agent identity is not Process identity.
8. Agent remains the capability principal.
9. Scheduler owns runtime mechanism, not business policy.
10. Durable external mutation remains WAL and reconciliation controlled.
11. Runtime accounting remains observation, not durable billing truth.
12. ResourceStore remains a storage driver, not authorization authority.
13. IPC messages must not implicitly carry authority.
14. Child runtime authority must never exceed explicitly delegated authority.
15. Durable facts cannot disappear because a process or agent was cancelled.

These are supported by the current code:

- `CapabilityGrant.subject` and `AuthorizationRequest.agent_id` are Agent-based.
- `ProcessControlBlock.capability_snapshot` is a point-in-time Agent-derived
  view and does not make `process_id` an authorization subject.
- `ResourceService` checks owner and capability before store reads.
- `DurableToolExecutor` checks authorization before prepare and again before
  dispatch.
- `ProcessManager` and `CooperativeScheduler` keep process table and queues as
  live runtime state.

## 3. Current Runtime Boundary

Current implemented boundary:

```text
LLM
  |
DefaultAgentLoop
  |
Kernel Services
  |-- Session / Recovery
  |-- ToolRegistry / DurableToolExecutor
  |-- CapabilityEvaluator
  |-- Context VM
  |-- ResourceService
  |-- ProcessManager / CooperativeScheduler
  |-- UsageCollector
  |
Drivers
  |-- LLM provider
  |-- Tool handler
  |-- ResourceStore
  |-- SessionPersistence
  |
External World
```

The current boundary remains valid for V0.8 if multi-agent features are added
as Kernel services around these concepts, not as prompt conventions.

Important current facts:

| Object | Current role | V0.8 implication |
| --- | --- | --- |
| `AgentControlBlock` | Agent identity, parent agent id placeholder, capability strings, structured grants, budget. | Add child-agent identity and registry semantics here or adjacent to it, not inside Scheduler. |
| `ProcessControlBlock` | Runtime identity, state, parent process placeholder, budget, pause/cancel, recovery-derived live state. | Extend with tree metadata and supervision only as runtime process facts. |
| `Session` | Append-only durable event log with closed vocabulary. | Keep one writer; do not let many agents write one transcript. |
| `CapabilityEvaluator` | Exact action and resource-scope grant evaluator. | Delegation should narrow and produce new positive grants for a child Agent. |
| `ResourceService` | Trusted owner/capability/range boundary above `ResourceStore`. | Resource sharing must be a new authorization relation, not handle copying. |
| `DurableToolExecutor` | WAL prepare/dispatch/commit/reconcile with authorization context. | Child cancellation/failure cannot erase dispatched facts. |
| `CooperativeScheduler` | READY queue, WAITING/BLOCKED registries, safe points, budget blocking. | It can schedule different `agent_id` processes without becoming an Agent scheduler. |

## 4. Agent Tree vs Process Tree

V0.8 should introduce two related but independent trees.

```text
Agent Tree

Host
  |
  +-- Agent A
      |
      +-- Agent B
      +-- Agent C

Process Tree

Process A1 (agent A)
  |
  +-- Process A2 (agent A)
  +-- Process B1 (agent B)
  +-- Process C1 (agent C)
```

The trees are independent because they answer different questions.

| Question | Agent Tree | Process Tree |
| --- | --- | --- |
| Who is the semantic actor? | Yes | No |
| Who is the capability principal? | Yes | No |
| Who owns a Session? | Usually yes | No |
| What is runnable now? | No | Yes |
| What can be paused/cancelled? | Indirectly | Yes |
| What failed at runtime? | Supervision target | Direct source |
| What authority can be delegated? | Yes | No, only receives Agent-derived snapshot |

Frozen decisions:

| Question | Decision |
| --- | --- |
| Does V0.8 have both Agent Tree and Process Tree? | Yes. |
| Does spawning a process create a new Agent principal? | No. |
| Does spawning a child Agent create a new principal? | Yes. |
| Does a child Agent need at least one Process? | Yes for execution, but identity creation and scheduling admission are separate steps. |
| Can one Agent have multiple Processes? | Yes, but V0.8 should start with a constrained form and keep Session single-writer. |
| Must Process parent equal Agent parent? | No. A parent process can request child-agent creation, but Process lineage and Agent lineage must remain separately recorded. |
| Can Process identity inherit authority? | No. Authority belongs to Agent grants; a process may carry only an Agent-derived snapshot for attribution. |

This avoids an architectural trap: a child process is not a child security
principal. If V0.8 needs a weaker security subject, it must create a child
Agent and delegate narrowed authority to it.

## 5. Session Ownership

Three Session ownership models were reviewed.

### Model A: Multiple Agents Co-Write One Session

```text
Agent A \
Agent B  -> Session X
Agent C /
```

Pros:

- simplest transcript for model-visible collaboration;
- no cross-session correlation needed for a small demo.

Cons:

- breaks the current single-writer assumption;
- creates ambiguous event ordering between agents;
- makes capability attribution difficult;
- mixes different model/provider/prompt contexts;
- lets one Agent's context pressure affect another;
- makes child failure and recovery contaminate parent history;
- encourages transcript sharing as an authority transport.

Decision: reject for V0.8.

### Model B: One Session Per Agent

```text
Agent A -> Session A
Agent B -> Session B
Agent C -> Session C
```

Pros:

- preserves current Session semantics;
- gives each Agent a durable local journal;
- keeps model-visible context isolated;
- makes audit attribution clear;
- allows child failure without parent transcript corruption;
- keeps cross-agent collaboration explicit through IPC.

Cons:

- requires cross-session correlation IDs;
- requires IPC delivery semantics;
- parent inspection of child work needs a controlled read/audit path;
- global debugging may eventually need an audit index.

Decision: freeze as the V0.8 default.

### Model C: One Session Per Process

```text
Process A1 -> Session A1
Process A2 -> Session A2
Process B1 -> Session B1
```

Pros:

- very strong runtime isolation;
- simple replay for each live process.

Cons:

- fragments one Agent's semantic history;
- makes one Agent with multiple Processes hard to project into context;
- creates more cross-session joins;
- blurs whether Session is owned by Agent or by scheduler lifecycle.

Decision: defer. Useful for future specialized workers, but not V0.8 default.

Frozen Session model:

```text
Agent owns one primary Session.
Session remains single-writer.
Cross-Agent collaboration uses Kernel IPC.
Cross-session joins use correlation IDs, not shared transcripts.
```

Parent read rules:

- Parent does not automatically read child Session.
- Parent may receive child output through IPC.
- A future audit or supervised read path may expose child events, but it must be
  authorized and must not become shared mutable transcript state.
- Child Session may record `parent_agent_id` and spawn correlation metadata.
- A future global audit index can correlate events, but it must not replace
  Session replay truth.

## 6. Process Tree Design

V0.7 already has `parent_process_id` in `ProcessControlBlock`, but it has no
implemented tree semantics. V0.8 should define those semantics carefully.

Candidate fields:

| Field | Purpose | Durable? |
| --- | --- | --- |
| `parent_process_id` | Immediate runtime parent. | Runtime by default; may be recoverable from spawn facts. |
| `root_process_id` | Efficient subtree control. | Runtime-derived. |
| `agent_id` | Owning Agent principal. | Existing PCB field; derived from Agent identity. |
| `session_id` | Agent Session backing execution. | Existing PCB field. |
| `spawn_depth` | Guard recursion and runaway spawning. | Runtime or policy-derived. |
| `child_process_ids` | Fast supervision and cancellation traversal. | Runtime index. |
| `supervision_policy_ref` | Host policy for child failure. | Policy reference, not Kernel mechanism. |

Frozen principle:

```text
Process Table remains live runtime state.
Durable replay reconstructs semantic facts first.
Process Tree is reconstructed from durable spawn/admission facts when needed.
```

The parent-child relation should be recorded as a durable fact only at the
semantic creation boundary:

- child Agent created;
- child Session created;
- initial child Process admitted;
- IPC channel created if needed;
- delegated grants recorded.

The live READY queue, WAITING registry, BLOCKED registry, current RUNNING
process, and transient child index should not be treated as durable truth.

## 7. Spawn Semantics

V0.8 should define conceptual `spawn_agent()` and `spawn_process()` semantics,
but not conflate them.

### `spawn_process()`

Purpose:

Run additional schedulable work for the same Agent principal.

Inputs:

- `parent_process_id`;
- `agent_id`;
- `session_id`;
- requested priority;
- requested budget override bounded by Agent/host policy;
- task-local runtime metadata.

Rules:

- does not create a new capability principal;
- does not widen authority;
- uses the same Agent-owned authorization subject;
- must not create concurrent writers to the same Session without an explicit
  single-writer turn/step admission rule.

V0.8 should be conservative: allow only one active writer process per Agent
Session until an explicit Session concurrency rule exists.

### `spawn_agent()`

Purpose:

Create a new semantic actor and capability principal.

Conceptual flow:

```text
Parent Process
  -> spawn request
  -> Kernel validates request shape
  -> Host policy chooses role/model/budget/grant limits
  -> Kernel creates child Agent principal
  -> Kernel validates delegated grants are narrowed
  -> Kernel creates child Session
  -> Kernel creates child Process
  -> Scheduler admission
```

Important rule:

```text
spawn request != authority grant
```

The parent or LLM can propose a child and proposed authority. The Kernel must
validate narrowing, and Host policy may approve or reject business-level choices
such as role, model, budget, or human approval requirement.

Kernel mechanism:

- identity creation;
- parent relation recording;
- grant narrowing validation;
- budget ceiling enforcement;
- Session creation;
- process creation and admission;
- audit/correlation identity generation.

Host policy:

- whether to spawn;
- which role or prompt to use;
- model/provider selection;
- budget allocation amount;
- tool selection intent;
- human approval;
- restart or fail-fast behavior.

## 8. IPC Architecture

V0.8 should add a minimal Kernel-owned structured IPC abstraction. It should not
copy UNIX pipes or create a general message bus first.

Reviewed options:

| Option | Strength | Weakness | Decision |
| --- | --- | --- | --- |
| Mailbox | Simple per-Agent inbox. | Backpressure and ordering become receiver-wide and coarse. | Good fallback, not the first frozen primitive. |
| Queue | Easy durable envelope. | Ambiguous ownership unless scoped. | Useful implementation detail. |
| Channel | Explicit participants, ordering, bounds, and lifecycle. | Slightly more setup. | Preferred V0.8 primitive. |
| Message bus | Flexible. | Too broad; harder to preserve least authority. | Defer. |

Frozen IPC model:

```text
Kernel-owned local structured channel
```

Message fields to design for:

| Field | Purpose |
| --- | --- |
| `message_id` | Stable message envelope identity. |
| `channel_id` | Bounded local channel identity. |
| `sender_agent_id` | Capability principal that sent the message. |
| `sender_process_id` | Runtime process that sent the message. |
| `receiver_agent_id` | Intended receiving principal. |
| `receiver_process_id` | Optional direct process target. |
| `payload` | JSON-compatible data. |
| `resource_refs` | Resource handle references included as data. |
| `created_at` | Local timestamp for audit and diagnostics. |
| `sequence` | Per-channel or per-sender sequence. |
| `correlation_id` | Cross-session correlation identity. |

IPC messages must not include an authority grant field that automatically
changes receiver permissions.

Core invariant:

```text
Data may cross IPC.
Authority does not cross IPC implicitly.
```

If a message asks the receiver to use a resource or tool, the receiver still
needs its own authority or an explicit delegated/share grant.

## 9. IPC Durability / Ordering / Backpressure

### Durability

Options reviewed:

| Option | Meaning | Problem |
| --- | --- | --- |
| Volatile IPC | Messages vanish on crash. | Too weak for recoverable multi-agent tasks. |
| Fully durable global IPC log | Every message is a global journal fact. | Too much complexity and risks replacing Session truth. |
| Hybrid durable envelope | Channel records durable send/delivery envelope while each Agent Session records local send/receive facts. | Best fit for current Session model. |

Frozen V0.8 first version:

```text
Local durable message envelope with explicit delivery state.
```

The guarantee should be:

```text
at-least-once observable delivery until acknowledged, with idempotent receiver
handling by message_id
```

Do not claim exactly-once. A receiver may see a message again after crash, so
handlers must use `message_id` and Session facts to avoid duplicate semantic
commit.

Crash cases:

| Crash point | Required recovery rule |
| --- | --- |
| After sender send before receiver delivery | Envelope remains pending; receiver can later observe it. |
| After receiver delivery before receive Session event | Envelope may redeliver; receiver must de-duplicate by `message_id`. |
| After receive Session event before ack | Replay sees receive fact; ack can be repaired or redelivery ignored. |
| After ack | Message is not delivered again by mechanism. |

### Session Relationship

IPC should be represented in local Session facts without making Session global.

Recommended future events:

```text
sender Session:   ipc/send(message_id, channel_id, receiver, correlation_id)
receiver Session: ipc/receive(message_id, channel_id, sender, correlation_id)
```

The durable envelope or audit index links them with `message_id` and
`correlation_id`.

No single global Session log is required for V0.8.

### Ordering

Freeze the minimal ordering guarantee:

```text
per-channel FIFO for one sender on one channel
```

Do not promise global total order. Multiple senders to one receiver may be
interleaved by channel policy, but each message must carry sender identity and
sequence so replay can reason about what happened.

If V0.8 needs multi-sender ordering, use channel-specific sequence assignment.
Do not make all Sessions share one global event order.

### Backpressure

IPC must not allow unbounded queue growth.

Kernel mechanism:

- measure message count;
- measure queued bytes;
- enforce hard bounds;
- block sender or receiver process when a bound is exceeded;
- expose WAITING/BLOCKED reason;
- preserve delivery state.

Host policy:

- choose `max_messages`;
- choose `max_bytes`;
- choose timeout behavior;
- choose whether to drop, reject, block, or cancel;
- choose retry/supervision behavior.

Recommended default:

```text
bounded channel + sender BLOCKED on full queue
```

Dropping messages should be a policy choice with explicit status, not the
Kernel default.

## 10. Capability Delegation

V0.8 delegation is the security core.

Required conceptual objects:

| Object | Purpose |
| --- | --- |
| `DelegationRequest` | Parent asks to delegate specific authority to child. |
| `DelegationDecision` | Kernel/Host result, reason, and narrowed grant set. |
| `DelegatedGrant` | Child grant with provenance and parent linkage. |
| `DelegationChain` | Auditable chain from parent grant to child grant. |

Frozen invariant:

```text
child effective authority <= delegated authority <= parent effective authority
```

Delegation must support:

- action narrowing;
- resource scope narrowing;
- constraint narrowing;
- bounding set validation;
- expiration or lease metadata;
- delegation depth limit;
- grant identity;
- parent grant reference;
- delegation provenance;
- audit event identity.

It must not be implemented as:

```text
copy parent grant strings into child
```

Delegation should use the current structured `CapabilityGrant` model. Legacy
capability strings may be bridged for compatibility, but new child authority
should be expressed as structured grants.

Example:

```text
Parent grant:
  subject: agent-a
  action: resource.read
  resource_scope: artifact://project-a/**
  constraints: {"max_bytes": 104857600}

Delegated child grant:
  subject: agent-b
  action: resource.read
  resource_scope: artifact://project-a/logs/**
  constraints: {"max_bytes": 1048576, "expires_at": "..."}
```

The child grant is valid only if the action is not broader, the scope is not
broader, and every constraint is equal or stricter under the defined constraint
semantics.

## 11. Delegation vs Inheritance

Inheritance and delegation must be distinct.

Inheritance:

- default structural metadata from parent;
- parent identity reference;
- optional prompt/model policy reference;
- default budget ceiling reference;
- supervision relation.

Delegation:

- explicit positive authority grant;
- narrowed action/scope/constraints;
- auditable provenance;
- optionally leased or revocable later.

Frozen default:

```text
Child Agent starts with zero authority except minimal Kernel-internal runtime
authority required to exist.
```

Any Tool, Resource, Durable mutation, IPC send/receive, or future memory access
must come from explicit grants or Kernel-created minimal lifecycle permissions.

This is a deny-by-default model. It avoids accidental authority expansion when a
parent creates a helper.

## 12. Revocation Compatibility

V0.8 does not implement revocation, but V0.8 delegation objects must not block a
future revocation model.

Reviewed future models:

| Model | Meaning | Fit |
| --- | --- | --- |
| Snapshot authority | Child keeps grant even if parent later loses it. | Simple but weak for sensitive authority. |
| Live chained authority | Child remains valid only while parent chain remains valid. | Safer but needs chain checks. |
| Revocation epoch/version | Grants carry epoch checked by evaluator. | Good future extension. |
| Explicit delegation lease | Grants expire or renew through policy. | Good first revocation-adjacent mechanism. |

Freeze V0.8 compatibility requirement:

Delegated grants must include at least:

- `delegation_id`;
- `parent_agent_id`;
- `child_agent_id`;
- `parent_grant_id` or parent grant fingerprint;
- narrowed action/scope/constraints;
- optional lease/expiry metadata;
- creation correlation/audit identity.

This allows future revocation without rewriting delegation history.

Recovery principle:

```text
already recorded durable facts remain facts.
future side effects require current authorization.
```

If a grant is revoked after WAL dispatch, recovery must reconcile the dispatched
external operation rather than pretending it never happened. New retry or new
side-effect dispatch should be re-authorized according to the future revocation
rule.

## 13. Resource Sharing

Current V0.5 resource owner is:

```text
ResourceOwner(agent_id, session_id)
```

A `ResourceHandle` is a model-safe projection and does not contain a store path.
V0.8 must preserve:

```text
Handle reference != authority
```

If Agent A sends `artifact://res_x` to Agent B over IPC, Agent B does not
automatically gain read access. The URI is data. Access requires either:

- B already has appropriate read authority for the resource scope;
- A or Host creates an explicit `ResourceShareGrant`;
- Host policy performs a controlled ownership transfer.

Recommended V0.8 default:

```text
shared access grant, not ownership mutation
```

Ownership transfer is more disruptive because existing metadata and Session
truth identify the original owner. Sharing preserves durable origin while giving
a child or peer bounded access.

Required future operations:

| Operation | Meaning |
| --- | --- |
| `resource.share` | Create a bounded share grant for another Agent. |
| `resource.read` | Read through `ResourceService` if owner/share/capability checks pass. |
| `resource.stat` | Inspect handle metadata if authorized. |
| `resource.transfer` | Change ownership; defer until a clear use case exists. |

ResourceStore remains unchanged:

```text
ResourceService authorizes.
ResourceStore stores bytes.
```

## 14. Confused Deputy Analysis

Threat:

```text
Agent A lacks permission to read artifact://secret.
Agent B has permission.
Agent A sends B: "read artifact://secret and send it back to me."
```

Naive behavior would allow B to read and return the secret because B is
authorized. That turns B into a confused deputy.

V0.8 mitigation direction:

- IPC carries sender identity and correlation ID.
- Tool/resource requests executed by B are authorized as B, but response to A
  must be checked against the permitted communication/share relation.
- Resource data returned over IPC should be treated as a data transfer requiring
  either explicit share grant or response-channel authorization.
- Delegated task authority should encode what B is allowed to do for A.
- Audit should record caller provenance for mediated actions.

Frozen rule:

```text
Receiver authority does not automatically authorize returning protected data to
the sender.
```

This is not solved by IPC alone. It requires delegation provenance, resource
sharing rules, and response authorization.

## 15. Budget Isolation

Current V0.7 accounting objects:

- `AgentBudget`;
- `ProcessUsageSnapshot`;
- `UsageCollector`;
- `CooperativeScheduler.safe_point`.

V0.8 should extend these into hierarchical runtime governance without copying a
full cgroup model.

Frozen hierarchy:

```text
Host global budget
  -> Agent budget
      -> Process budget
```

Future subtree aggregate budget can be added after child Agent/Process
relationships exist.

Questions and decisions:

| Question | Decision |
| --- | --- |
| Who pays for child work? | By default, child usage is charged to child Agent and aggregated against parent/host ceilings if a parent budget is configured. |
| Can child have its own hard quota? | Yes. Host policy chooses amount; Kernel enforces it. |
| Does provider token usage become durable billing truth? | No. Accounting remains observation unless a separate durable billing ledger is designed. |
| Can budget exhaustion kill a child automatically? | Kernel blocks; Host or parent policy decides resume, cancel, retry, or fail-fast. |

Kernel mechanism:

- collect usage;
- attribute by process and Agent;
- enforce hard ceilings at safe points;
- block or pause process;
- expose reason.

Host policy:

- allocate quotas;
- decide child budget;
- decide overage handling;
- choose model/provider costs.

## 16. Fault Isolation

Frozen rule:

```text
child crash != parent crash
```

Child failure should produce a supervised result, notification, or exit status.
It should not corrupt parent Session truth and should not automatically fail the
parent unless policy says so.

Kernel mechanism:

- record child exit status;
- wake or notify supervising parent process;
- preserve child Session replay facts;
- preserve IPC delivery state;
- preserve durable Tool recovery obligations.

Policy choices:

- ignore child failure;
- retry child;
- restart with narrowed or changed budget;
- fail parent;
- ask user/human;
- collect partial output.

The parent can choose fail-fast behavior, but the Kernel should not bake that
business policy into process lifecycle validation.

## 17. Cancellation Propagation

V0.8 should prefer structured child lifetime by default.

Default:

```text
parent cancellation -> cancellation request propagates to children
```

Detached child processes or detached child Agents should be out of scope for the
first implementation unless a strong use case appears. Detachment complicates
budget inheritance, failure reporting, resource cleanup, and revocation.

Important durable rule:

```text
Cancellation cannot delete durable truth or roll back an external fact.
```

If cancellation happens before durable dispatch, the process can stop before
external effect. If cancellation happens after dispatch, WAL recovery and
reconciliation still own the outcome.

## 18. Context Isolation

V0.8 must keep context scoped.

Frozen rule:

```text
Agent A ContextWorkingSet must not be directly visible to Agent B.
```

Cross-agent transfer paths:

- IPC payload;
- ResourceHandle plus explicit share authorization;
- durable child result message;
- future audited read path.

Non-transfer paths:

- direct access to another Agent's `ContextWorkingSet`;
- copying raw Context Pages as authority;
- sharing mutable Context Manager pin/request state.

Context Page remains a projection object. It is not an IPC object and not a
resource handle unless a future object abstraction explicitly models that.

## 19. Model / Provider Binding

Multi-agent runtime should allow different Agents to use different models or
providers, for example planner/coder/reviewer roles.

Frozen distinction:

| Concern | Owner |
| --- | --- |
| Which model/provider profile to use | Host policy |
| Stable binding/reference for attribution | Kernel runtime metadata |
| Token/cost attribution | Accounting mechanism |
| Provider failure handling | Driver plus host policy |

V0.8 should not implement provider routing as Kernel authority. Model choice is
not a capability grant. The Kernel needs enough stable metadata to attribute
usage and reproduce audit context, not to rank providers.

## 20. Tool Set Isolation

V0.6 already solves the core of tool visibility:

```text
Agent grants -> CapabilityEvaluator -> ToolRegistry.model_schemas()
```

V0.8 should reuse this. It should not add a parallel "subagent tool ACL" system.

Frozen rules:

- child Agent sees only schemas authorized by its grants;
- execution rechecks authorization even if a hidden tool call is fabricated;
- tool visibility is a projection of authority, not authority transport;
- IPC cannot cause a receiver to execute a tool unless the receiver is
  authorized or receives explicit delegated authority.

## 21. Scheduler Compatibility

Current Scheduler already schedules `ProcessControlBlock` values with `agent_id`
and `session_id`. It does not require a single global Agent.

V0.8 should not rewrite Scheduler. It should extend around:

- admission checks;
- process hierarchy metadata;
- cancellation propagation;
- budget attribution;
- waiting/block reasons for IPC;
- optional supervision notifications.

Current safe points are sufficient as a first integration surface:

- turn start;
- step start;
- LLM call before/after;
- Tool call before/after;
- durable dispatch before/after.

Multi-agent scheduling policy remains host-defined. Kernel mechanism must only
ensure legal process transitions and hard safety limits.

## 22. Multi-Agent Object Model

Frozen conceptual object model:

```text
Host
 |
 +-- AgentRegistry
 |    |
 |    +-- Agent A (capability principal)
 |    |    |
 |    |    +-- Session A (single-writer durable truth)
 |    |    +-- Process A1
 |    |         |
 |    |         +-- Process A2 (same Agent, no new principal)
 |    |
 |    +-- Agent B (child principal)
 |         |
 |         +-- Session B
 |         +-- Process B1
 |
 +-- Kernel Services
      |
      +-- Scheduler / Process Table
      +-- Capability / Delegation
      +-- IPC Channels
      +-- ResourceService
      +-- DurableToolExecutor
      +-- Recovery
      +-- Context VM
      +-- Accounting
```

Allowed cross-agent links:

```text
Agent A <-> Kernel IPC <-> Agent B
Agent A -> Resource share grant -> Agent B
Parent Agent -> narrowed delegated grant -> Child Agent
```

Forbidden implicit sharing:

- raw mutable Session transcript;
- raw ContextWorkingSet;
- unbounded ResourceStore access;
- copied parent grant strings;
- authority hidden inside IPC payload;
- Process identity as capability subject.

## 23. Durable vs Runtime State

V0.8 must freeze which facts survive recovery.

| Item | Durable or Runtime | Reason |
| --- | --- | --- |
| Agent identity | Durable or host-reconstructable | Child Agent identity affects authority, audit, and Session ownership. |
| Agent parent relation | Durable | Needed for delegation provenance and supervision after restart. |
| Session events | Durable | Replay truth and context projection source. |
| Delegated grant | Durable | Authority must survive restart and support future revocation. |
| Delegation provenance | Durable | Required for audit and revocation compatibility. |
| IPC message envelope | Durable for V0.8 | Needed to recover send-before-receive crashes. |
| IPC in-memory queue position | Runtime-derived | Can be reconstructed from pending envelopes. |
| IPC ack/delivery state | Durable envelope state | Needed to avoid lost messages and support redelivery semantics. |
| Resource ownership | Durable metadata | Existing V0.5 model. |
| Resource share grant | Durable | Access must survive restart and be auditable. |
| Durable Tool WAL | Durable | Existing V0.3/V0.6 external effect invariant. |
| READY queue | Runtime only | Scheduling order is live state. |
| RUNNING process | Runtime only | Reconstructed from Session/recovery facts. |
| WAITING registry | Runtime only | Reconstructed from pending IPC/tool/context facts when necessary. |
| BLOCKED registry | Runtime only | Reconstructed from recovery, budget, or policy state. |
| Process usage counters | Runtime observation | Not durable billing truth. |
| ContextWorkingSet | Runtime projection | Rebuilt from Session and policy. |
| Context summaries | Durable when committed | They are derived but non-deterministic and affect projection. |

Do not persist the entire process table as canonical truth. Persist only the
semantic facts required to rebuild it.

## 24. Mechanism vs Policy Matrix

| Component | Kernel mechanism | Host policy |
| --- | --- | --- |
| Agent creation | Allocate identity and record parent relation. | Decide whether a child should exist. |
| Process creation | Create PCB, validate lifecycle, admit to scheduler. | Choose role, priority, model, prompt, budget. |
| Process tree | Maintain parent-child runtime relation. | Choose supervision strategy. |
| IPC channel | Create bounded channel, message identity, delivery state. | Choose channel size, timeout, drop/retry policy. |

| Delegation | Validate narrowing and provenance. | Decide which authority to request/approve. |
| Resource sharing | Enforce share grant and access checks. | Decide whether sharing is allowed. |
| Budget accounting | Measure, attribute, block on hard ceiling. | Allocate quota and handle overage. |
| Fault isolation | Preserve child exit state and notify supervisor. | Retry, restart, ignore, or fail parent. |
| Cancellation | Propagate signal and stop at safe points. | Decide when to cancel and whether detachment is allowed. |

## 25. Threat Model

| Threat | Invariant | Enforcement boundary | V0.8 mitigation direction |
| --- | --- | --- | --- |
| Child capability escalation | Child authority <= delegated authority <= parent authority. | Delegation evaluator. | Validate action, scope, constraints, bounding set, depth, and provenance. |
| Forged sender identity | IPC sender is Kernel-attached metadata. | IPC send boundary. | Sender fields come from current process/agent, not payload. |
| IPC carrying fake authority | IPC transfers data, not authority. | IPC receive and capability evaluator. | Ignore grant-like payload unless it arrives through Kernel delegation path. |
| Cross-agent resource access | Handle reference != authority. | ResourceService. | Require owner/share/capability checks before read/stat. |
| Confused deputy | Receiver authority does not authorize leaking data to sender. | IPC response/resource share boundary. | Track caller provenance and require response/share authorization. |
| Child budget exhaustion | Child cannot consume unbounded parent/host resources. | Scheduler/accounting. | Enforce process, agent, and aggregate host ceilings. |
| IPC queue exhaustion | Channels are bounded Kernel objects. | IPC channel. | Enforce max messages/bytes and block sender. |
| Cross-agent context leak | ContextWorkingSet is process/session scoped. | Context VM and IPC boundary. | No direct sharing; transfer only through IPC/resource grants. |
| Malicious child tool request | LLM is untrusted proposer. | ToolRegistry and DurableToolExecutor. | Schema visibility plus execution recheck. |
| Parent cancellation after durable dispatch | Durable facts cannot disappear. | Durable Tool WAL/recovery. | Reconcile dispatched operations; do not roll back by cancellation. |
| Stale delegated capability | Future revocation must be possible. | Delegation provenance and evaluator. | Include delegation id, parent grant reference, epoch/lease compatibility. |
| Crash during IPC delivery | Message must not be silently lost. | Durable IPC envelope and Session send/receive facts. | Redeliver until ack; receiver de-duplicates by message_id. |

This is not a production sandbox claim. Host integrations must still keep
sensitive OS, network, file, and credential access behind Kernel-controlled
tools, resources, and policy.

## 26. Reference Systems Review

References were used only as architecture pressure tests, not as products to
copy.

| System | Useful lesson | What AgentKernel should not copy |
| --- | --- | --- |
| Linux process model | Separate runnable state, wait/block states, parent relation, scheduling, and resource accounting. | `fork`, POSIX signals, fd-as-universal-object, preemptive CPU scheduling. |
| seL4 thread/capability model | Keep authority explicit and capability-based; avoid policy in mechanism. | Low-level microkernel object granularity and reply-capability protocol. |
| Kubernetes workload model | Separate desired spec from observed status; schedule with resource limits and status. | Cluster controllers and Pods as conversation/session substitutes. |
| Codex-style task runtime | Sandbox and approvals are separate controls; isolated workspaces help parallel tasks. | Product task orchestration as Kernel object model. |
| Gemini CLI | Session resume, approval modes, and subagent display are useful UX signals. | Treating UI subagent history as Kernel IPC semantics. |
| DeepSeek Harness | Separate durable session facts from live agent control surfaces and composition backends. | Making every Kernel invariant a plugin choice. |
| OpenHands | Conversation/workspace/server boundaries show value of workspace isolation and session auth. | Frontend Agent Canvas semantics as core Kernel runtime. |
| Letta | Memory/channel/product runtime concerns are distinct from local Kernel scheduling. | Pulling persistent memory into V0.8 before AgentKernel has V0.9 memory design. |
| LangChain/LangGraph | Workflow persistence and graph control are useful baselines for orchestration. | Collapsing Kernel authority into chain/graph node conventions. |

AgentKernel's positioning remains distinct: it is designing trusted local
runtime mechanisms for uncertain agent execution, not a product shell, workflow
DSL, or general distributed system.

## 27. Backward Compatibility

| Version | V0.8 extension | Potential regression | Required invariant |
| --- | --- | --- | --- |
| V0.1 Execution | Child Agents and Processes still call tools through ToolRegistry/DurableToolExecutor. | Direct child tool calls bypass Kernel. | All tool execution crosses trusted boundary. |
| V0.2 Recovery | Multiple Sessions need correlation for IPC/spawn. | Shared transcript destroys single-writer replay. | One Session per Agent, single writer. |
| V0.3 Durable Tool | Child cancellation and failure interact with WAL. | Cancelling child erases ambiguous dispatch. | Dispatched external effect must reconcile. |
| V0.4 Context VM | Each Agent/Process gets isolated working-set projection. | Shared Context leaks facts or policy pins. | Context is projection and scoped. |
| V0.5 Resource | Resource sharing adds authorized access relation. | Sending handle grants implicit read. | Handle reference != authority. |
| V0.6 Capability | Delegation narrows structured grants. | Child copies parent grants or legacy strings. | Child authority <= parent effective authority. |
| V0.7 Process Runtime | Process tree extends PCB relation. | Scheduler starts scheduling Agents or policy roles. | Scheduler schedules Processes only. |

No major rewrite is required. V0.8 must add new objects and validation paths
without changing existing V0.1-V0.7 meanings.

## 28. V0.8 Scope

In scope for V0.8 implementation:

1. Agent registry and child Agent identity.
2. Process Tree metadata and supervision hooks.
3. Local Kernel IPC channel with durable envelope.
4. Capability delegation and narrowing validation.
5. Resource sharing authorization.
6. Process/Agent budget isolation and attribution.
7. Child fault isolation.
8. Structured cancellation propagation.
9. Multi-agent recovery semantics.
10. Deterministic Multi-Agent RuntimeBench.

Out of scope:

- distributed agents;
- remote IPC;
- cluster scheduling;
- RBAC;
- IAM;
- general namespace framework;
- full revocation engine;
- persistent memory;
- network sandbox;
- preemptive scheduling;
- consensus;
- distributed transaction;
- workflow DSL;
- B8 scheduler scalability unless separately scheduled as a microbenchmark.

## 29. Implementation Dependency Graph

Recommended implementation phases:

```text
Phase 1: Agent Registry / Child Agent Identity
  -> Phase 2: Process Tree and Supervision Metadata
      -> Phase 3: Capability Delegation Core
          -> Phase 4: Kernel IPC Channels
              -> Phase 5: Resource Sharing Grants
                  -> Phase 6: Budget / Fault / Cancellation Isolation
                      -> Phase 7: Multi-Agent Recovery Semantics
                          -> Phase 8: Multi-Agent RuntimeBench
```

Reasoning:

- Delegation should exist before IPC can safely carry resource/task requests.
- Process Tree can be implemented before IPC because it is runtime metadata.
- Resource sharing depends on delegation/capability shape.
- Budget/fault/cancellation become meaningful after child Agents and processes
  can exist.
- Multi-Agent RuntimeBench should validate the integrated mechanism, not lead
  implementation.

Alternative:

IPC could be implemented before delegation as data-only channels. That is
acceptable only if resource references and tool requests remain inert and
authorization denial is explicit. The safer implementation order is to add
delegation first.

## 31. Architecture Risks

| Risk | Severity | Mitigation |
| --- | --- | --- |
| Shared transcript temptation | High | Freeze one Session per Agent and IPC for collaboration. |
| Delegation accidentally becomes inheritance | High | Child starts deny-by-default; require positive narrowed grants. |
| IPC becomes hidden authority transport | High | No authority fields in message payload; grants only through Kernel delegation. |
| Confused deputy through capable child/peer | High | Track provenance and require response/resource sharing authorization. |
| Process Tree treated as durable truth | Medium | Persist semantic spawn facts; reconstruct live queues. |
| Global ordering overreach | Medium | Promise per-channel/per-sender ordering only. |
| Resource sharing mutates ownership | Medium | Prefer share grants over transfer. |
| Budget accounting treated as billing ledger | Medium | Keep accounting observational unless a separate ledger is designed. |
| Cancellation hides durable side effect | High | WAL reconciliation remains authoritative after dispatch. |
| Scope creep into namespace/memory/RBAC | Medium | Keep those out of V0.8 scope. |

## 32. Design Freeze Decision

Decision:

```text
READY_FOR_V0.8_IMPLEMENTATION
```

The V0.8 architecture is frozen with these decisions:

- Agent Tree and Process Tree are separate.
- Agent is the capability principal.
- Process is the runtime schedulable identity.
- Child process does not create a new principal.
- Child Agent creates a new principal and normally owns a new Session and at
  least one Process.
- One primary Session per Agent is the default.
- Session remains single-writer.
- Cross-agent collaboration uses Kernel IPC, not shared transcript mutation.
- IPC uses local durable message envelopes with explicit delivery state.
- IPC does not implicitly transport authority.
- Delegation is explicit, positive, narrowed, and provenance-carrying.
- ResourceHandle transfer is data transfer, not permission transfer.
- Resource sharing uses explicit share grants by default.
- Scheduler continues to schedule Processes, not Agents.
- Budget, fault, and cancellation isolation are Kernel mechanisms with policy
  choices supplied by Host.
- Durable facts remain durable across child failure and cancellation.

V0.8 implementation may begin in a later task. This review did not implement
any V0.8 runtime feature.
