# V0.6 Capability Architecture Freeze Review

Status: review only. This document freezes the V0.6 Capability / Namespace
architecture direction before implementation. It does not define new runtime
code and does not require changes to `agentkernel/`.

Final decision: `READY_FOR_IMPLEMENTATION`.

## 1. Executive Summary

AgentKernel V0.6 Capability Architecture passes the freeze review.

The design preserves the core AgentKernel runtime principle:

```text
LLM = untrusted proposer
Kernel = authority
```

The model may propose tool calls, resource reads, child-agent creation, memory
operations, or future IPC. It must not decide whether those operations are
authorized. V0.6 should therefore place capability evaluation at trusted Kernel
boundaries that already exist after V0.5:

- `AgentControlBlock` provides stable agent identity and current legacy
  capability state.
- `ToolRegistry` is the model-schema and tool-execution gate.
- `DurableToolExecutor` is the side-effect WAL gate.
- `ResourceService` is the resource-handle resolution and read gate.
- `Session` remains the durable source of recovery facts.
- Context VM remains a projection and budget mechanism, not an authority store.

The V0.6 design should be implemented as a structured, Kernel-owned
authorization mechanism over these existing boundaries. The current V0.1-V0.5
architecture does not require a major rewrite before V0.6 implementation.

## 2. Trusted Kernel Boundary Review

`KERNEL_BOUNDARY_REVIEW`: capability decisions belong in the Trusted Kernel.

The Kernel must own authorization mechanism because capability checks protect
state transitions, side effects, and cross-boundary access. If a model, tool, or
resource driver can make final permission decisions independently, the runtime
loses the property that model-directed work is mediated by Kernel authority.

| Responsibility | Kernel/Host | Freeze decision |
|---|---|---|
| Capability evaluation | Kernel | Evaluate grants against subject, action, scope, and constraints. |
| Authorization decision | Kernel | Return allow, deny, or needs-approval without delegating final authority to the model. |
| Resource scope checking | Kernel | Resolve handles and check scope before reaching a `ResourceStore` driver. |
| Tool schema projection | Kernel mechanism using host-provided tool definitions | Hide unauthorized tools, but still recheck execution. |
| Tool execution authorization | Kernel | Reject unadvertised or unauthorized calls before handler invocation. |
| Durable side-effect authorization | Kernel | Authorize prepare, dispatch, reconcile, and recovery-sensitive actions. |
| Delegation validation | Kernel | Enforce child grants as a subset of parent effective authority. |
| Revocation state | Kernel | Apply to future authorization decisions and delegated grant chains. |
| Audit event shape | Kernel | Record security-relevant decisions without leaking secrets. |
| Business permission policy | Host policy | Decide which grants to issue or revoke for a product or user. |
| Human approval UX | Host policy | Convert `NEEDS_APPROVAL` into a product-specific workflow. |
| Payment/business rules | Host policy | Decide whether payment is allowed; Kernel enforces the resulting grant. |
| Retry strategy | Host policy constrained by Kernel | Strategy may vary, but durable retry cannot bypass WAL authorization. |

Mechanism and policy should stay separated:

- Kernel mechanism: capability evaluation, action matching, scope checking,
  constraint enforcement, delegation restriction, revocation application, stable
  denial codes, and recovery-safe WAL checks.
- Host policy: whether a user may pay, which business account is active,
  whether human approval is required, model selection, prompt design, plugin
  selection, memory strategy, and context-reclaim preferences.

The design should not allow:

- model-authored prompts to grant authority;
- tools to self-authorize external effects;
- resource drivers to decide whether an agent may read a logical handle;
- Context Pages to carry authority merely because their text appears in the
  working set.

## 3. Capability Model Validation

The proposed model is expressive enough for V0.6 and compatible with V0.1-V0.5.

Required concepts:

| Concept | Validation |
|---|---|
| Agent Identity | Current `AgentControlBlock` already contains `agent_id`, `session_id`, and `parent_agent_id`. V0.6 can derive a stable subject identity without changing the loop shape. |
| Capability Grant | A Kernel-owned positive grant can represent legacy string capabilities and future structured authority. |
| Action | A small verb vocabulary can distinguish read, write, execute, prepare, dispatch, reconcile, spawn, delegate, and revoke. |
| Resource Scope | URI-like logical scopes can address tools, artifacts, agents, sessions, memory, datasets, databases, and external services. |
| Constraint | Constraints can narrow authority by expiration, byte limits, call count, effect kind, approval requirement, recovery-only use, and argument profile. |

Validation example:

```text
Subject:
  agent://agent-a

Allowed grant:
  action: resource.read
  scope: artifact://project-a/**

Denied requests:
  action: resource.write
  scope: artifact://project-a/report.md

  action: database.write
  scope: database://finance/**
```

This is expressible because the allowed grant is positive and narrow. It grants
only `resource.read` under `artifact://project-a/**`. It does not imply write,
delete, database access, or access to other artifact scopes.

The design also supports tool-specific distinction:

```text
Allowed:
  action: tool.execute
  scope: tool://payment.quote

Denied:
  action: tool.execute
  scope: tool://payment.charge
```

This avoids the current limitation where coarse capability strings can blur a
safe quote operation and an irreversible charge operation.

Freeze decision: the model is suitable for implementation if V0.6 starts with a
small mandatory action vocabulary and treats current `required_capability`
strings as compatibility aliases.

## 4. Namespace Review

The proposed namespace model is valid if it remains a logical authorization
view, not a Linux filesystem clone.

Namespaces should make Kernel authority legible:

| Namespace | Purpose |
|---|---|
| `tool://` | Registered tool and tool-package authority. |
| `artifact://` | V0.5 resource handles and future project/session artifact scopes. |
| `resource://` | Optional generic resource namespace for non-artifact resources if needed later. |
| `agent://` | Agent identities, parent-child subtrees, spawn, signal, and delegation targets. |
| `memory://` | Future V0.9 durable memory scopes. |
| `session://` | Session-local event, context, and recovery objects if exposed to authorization. |
| `database://` | External structured stores. |
| `network://` | External network or API boundary. |

The namespace layer should not imply that AgentKernel is becoming a Linux VFS.
It is a logical isolation view used for authorization requests and audit. A
scope such as `artifact://project-a/**` does not require a backing directory
tree. It means the Kernel can map a model-visible or host-visible object to a
stable logical name and decide whether a subject may act on it.

Namespace freeze rules:

- Model-facing handles remain opaque.
- Backend paths remain hidden behind drivers.
- Scope matching should start with exact and suffix-wildcard matching.
- Regex-style matching should be deferred until there is a real need.
- Scope normalization must be Kernel-owned to avoid alternate spellings that
  bypass checks.

Freeze decision: the namespace design is appropriate for V0.6 as a logical
authorization surface.

## 5. Delegation Review

`DELEGATION_REVIEW`: delegation is valid only when child authority is a subset
of parent authority.

Required invariant:

```text
child privilege <= parent privilege
```

A parent agent may create a child only if it has authority to spawn or delegate
within the target `agent://` scope. The child grant set must be computed by
intersection, not by copying parent authority wholesale.

Delegation must forbid:

- expanding actions, such as parent has `resource.read` but child receives
  `resource.write`;
- expanding scope, such as parent has `artifact://project-a/logs/**` but child
  receives `artifact://project-a/**`;
- lowering constraints, such as parent has `max_bytes=8192` but child receives
  `max_bytes=65536`;
- removing required approval;
- extending expiration;
- increasing delegation depth;
- bypassing revocation by copying grants into independent child state.

Example:

```text
Parent grant:
  action: resource.read
  scope: artifact://project-a/**
  constraint: max_bytes=65536

Child request:
  action: resource.read
  scope: artifact://project-a/logs/**
  constraint: max_bytes=8192

Child grant:
  action: resource.read
  scope: artifact://project-a/logs/**
  constraint: max_bytes=8192
```

If the intersection is empty, delegation must be denied.

Freeze decision: the design is correct if implementation persists or can
reconstruct delegation lineage through `parent_grant_id`, issuer identity, and
revocation state.

## 6. Recovery Compatibility

V0.6 must be compatible with the V0.3 Durable Tool WAL. Capability revocation
must not corrupt recovery.

Important WAL sequence:

```text
prepare
dispatch
commit
```

Revocation timing review:

| Revocation timing | Required behavior |
|---|---|
| Before `prepare` | Deny creation of durable intent. No `tool/prepare` should be appended for an unauthorized operation. |
| After `prepare`, before `dispatch` | Keep the `prepare` event as a durable fact. Deny new dispatch unless current authority still permits it. The runtime may record abort/denied bookkeeping. |
| After `dispatch`, before `commit` | Keep `dispatch` as a durable fact. Do not delete or rewrite history. Recovery may reconcile or record observed commit/abort state, but must not create a new external side effect without current authorization. |
| After `commit` | Keep commit as historical truth. Revocation affects future operations only. |

The governing principles are:

```text
durable fact cannot be deleted
future side effect requires authorization
```

This means revocation is prospective. It blocks future authority, but it does
not pretend an already dispatched payment, email, write, or API call did not
happen. A recovery-only permission may be useful for reconciling ambiguous
external state after restart without granting permission to dispatch again.

Freeze decision: V0.6 can be implemented without changing the WAL ordering.
Implementation must be careful to split permission for `prepare`, `dispatch`,
and `reconcile`.

## 7. Least Privilege Review

The V0.6 design supports least privilege for the required cases.

Case 1: Research Agent

```text
Grant:
  action: resource.read
  scope: artifact://research/**

Denied:
  action: resource.delete
  scope: artifact://research/**
```

The agent can read artifacts required for research but cannot delete them. A
separate `resource.delete` grant would be required for destructive operations.

Case 2: Payment Agent

```text
Grant:
  action: tool.execute
  scope: tool://payment.quote

Denied:
  action: tool.execute
  scope: tool://payment.charge
```

The agent can obtain quotes without being able to execute a charge. This is a
key improvement over coarse payment capability strings.

Case 3: Parent Agent creates Child Agent

```text
Parent grant:
  action: resource.read
  scope: artifact://project-a/**
  constraint: max_bytes=65536

Child grant:
  action: resource.read
  scope: artifact://project-a/logs/**
  constraint: max_bytes=8192
```

The child receives a narrower scope and a stricter byte limit. It cannot infer
or request the parent's broader authority unless the parent and Kernel
explicitly delegate it.

Freeze decision: least privilege is expressible with the proposed
subject/action/scope/constraint model.

## 8. Compatibility Review

V0.6 does not require a major rewrite of V0.1-V0.5.

| Version | Existing abstraction | V0.6 impact | Major rewrite required |
|---|---|---|---|
| V0.1 Execution | Agent loop and tool syscall boundary | Replace exact string authorization internals with structured evaluation at the same boundary. | No |
| V0.2 Recovery | Ordered Session Event Log and replay analysis | Optional audit events may be added later; existing recovery events remain valid. | No |
| V0.3 Durable Tool | WAL with prepare, dispatch, commit, abort, reconcile | Add action-specific authorization checks around existing phases. | No |
| V0.4 Context VM | Event projection into context pages and working set | No authority should move into Context Pages; future context actions can be authorized at Kernel boundaries. | No |
| V0.5 Resource Layer | ResourceHandle, ResourceService, ResourceStore | Add structured scope checks inside the trusted service while preserving handle semantics. | No |

Compatibility notes:

- `required_capability` can remain a compatibility declaration.
- `capability_bounding_set` maps naturally to maximum effective or delegable
  authority.
- `ResourceHandle` does not need immediate format changes if V0.6 resolves old
  handles to internal logical scopes.
- `Session` does not need a rewrite; audit events should be additive.
- ACB should not become a policy database. It should remain identity and
  lifecycle state, with grants attached or stored in a Kernel-owned grant store.

Future version readiness:

| Future version | V0.6 contribution | Redesign needed |
|---|---|---|
| V0.7 Process Scheduler | Process identity, grant-bound execution, and future quota constraints can build on Agent Identity and Capability Grants. | No, if identity remains stable. |
| V0.8 Multi-Agent IPC | Delegation, `agent://`, and future `ipc.*` actions provide the required authority shape. | No, but event ownership must be designed carefully. |
| V0.9 Memory | `memory://` scopes and read/write actions provide a natural memory permission model. | No, if memory is treated as Kernel-managed resource access. |

## 9. Risks

Known risks before implementation:

| Risk | Why it matters | Required mitigation |
|---|---|---|
| Constraint semantics | Constraints such as `max_calls`, `allowed_args`, `requires_approval`, and `recovery_only` can become ambiguous or policy-heavy. | Start with a small required set and define deterministic evaluation order. |
| Revocation timing | Revocation during WAL recovery can accidentally block recording truth or allow duplicate external dispatch. | Freeze separate rules for prepare, dispatch, reconcile, and commit bookkeeping. |
| Audit event design | Persisted authorization events may expose sensitive data or complicate replay. | Record stable decision metadata only; avoid raw secrets and full arguments by default. |
| Namespace normalization | Alternate spellings, wildcard edge cases, or URI confusion can create bypasses. | Kernel-owned canonicalization and conservative matching; no arbitrary regex in V0.6. |
| Multi-agent ownership | Child sessions, shared artifacts, and parent-child revocation can become unclear. | Persist delegation lineage and keep child grants derived from parent grants. |
| Legacy alias width | Mapping old strings to structured grants may accidentally over-grant. | Make compatibility aliases conservative and test hidden-schema plus runtime denial behavior. |
| Tool metadata trust | Tool definitions may under-declare effects or scopes. | Treat tool metadata as declarations checked by Kernel, and require durable tools to provide effect metadata. |
| Host policy leakage | Product-specific rules may drift into Kernel mechanism. | Keep Kernel decisions generic and let Host issue, revoke, or require approval for grants. |

None of these risks blocks implementation. They should become V0.6 test cases
and implementation acceptance criteria.

## 10. Final Decision

`READY_FOR_IMPLEMENTATION`

The V0.6 Capability / Namespace architecture is ready to move from design into
an implementation plan. The design is aligned with AgentKernel's OS-inspired
principles without becoming a Linux clone:

- authority is Kernel-owned;
- policy remains host-owned;
- namespaces are logical isolation views;
- tools and resources declare or expose facts but do not self-authorize;
- delegation is narrowing only;
- revocation is prospective and recovery-safe;
- V0.1-V0.5 abstractions remain intact.

Implementation should start with the smallest structured evaluator that
preserves current behavior, then add resource scope checks, durable action
checks, audit events, and delegation tests incrementally.
