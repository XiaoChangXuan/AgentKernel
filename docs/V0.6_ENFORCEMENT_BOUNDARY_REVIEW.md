# V0.6 Enforcement Boundary Review

Status: architecture design only. This document reviews where V0.6 Capability
enforcement belongs in the Kernel after Phase 1. It does not implement
namespace, delegation, revocation, RBAC, IAM, or a full policy engine.

Final decision: `READY_FOR_PHASE_2_IMPLEMENTATION`.

## 1. Current Authorization Flow

Phase 1 introduced a minimal Kernel-owned capability core:

```text
CapabilityGrant
AuthorizationRequest
AuthorizationDecision
CapabilityEvaluator
```

The only integrated enforcement path today is legacy Tool authorization.

Current Tool schema projection:

```text
AgentControlBlock.capabilities
  |
CapabilityEvaluator.from_legacy_capabilities()
  |
ToolDefinition.required_capability
  |
legacy_tool_request(
  action = tool.execute,
  resource = tool://<required_capability>
)
  |
ToolRegistry.model_schemas()
```

Current Tool execution:

```text
LLM proposes ToolCall
  |
ToolRegistry.resolve_for_execution()
  |
CapabilityEvaluator.authorize()
  |
ToolRegistry.invoke()
  |
Tool handler
```

The current compatibility mapping is intentionally conservative:

```text
required_capability = "math.add"

maps to:
  action: tool.execute
  resource: tool://math.add
```

This preserves V0.1-V0.5 behavior:

- authorized tools are projected to the model;
- unauthorized tools are hidden from model schemas;
- unauthorized or unadvertised tool calls are denied again at execution time;
- `AgentControlBlock.capabilities` and `capability_bounding_set` remain active;
- old exact capability strings are not removed.

Current non-Tool boundaries:

| Module | Current authorization role |
|---|---|
| `agentkernel/agent.py` | Owns stable agent identity, lifecycle, budgets, legacy effective capabilities, and bounding set. |
| `agentkernel/session.py` | Owns append-only event ordering, durability boundary, recovery facts, and model-history projection. It does not make authorization decisions today. |
| `agentkernel/durable_tools.py` | Calls `ToolRegistry.resolve_for_execution()` before read-only invocation or durable mutation `prepare`. Retry and reconcile re-resolve the registered tool. |
| `agentkernel/resources/tools.py` | Exposes model-facing `resource_stat` and `resource_read` tools guarded by legacy `required_capability="resource.read"`. |
| `agentkernel/resources/service.py` | Enforces trusted resource URI parsing, owner matching, byte range checks, read limits, and store access. It does not yet consume structured `AuthorizationRequest`. |

The important current invariant is:

```text
LLM = untrusted proposer
ToolRegistry = Kernel authority for tool execution
```

## 2. Kernel Enforcement Points

Capability checks should appear at Kernel boundaries, not inside prompts, model
messages, or untrusted tool code.

### Tool Layer

Current status: implemented for legacy compatibility.

The Tool layer must remain the first enforcement point because it controls both
model-visible schema projection and runtime execution. Schema projection alone
is insufficient because a model or provider may still emit a hidden tool call.

Required Tool-layer checks:

| Flow | Check |
|---|---|
| `ToolRegistry.model_schemas()` | Authorize `tool.execute` before showing a schema to the model. |
| `ToolRegistry.resolve_for_execution()` | Authorize `tool.execute` before any handler invocation or durable intent. |
| `ToolRegistry.invoke()` | Should receive already-authorized definitions only. It should not become the primary authorization boundary. |

Phase 2 should keep the public behavior of `required_capability`, but route
structured tool metadata through the same evaluator.

### Resource Layer

Current status: V0.5 owner/range security is implemented, structured
capability enforcement is not.

Resource authorization should be enforced in `ResourceService`, not only in the
model-facing resource tools.

Reason:

```text
Permission to call resource_read
  !=
Permission to read every artifact handle
```

The resource tools should remain syscall wrappers. The trusted service should
combine:

1. URI parsing;
2. metadata lookup;
3. owner/session checks;
4. structured capability check;
5. byte range and limit validation;
6. store read.

Recommended Phase 2 Resource flow:

```text
Tool handler
  |
ResourceService.stat/read
  |
resolve ResourceHandle metadata
  |
CapabilityEvaluator.authorize(
  action = resource.stat or resource.read,
  resource = artifact://<logical-scope>
)
  |
range/limit validation
  |
ResourceStore
```

`ResourceStore` must remain a driver, not an authority source.

### Durable Side Effect Layer

Current status: `DurableToolExecutor` inherits legacy tool authorization by
calling `ToolRegistry.resolve_for_execution()` before appending
`TOOL_PREPARE`. Retry and reconcile also re-resolve the tool.

That current ordering is correct for Phase 1, but Phase 2 needs action-specific
checks at durable boundaries.

Recommended Phase 2 mutation actions:

| Durable phase | Capability action | Enforcement point |
|---|---|---|
| Before `TOOL_PREPARE` | `tool.prepare` or mutation-specific `tool.execute` | Deny before durable intent exists. |
| Before `TOOL_DISPATCH` | `tool.dispatch` | Deny before external side effect can occur. |
| During retry | `tool.dispatch` | Re-authorize before repeated dispatch. |
| During reconcile | `tool.reconcile` | Allow safe observation without granting new dispatch. |
| Commit/abort bookkeeping | Kernel recovery authority | Record observed truth; do not require new external side-effect authority. |

The durable layer is a Kernel enforcement point because WAL events define the
boundary between proposed work, durable intent, external dispatch, and recovery
classification.

## 3. WAL Compatibility

The WAL-compatible authorization order should be:

```text
Capability Check
  |
WAL prepare
  |
Capability Check
  |
dispatch
  |
commit or abort
```

Current Phase 1 order for mutation tools:

```text
ToolRegistry.resolve_for_execution()
  |
TOOL_PREPARE append
  |
flush
  |
TOOL_DISPATCH append
  |
flush
  |
handler invocation
  |
TOOL_COMMIT or TOOL_ABORT append
```

This is compatible with V0.6 because no durable mutation intent is written
until the tool call is authorized.

Phase 2 should split the current single legacy check into explicit durable
actions:

```text
authorize tool.execute/tool.prepare
append TOOL_PREPARE
flush
authorize tool.dispatch
append TOOL_DISPATCH
flush
invoke external side effect
append TOOL_COMMIT or TOOL_ABORT
flush
```

Recovery compatibility rules:

- If authorization fails before `prepare`, no durable operation should exist.
- If authorization is revoked after `prepare` but before `dispatch`, the
  `prepare` event remains a durable fact, but no new dispatch may occur.
- If authorization is revoked after `dispatch`, the `dispatch` event remains a
  durable fact. Reconcile may need a narrower recovery-only authority to record
  observed external state.
- Commit and abort events record Kernel truth about an existing operation. They
  must not be used to create new external side effects.

The principle remains:

```text
durable fact cannot be deleted
future side effect requires authorization
```

No Session rewrite is required. If future authorization audit events are added,
they should be append-only and additive to current recovery analysis.

## 4. Resource Handle Security

V0.5 Resource Handle security currently has three layers:

| Layer | Current role |
|---|---|
| `ResourceHandle` | Model-safe projection containing an opaque `artifact://res_*` URI and safe metadata. |
| `ResourceService` | Trusted URI parser, owner checker, byte-range validator, read limiter, and metrics owner. |
| `ResourceStore` | Replaceable byte driver for metadata and payload storage. |

This is the right foundation for V0.6 because the model never receives a raw
store path or driver handle.

Capability should compose with Resource Handle security as an additional
Kernel-owned check:

```text
resource_read tool authorization
  |
ResourceService owner and URI resolution
  |
Capability check on logical resource scope
  |
range and max_read_bytes validation
  |
ResourceStore.read()
```

The exact logical scope should be resolved by the Kernel, not guessed by model
text. The current handle format is:

```text
artifact://res_<id>
```

Phase 2 can preserve that model-facing URI while internally authorizing against
metadata-derived scopes such as:

```text
artifact://session/<session_id>/<resource_id>
artifact://agent/<agent_id>/<resource_id>
artifact://project/<project_id>/**
```

Important boundary decisions:

- `resource_read` legacy tool permission should not imply cross-session access.
- Owner mismatch should remain an immediate `ResourceAccessDenied`.
- Capability denial should also map to a stable access-denied result.
- `ResourceStore` should not know about agents, grants, or policy.
- Resource handles should remain durable references, not permission tokens by
  themselves.

This preserves least privilege while keeping V0.5 artifact handles compatible.

## 5. Future Compatibility

### V0.7 Process

V0.7 Process/Scheduler will need stable process identity and possibly quotas.
The current ACB already provides `agent_id`, `session_id`,
`parent_agent_id`, lifecycle state, budgets, and legacy capability bounds.

No major redesign is required if Phase 2 keeps authorization requests based on
Kernel identity rather than model text.

Expected extension:

```text
AgentControlBlock identity
  +
CapabilityGrant set
  +
process quota/budget metadata
```

### V0.8 Multi-Agent

V0.8 Multi-Agent requires child identity, IPC, delegation, and ownership
boundaries. Enforcement review supports this direction, but Phase 2 should not
implement delegation yet.

Required later checks:

- `agent.spawn` before child creation;
- `agent.signal` before pause/resume/cancel;
- `ipc.send` and `ipc.receive` before cross-agent communication;
- delegation by intersection so `child privilege <= parent privilege`.

No Tool or Resource boundary rewrite is required if grants remain
subject/action/scope based.

### V0.9 Memory

V0.9 Memory should reuse the same enforcement shape:

```text
action: memory.read or memory.write
resource: memory://<logical-scope>
```

Memory should not become hidden prompt state that bypasses Kernel authority.
Memory reads and writes should behave like Resource or IPC access: the model can
request them, but Kernel services authorize and record them.

No major redesign is required if memory is introduced as another Kernel-managed
resource namespace rather than as ad hoc prompt injection.

## 6. Final Decision

`READY_FOR_PHASE_2_IMPLEMENTATION`

The current Phase 1 Capability Core is positioned correctly:

- Tool enforcement already lives in `ToolRegistry`.
- Durable Tool WAL already calls the Tool boundary before `prepare`.
- Resource Handle security already has a trusted `ResourceService` boundary.
- `AgentControlBlock` provides stable subject identity and legacy bounding.
- `Session` remains the append-only source of recovery truth rather than a
  mutable policy store.

Phase 2 should implement structured enforcement only at these existing Kernel
boundaries:

1. Tool layer: structured `tool.execute` compatibility with existing
   `required_capability`.
2. Resource layer: `resource.stat` and `resource.read` checks inside
   `ResourceService`.
3. Durable side-effect layer: action-specific checks for prepare, dispatch, and
   reconcile without breaking WAL ordering.

Phase 2 should not include delegation, revocation, RBAC, IAM, users, or a full
policy engine. Those remain future work after the Kernel enforcement points are
stable and tested.
