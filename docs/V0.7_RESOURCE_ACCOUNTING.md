# V0.7 Resource Accounting

Status: Phase 3 implementation.

## Scope

This phase adds minimal Kernel runtime resource accounting for `ProcessControlBlock`.

Implemented:

- `ProcessUsageSnapshot`
- `UsageCollector`
- optional runtime quota fields on `AgentBudget`
- scheduler budget checks at cooperative safe points
- DefaultAgentLoop usage collection for provider-reported LLM usage and Tool execution
- ResourceService metrics sampling through existing `ResourceMetrics`

Not implemented:

- Capability authority changes
- ResourceService authorization changes
- ResourceStore changes
- Durable Tool WAL schema changes
- IPC
- delegation
- namespace
- multi-agent scheduling policy
- persisted accounting ledger

## Runtime Usage Snapshot

`ProcessUsageSnapshot` is a process-local runtime view:

| Field | Meaning |
| --- | --- |
| `process_id` | Runtime process identity. |
| `token_usage` | Accumulated provider-reported total tokens. |
| `model_cost` | Optional host-supplied model cost accumulator. |
| `tool_calls` | Count of executed Tool calls observed by the loop. |
| `resource_reads` | Count of Resource read operations sampled from `ResourceMetrics`. |
| `resource_bytes` | Bytes read from ResourceService sampled from `ResourceMetrics`. |
| `wall_time` | Monotonic elapsed runtime since process accounting started. |

The snapshot is not a durable Session fact. It is live runtime accounting used by
the scheduler.

## Usage Collector

`UsageCollector` collects only Kernel-observable facts:

- `record_llm_usage()` consumes `ModelResponse.usage` when a provider reports it.
- `record_tool_call()` is invoked by `DefaultAgentLoop` after a Tool result is
  appended to the Session.
- `begin_resource_metrics()` and `observe_resource_metrics()` collect deltas from
  existing `ResourceMetricsSnapshot` values.
- `record_resource_read()` exists for host integrations that have a direct read
  byte count without sampling ResourceService metrics.

The collector does not authorize access and does not own persistence.

## Budget Model

`AgentBudget` keeps the existing per-turn limits:

- `max_steps_per_turn`
- `max_tool_calls_per_turn`

V0.7 Phase 3 adds optional process runtime limits:

- `max_token_usage`
- `max_model_cost`
- `max_total_tool_calls`
- `max_resource_reads`
- `max_resource_bytes`
- `max_wall_time_seconds`

All runtime limits default to `None`, which means no limit. This preserves
existing behavior for callers that do not opt into accounting.

## Scheduler Integration

`CooperativeScheduler` accepts an optional `UsageCollector`.

At a safe point, the scheduler checks:

1. cancellation request
2. pause request
3. runtime budget

If a running process exceeds a runtime budget, the scheduler transitions it to:

```text
RUNNING -> BLOCKED
```

The blocked reason is:

```text
budget_exceeded:<limit>
```

The scheduler raises `ProcessBudgetExceeded` so the caller can close the current
turn consistently.

## DefaultAgentLoop Integration

The loop starts process accounting when it dispatches or observes a running
process.

It records LLM usage after a response is returned and before the assistant
message is followed by the next scheduler safe point.

It records Tool usage after `TOOL_RESULT` is appended and after `AFTER_TOOL`
hooks run. This preserves the durable fact that the Tool result happened before
the scheduler blocks future progress.

Resource usage is collected by sampling optional `ResourceMetrics` instances
passed to the loop. The Resource Layer itself is unchanged.

## Recovery Semantics

Runtime usage accounting is not durable truth in this phase.

If a process is blocked because a budget is exceeded, host policy can decide to:

- increase the budget outside this phase;
- reset runtime usage with `UsageCollector.reset_process()`;
- unblock the process with `CooperativeScheduler.unblock()`;
- cancel or exit the process.

This keeps mechanism and policy separate:

- Kernel mechanism: measure usage, compare against configured quota, block.
- Host policy: decide whether to grant more budget, resume, or terminate.

## Compatibility

V0.1 Execution:

- Existing loop behavior is unchanged when no scheduler or collector is present.

V0.2 Recovery:

- Session remains the durable journal.
- Usage snapshots are live runtime state, not replay facts.

V0.3 Durable Tool:

- WAL prepare, dispatch, commit, abort, and authorization context are unchanged.
- Tool usage is recorded after the durable result is represented to the loop.

V0.4 Context VM:

- Context budgeting and reclaim remain owned by Context VM.
- Process token usage is provider-reported runtime consumption, not a replacement
  for context-window accounting.

V0.5 Resource Layer:

- ResourceService and ResourceStore are unchanged.
- Existing `ResourceMetrics` snapshots are sampled by the collector.

V0.6 Capability:

- Agent remains the capability principal.
- Resource accounting does not grant or deny capability by itself.

## Tests

Covered by `tests/test_resource_accounting.py`:

- usage accumulation from LLM usage, Tool execution, and ResourceService metrics
- budget exceeded detection
- scheduler transition to `BLOCKED`
- DefaultAgentLoop budget blocking after provider usage
- host-controlled recovery after budget pause/block

## Limitations

- Runtime accounting is in-memory only.
- Model cost is host supplied; there is no pricing table.
- Resource metrics are sampled by integration, not pushed by ResourceService.
- There is no persisted accounting event stream.
- Multi-process attribution for shared ResourceService instances remains future
  work for V0.8/V0.9.
