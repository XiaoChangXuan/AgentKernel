# V0.7 Cooperative Scheduler Implementation

## Scope

V0.7 Phase 2 adds a minimal Kernel-owned cooperative scheduler on top of the
V0.7 Process Core.

Implemented:

- ProcessManager / process table
- CooperativeScheduler
- READY queue
- WAITING registry
- BLOCKED registry
- schedule_next
- dispatch
- yield_process
- wake / unblock
- pause / resume
- cancellation safe points
- optional DefaultAgentLoop scheduler integration

Not implemented:

- preemptive scheduling
- IPC
- delegation
- namespace
- multi-agent runtime
- RBAC / IAM / policy engine
- changes to Capability, Resource, Durable Tool, or Context VM boundaries

The API uses `yield_process()` instead of `yield()` because `yield` is a Python
keyword.

## Boundary

The scheduler is a Kernel mechanism. It owns runtime process state and decides
which READY process may run next.

The scheduler does not own:

- Agent capability grants
- Resource authorization
- Durable Tool WAL schema
- Context VM page policy
- Host policy about whether a process should be paused or cancelled

The preserved identity split is:

| Concept | Role |
| --- | --- |
| Agent | Capability principal |
| Process | Runtime identity |
| Session | Durable journal |

## Process Manager

`ProcessManager` is the live process table.

Responsibilities:

- create a `ProcessControlBlock` from an `AgentControlBlock`
- register an existing PCB
- query process state
- list current process table entries
- delete exited processes

The process table is live runtime state. It is not a replacement for the Session
event log and does not persist scheduling decisions.

## Scheduler Core

`CooperativeScheduler` maintains:

- `ready_queue`: process ids that are in `READY`
- `waiting_registry`: process ids in `WAITING` mapped to wait reasons
- `blocked_registry`: process ids in `BLOCKED` mapped to blocked reasons

Core operations:

| Operation | Effect |
| --- | --- |
| `schedule_next()` | Selects and dequeues the next READY process |
| `dispatch()` | Moves a READY process to RUNNING |
| `yield_process(..., READY)` | Returns a RUNNING process to READY |
| `yield_process(..., WAITING)` | Moves a RUNNING process into WAITING |
| `yield_process(..., BLOCKED)` | Moves a RUNNING process into BLOCKED |
| `wake()` | Moves WAITING to READY |
| `unblock()` | Moves BLOCKED to READY |
| `pause()` / `resume()` | Moves PAUSED processes through host-controlled pause flow |
| `cancel()` | Records cancellation for the next cooperative safe point |

`schedule_next()` is priority-aware while preserving FIFO order for equal
priority.

## DefaultAgentLoop Safe Points

`DefaultAgentLoop` accepts an optional scheduler and optional `process_id` in
`run()`.

When no scheduler or process id is provided, the existing V0.1-V0.6 behavior is
unchanged.

Current safe points:

- before turn start
- before step start
- before LLM call
- before tool call
- before DurableToolExecutor execution
- after DurableToolExecutor execution

The Durable Tool WAL boundary remains owned by `DurableToolExecutor`. The loop
safe points wrap the durable executor call without modifying WAL schema or
authorization semantics.

## WAITING Semantics

The loop moves the process into `WAITING` while awaiting:

- Context VM working set preparation
- Context reclaim
- LLM generation
- Tool execution

When the awaitable completes, the process is woken back to `READY` and
dispatched back to `RUNNING` so the current cooperative turn can continue.

This models cooperative waiting without introducing concurrent execution,
preemption, or IPC.

## Pause And Cancellation

Pause and cancellation are cooperative.

- `request_pause()` records intent.
- `pause()` pauses a non-running process immediately or records intent for a
  running process.
- `resume()` returns PAUSED to READY.
- `cancel()` records cancellation intent.
- `safe_point()` converts a pending cancellation into EXITED with
  `exit_status="cancelled"`.

The LLM and tools do not decide whether a process is paused or cancelled. They
only run inside scheduler-controlled safe points.

## Compatibility

V0.1 Execution:

- Agent loop remains the turn/step driver.
- Scheduler integration is optional.

V0.2 Recovery:

- Session remains the durable journal.
- Scheduler state is reconstructed from PCB/recovery inputs, not from new
  scheduler events.

V0.3 Durable Tool:

- WAL prepare/dispatch/commit semantics are unchanged.
- Scheduler safe points wrap the executor call but do not alter operation ids or
  authorization context.

V0.4 Context VM:

- Context VM remains the owner of context page projection and reclaim policy.
- Scheduler only marks the process WAITING while context work is awaited.

V0.5 Resource Layer:

- ResourceStore and ResourceService boundaries are unchanged.

V0.6 Capability:

- Agent remains the capability principal.
- Process keeps a capability snapshot for runtime accounting but does not become
  an authority principal.

## Limitations

This is the smallest scheduler core needed for V0.7.

Remaining future work:

- persisted process table reconstruction strategy
- scheduler metrics
- time slice accounting
- resource budget enforcement
- host policy hooks for pause/cancel decisions
- V0.8 IPC integration
- multi-process ownership rules
