# V0.8 Phase 2 - Process Tree / Supervision Metadata

Status: implemented for V0.8 Phase 2.

Decision:

```text
V0.8_PHASE2_PROCESS_TREE_COMPLETE
```

## 1. Scope

This phase adds Process Tree and supervision metadata without changing the
Agent capability principal model.

Implemented:

- root Process creation;
- same-Agent child Process creation;
- child-Agent initial Process creation;
- deterministic Process Tree queries;
- Process ownership validation against `AgentRegistry`;
- child exit observation;
- durable `process/created` semantic facts;
- Process Tree reconstruction from Session facts;
- a minimal Scheduler dispatch guard for Session single-writer safety.

Not implemented:

- full `spawn_agent()`;
- Capability Delegation;
- IPC;
- Agent message passing;
- Resource Sharing;
- budget hierarchy;
- retry, restart, fail-fast, or cancellation propagation policy;
- detached children;
- Multi-Agent RuntimeBench.

## 2. Design Freeze References

This implementation follows:

- `docs/architecture/V0.8_MULTI_AGENT_ARCHITECTURE_REVIEW.md`;

Frozen object roles remain unchanged:

```text
Agent   = capability principal
Process = schedulable runtime identity
Session = durable single-writer journal
Scheduler = schedules Processes, not Agents
```

## 3. Process Tree Model

`ProcessControlBlock.parent_process_id` is now the immediate parent Process
relation. Root Processes use `parent_process_id = None`.

`ProcessManager` owns the live Process Table and a deterministic child index.
It intentionally does not introduce a separate `ProcessGraph`,
`ProcessTreeManager`, or `SupervisorRegistry`.

Derived Process Tree queries:

| API | Meaning |
| --- | --- |
| `parent_of(process_id)` | Immediate parent id, or `None` for a root. |
| `children_of(process_id)` | Direct children in creation order. |
| `root_of(process_id)` | Root process id for the tree. |
| `lineage(process_id)` | Root-to-process path. |
| `descendants_of(process_id)` | All descendants in deterministic depth-first creation order. |
| `depth(process_id)` | Root depth is `0`; each child increments by one. |

The Process Tree is forest-compatible: multiple root Processes are legal.

## 4. Agent Tree vs Process Tree

Agent Tree and Process Tree remain independent.

Same-Agent child Process:

```text
Agent A
  Process A1
    Process A2
```

`A2.agent_id == A1.agent_id`. This does not create a new Agent principal and
does not change authority.

Child-Agent Process:

```text
Agent A
  child Agent B

Process A1 (Agent A)
  Process B1 (Agent B)
```

`B1.parent_process_id == A1.process_id`, while
`Agent B.parent_agent_id == Agent A.agent_id`. These are different relations.
The Process relation does not imply capability inheritance.

## 5. ProcessManager Extensions

`ProcessManager` now supports:

- optional `agent_registry` validation;
- `create_process(...)` for root or explicit-parent Process creation;
- `create_child_process(...)` for child Process creation;
- `record_process_created(...)` for durable semantic facts;
- deterministic tree query APIs;
- child exit observation APIs;
- `reconstruct(...)` / `from_sessions(...)` for durable rebuild.

Backward compatibility:

- `ProcessManager()` without an `AgentRegistry` still accepts V0.7-style
  Process creation.
- Root Process creation with `parent_process_id = None` remains the legacy path.
- Existing `ProcessControlBlock.create(...)` remains compatible.

## 6. Parent / Child Semantics

Child Process creation is fail-closed:

- parent id must be non-empty;
- parent Process must already exist in the live Process Table;
- `process_id == parent_process_id` is rejected;
- duplicate Process ids are rejected.

Live creation structurally prevents cycles because children can only point to an
existing parent. Reconstruction validates cycles again from durable facts and
raises `ProcessRegistryCorruptionError` on corruption.

## 7. Session Ownership / Single-Writer Boundary

Process ownership is validated as:

```text
Process.agent_id -> AgentRegistry.get(agent_id)
Process.session_id == owning Agent primary session_id
```

`process/created` must be written to the owning Agent's Session.

The Scheduler now adds one narrow Session writer guard at dispatch:

```text
READY Process
  -> dispatch()
  -> reject if another RUNNING Process has the same session_id
  -> RUNNING
```

This preserves the current single-writer Session boundary without adding a
Session lock manager or changing scheduling policy. The READY queue, WAITING
registry, BLOCKED registry, and current RUNNING state remain runtime-only.

## 8. Supervision Metadata

`parent_process_id` is the default supervisor relation for Phase 2.

`ProcessManager` exposes:

- `exited_children_of(parent_process_id)`;
- `child_exit_statuses(parent_process_id)`.

Child exit observation is a Kernel lifecycle signal, not IPC. It carries no
LLM payload, ResourceHandle transfer, or authority.

Child failure does not automatically exit the parent Process and does not mutate
the parent Session. Retry, restart, ignore, and fail-fast behavior are deferred
to later policy phases.

## 9. Durable Process Creation Fact

This phase adds one durable Session event type:

```text
process/created
```

Payload:

```text
process_id
agent_id
session_id
parent_process_id
creation_id
```

The fact records semantic Process existence and lineage. It does not persist:

- READY queue order;
- current RUNNING Process;
- WAITING or BLOCKED registries;
- scheduler priority aging;
- usage counters;
- Context working sets.

`creation_id` makes duplicate replay idempotent when the exact same fact is
observed more than once. Conflicting creation ids or conflicting payloads are
rejected.

## 10. Reconstruction

`ProcessManager.reconstruct(sessions, agent_registry=...)` scans Session events
for `process/created` facts, validates ownership and parent relations, then
rebuilds a live Process Table.

Reconstruction rules:

- missing owning Agent: corruption;
- Session mismatch with owning Agent: corruption;
- missing parent durable fact: corruption;
- self-parent: corruption;
- cycle: corruption;
- duplicate identical fact by `creation_id`: idempotent;
- duplicate Process identity with different creation fact: corruption.

Reconstructed Processes are live runtime objects. Scheduler admission and queue
state remain runtime decisions after recovery.

## 11. Capability Boundary

Capability authority is unchanged.

Process lineage does not grant authority. A child Process owned by the same
Agent uses the same Agent principal. A Process owned by a child Agent uses the
child Agent principal, which remains deny-by-default unless future delegation
grants explicit narrowed authority.

`CapabilityEvaluator` still evaluates `agent_id`, not `process_id`.

## 12. Error Rules

New scheduler/process tree errors:

| Error | Meaning |
| --- | --- |
| `InvalidProcessParent` | Parent relation is invalid for live Process creation. |
| `ProcessTreeError` | Runtime Process Tree invariant failed. |
| `ProcessRegistryCorruptionError` | Durable Process creation facts cannot be replayed safely. |
| `ProcessSessionConflict` | Dispatch would create concurrent writers for one Session. |

## 14. Limitations

Phase 2 is intentionally only a metadata and reconstruction foundation.

Deferred to later V0.8 phases:

- `spawn_agent()` orchestration;
- capability delegation and grant narrowing;
- IPC channels and message envelopes;
- Resource sharing grants;
- aggregate budget hierarchy;
- child retry/restart/fail-fast policy;
- cancellation propagation;
- Multi-Agent RuntimeBench.
