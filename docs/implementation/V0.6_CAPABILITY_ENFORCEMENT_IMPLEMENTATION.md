# V0.6 Capability Enforcement Implementation

Status: Phase 2 Part 1 implementation.

This change connects the V0.6 Capability Core to the current Kernel boundary.
It intentionally implements only Tool Layer and Resource Layer enforcement.

## Changed Boundaries

| Boundary | Change |
|---|---|
| `AgentControlBlock` | Carries optional structured `CapabilityGrant` values in addition to legacy capability strings. |
| `ToolRegistry.model_schemas()` | Filters model-visible tools through `CapabilityEvaluator`. |
| `ToolRegistry.resolve_for_execution()` | Re-checks tool authorization before handler invocation or durable prepare. |
| `ToolExecutionContext` | Carries the Kernel-built evaluator for Kernel-owned services invoked by tool handlers. |
| `ResourceService.stat()` | Optionally checks `resource.stat` after owner validation. |
| `ResourceService.read()` | Optionally checks `resource.read` after owner validation and before range/store access. |

`ResourceStore` remains a replaceable driver and does not participate in
authorization.

## Tool Compatibility

Legacy tool authorization is preserved.

Existing declarations such as:

```text
required_capability = "math.add"
```

are still compiled into:

```text
action: tool.execute
resource: tool://math.add
```

Structured tool requirements can now be declared with:

```text
required_action = "tool.execute"
required_resource = "tool://math.add"
```

The LLM only receives schemas that pass this check. Execution repeats the same
check, so an unadvertised tool call is still denied at the syscall boundary.

## Resource Compatibility

`ResourceService` keeps the V0.5 owner check as the first authority gate. When
a `CapabilityEvaluator` is supplied, the service then evaluates:

```text
stat -> action: resource.stat
read -> action: resource.read
resource: artifact://<resource_id>
```

The current resource scope is the existing opaque artifact URI. This avoids
introducing a full namespace implementation in Phase 2 Part 1.

For legacy compatibility, an agent with the old `resource.read` capability is
adapted to:

```text
tool.execute on tool://resource.read
resource.read on artifact://**
resource.stat on artifact://**
```

The owner check still prevents cross-owner access.

## WAL Compatibility

Durable tool execution still resolves and authorizes before `TOOL_PREPARE`.
The WAL schema is unchanged:

```text
capability check
WAL prepare
dispatch
commit or abort
```

Read-only tools receive the same evaluator in their `ToolExecutionContext`, so
resource tools can call `ResourceService` without moving authorization into the
tool implementation.

## Not Implemented

This phase does not implement:

- delegation;
- revocation;
- namespace resolution;
- RBAC;
- IAM;
- policy engine;
- user/group models;
- audit events;
- constraint evaluation;
- durable authorization event recording;
- resource mutation authorization beyond read/stat.

`constraints` remain immutable metadata on `CapabilityGrant` and are not
evaluated yet.

## Phase 2 Follow-Up

The next implementation slice should decide whether authorization decisions need
durable audit events and whether resource scopes should remain opaque handle
URIs or move to a dedicated namespace resolver.
