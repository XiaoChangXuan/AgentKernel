# V0.8 Phase 3 - Capability Delegation Core

Status: implemented for V0.8 Phase 3.

Decision:

```text
V0.8_PHASE3_CAPABILITY_DELEGATION_COMPLETE
```

## 1. Scope

This phase adds the minimum Kernel-owned delegation primitive needed for child
Agents to receive explicit narrowed authority.

Implemented:

- `DelegateCapabilityRequest`;
- `DelegationDecision`;
- `DelegationProvenance`;
- `CapabilityDelegator`;
- stable grant fingerprints;
- stable delegation ids;
- safe resource-scope canonicalization and narrowing checks;
- constraint narrowing for known upper-bound and expiry-like constraints;
- direct parent-to-child delegation through `AgentRegistry`;
- deny-by-default child Agent authority;
- durable `capability/delegated` facts stored in the child Agent Session;
- deterministic replay of single-hop and multi-hop delegation chains;
- replay idempotency and fail-closed conflict detection;
- Tool and Durable Tool authorization through the existing
  `CapabilityEvaluator` after delegated grants are installed.

Not implemented:

- IPC;
- Resource Sharing;
- full `spawn_agent()`;
- revocation engine;
- Namespace framework;
- RBAC, IAM, roles, or policy engine;
- budget hierarchy;
- RuntimeBench B8 / Multi-Agent benchmark.

## 2. Security Invariant

The implemented invariant is:

```text
child effective authority
<= delegated authority
<= parent current effective authority
```

The LLM may propose actions, but it cannot create authority. A delegation
request is only a request. The Kernel validates it against the current parent
Agent authority and installs a normal `CapabilityGrant` for the child only on
success.

Agent remains the capability principal. Process lineage and Process Tree
metadata do not grant authority.

## 3. Delegation Object Model

`DelegateCapabilityRequest` contains:

- `parent_agent_id`;
- `child_agent_id`;
- `action`;
- `resource_scope`;
- `constraints`;
- optional `parent_grant_fingerprint`;
- optional `delegation_id`;
- optional `correlation_id`;
- optional `expires_at`;
- optional `max_depth`.

`DelegationDecision` contains:

- `allowed`;
- `reason`;
- optional `delegation_id`;
- optional delegated `CapabilityGrant`;
- optional `DelegationProvenance`.

Normal denial is represented as `DelegationDecision(allowed=False, reason=...)`.
Corrupted durable facts raise `AgentRegistryCorruptionError` during replay.

The delegated authority is represented as:

```python
CapabilityGrant(
    subject=child_agent_id,
    action=request.action,
    resource_scope=request.resource_scope,
    constraints=request.constraints,
)
```

No parallel child permission, role, ACL, or worker permission model was added.

## 4. Parent Effective Authority

Delegation checks the parent Agent's current effective authority:

- structured `capability_grants`;
- legacy capability strings converted to compatibility grants.

Host/root grants are not persisted as a global grant store. After restart, the
Host supplies current root authority through
`AgentRegistry.reconstruct(..., current_capability_grants=...)`, then durable
delegations are replayed against that current authority.

## 5. Action Narrowing

Action matching remains exact.

Allowed:

```text
parent action = resource.read
child action  = resource.read
```

Denied:

```text
parent action = resource.read
child action  = resource.write
```

No wildcard or action hierarchy such as `resource.*` was introduced.

## 6. Resource Scope Narrowing

`is_scope_narrower_or_equal(child_scope, parent_scope)` performs the scope
subset check. It does not use plain `startswith()`.

Allowed:

```text
parent artifact://project-a/**
child  artifact://project-a/logs/**
```

Denied:

```text
parent artifact://project-a/logs/**
child  artifact://project-a/**
```

The minimal scope grammar canonicalizes scheme case, rejects encoded paths,
rejects duplicate or trailing slashes, rejects `.` and `..`, and only accepts
`**` as a complete final path segment.

If a scope cannot be safely canonicalized, delegation fails closed.

## 7. Constraint Narrowing

Constraints are stored as canonical JSON mappings.

Rules:

- child constraints must retain every parent constraint;
- known numeric upper bounds such as `max_bytes` or `max_*` may be smaller;
- known expiry-like constraints may be earlier;
- unknown constraints may be equal;
- unknown changed or added constraints are denied.

This phase does not interpret arbitrary strings, enums, booleans, or nested
business policy values as stricter or looser.

## 8. Bounding Set

The existing `capability_bounding_set` remains the legacy capability-string
bound. `AgentControlBlock` still rejects legacy effective capabilities that are
outside that set.

Structured `CapabilityGrant` values are Host-provided current authority. This
phase does not introduce a structured bounding-set schema. The pure
`CapabilityDelegator` supports optional `parent_bounding_grants` for callers
that already have a structured bound, and it checks action, scope, and
constraints against that bound.

## 9. Provenance and Fingerprints

Each successful delegation records:

- `delegation_id`;
- `parent_agent_id`;
- `child_agent_id`;
- `parent_grant_fingerprint`;
- `action`;
- `resource_scope`;
- `constraints`;
- `correlation_id`;
- `delegation_depth`;
- `parent_delegation_id`;
- optional `expires_at`.

`grant_fingerprint(grant)` uses canonical grant payload JSON with sorted keys
and SHA-256:

```text
sha256:<hex digest>
```

`stable_delegation_id(...)` hashes the canonical delegation identity and returns:

```text
delegation_<32 hex chars>
```

It is deterministic across constraint insertion order and canonical-equivalent
scope spelling.

## 10. Multi-Hop Delegation

Multi-hop delegation is supported by replaying durable facts in deterministic
`(delegation_depth, delegation_id)` order.

Example:

```text
A owns  artifact://project-a/**
A -> B  artifact://project-a/logs/**
B -> C  artifact://project-a/logs/day-1/**
```

The B to C delegation only succeeds after the A to B grant has been activated.
A widening attempt such as B to C for `artifact://project-a/**` is denied.

## 11. Durable Event

Successful delegation appends:

```text
capability/delegated
```

The payload contains the provenance fields plus canonical `child_grant`.

The authoritative durable owner for the fact is the child Agent Session. The
parent id, parent grant fingerprint, and correlation id provide audit linkage
without introducing cross-Session atomic writes.

Denials are not persisted as durable truth in this phase. They remain runtime
`DelegationDecision` results.

## 12. Recovery Activation

`Session.load()` validates `capability/delegated` shape and canonical payload
through recovery replay. `AgentRegistry.reconstruct()` rebuilds Agents from
`agent/created`, installs Host-supplied current grants, then replays delegation
facts.

Replay rules:

- duplicate `delegation_id` with the same canonical payload is idempotent;
- duplicate `delegation_id` with a different payload is corruption;
- the same child grant with conflicting provenance is corruption;
- durable facts remain history even when current parent authority no longer
  covers them;
- future child authority is only activated when current parent authority covers
  the durable delegated grant.

## 13. Future Revocation Compatibility

This phase does not implement revocation. The durable provenance includes stable
delegation ids, parent grant fingerprints, parent delegation linkage, depth, and
optional lease metadata so a future revocation engine can invalidate current
authority without deleting historical facts.

`expires_at` is metadata only in this phase. Expiry inside `constraints` can be
used for narrowing comparison, but no wall-clock expiry enforcement is added.

## 14. Tool and Durable Tool Enforcement

After a delegated grant is installed, runtime authorization still goes through
the existing `CapabilityEvaluator`.

Tool behavior:

- `ToolRegistry.model_schemas()` shows only tools authorized by the child
  Agent's current grants;
- `ToolRegistry.resolve_for_execution()` checks again at execution time;
- a forged hidden tool call is denied.

Durable Tool behavior:

- an unauthorized child mutation is denied before durable prepare;
- after explicit delegation, the existing Durable Tool authorization boundary
  handles prepare and dispatch;
- `DurableToolExecutor` did not require Phase 3 changes.

## 15. Tests

`tests/test_capability_delegation.py` covers:

- direct parent-child delegation;
- unknown parent and child denial;
- non-parent delegation denial;
- child deny-by-default;
- no parent grant copying;
- action and scope narrowing;
- scope normalization fail-closed cases;
- constraint narrowing;
- legacy bounding-set behavior and structured delegator bounds;
- stable fingerprints and idempotent delegation ids;
- multi-hop narrowing and widening rejection;
- Tool schema visibility and forged execution denial;
- Durable Tool unauthorized child denial and authorized delegated mutation;
- Process lineage not granting authority;
- JSONL persistence and restart activation;
- replay idempotency and corrupt replay rejection;
- deterministic multi-hop reconstruction.

Regression suites also cover Agent Registry, Process Tree, and V0.6 capability
enforcement.

## 16. Limitations

- No namespace framework.
- No Resource Sharing.
- No IPC or Agent message passing.
- No revocation engine.
- No policy engine or approval workflow.
- No structured `capability_bounding_set` schema.
- No wall-clock expiry enforcement.
- No Multi-Agent RuntimeBench claim.

## 17. Decision

V0.8 Phase 3 is complete for the delegated CapabilityGrant core. The next phase
may build on this by adding explicit resource sharing or IPC, but those are not
part of this implementation.
