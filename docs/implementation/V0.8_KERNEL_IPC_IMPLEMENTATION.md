# V0.8 Phase 4 - Kernel IPC Channels

## 1. Scope

V0.8 Phase 4 adds a Kernel-owned local IPC mechanism for Agent/Process
communication. It provides point-to-point channels, durable message envelopes,
explicit delivery state, bounded backpressure, replay reconstruction, and
Session-local audit facts.

This phase is intentionally narrow. IPC carries structured data only. It does
not transfer authority, resource ownership, capability grants, namespace access,
or tool execution permission.

## 2. Frozen IPC Invariants

- LLM output and message payloads are untrusted data.
- KernelIPC owns channel identity, participant validation, message identity,
  ordering, durability, delivery state, and bounds enforcement.
- Agent remains the capability principal.
- Process remains the schedulable runtime identity.
- Session remains a per-Agent durable journal, not a shared multi-Agent
  transcript.
- IPC persistence is the durable source of truth for cross-Agent envelope state.
- Session `ipc/send`, `ipc/receive`, and `ipc/ack` events are local audit facts.

## 3. Object Model

The implementation lives in `agentkernel/ipc.py`.

Primary objects:

- `IPCChannel`: stable point-to-point channel metadata.
- `IPCMessageEnvelope`: durable data envelope with sender, receiver, sequence,
  payload, resource references, and delivery state.
- `IPCMessageState`: `PENDING`, `DELIVERED`, `ACKED`.
- `IPCRecordType`: append-only IPC persistence vocabulary.
- `IPCPersistence`: minimal durable record protocol.
- `InMemoryIPCPersistence`: deterministic in-memory store for tests.
- `JsonlIPCPersistence`: append-only JSONL store.
- `KernelIPC`: Kernel service implementing create, send, receive, ack, and
  replay reconstruction.

## 4. Channel Model

Phase 4 implements explicit point-to-point local channels:

- one sender Agent
- one receiver Agent
- optional receiver Process constraint
- bounded live message count
- bounded live payload bytes

`channel_id` may be supplied by the caller or generated by the Kernel. The id is
persisted as a channel creation fact and must replay without changing meaning.

The channel is owned by the Kernel. It does not belong to the sender or receiver.

## 5. Participant Identity

Send calls provide `sender_process_id`, not a trusted `sender_agent_id`. KernelIPC
derives the sender Agent from the Process table and verifies that it matches the
channel sender.

Receive and ack calls verify the receiver Agent. If the channel is
process-targeted, they also verify the receiver Process and its owning Agent.

Payload fields named `sender_agent_id`, `grant`, `capability`, or similar names
are not interpreted as authority. They remain ordinary JSON data.

## 6. Message Envelope

`IPCMessageEnvelope` records:

- `message_id`
- `channel_id`
- `sender_agent_id`
- `sender_process_id`
- `receiver_agent_id`
- optional `receiver_process_id`
- JSON-compatible `payload`
- string `resource_refs`
- per-channel `sequence`
- `correlation_id`
- `created_at`
- `delivery_state`
- deterministic `payload_bytes`
- `delivery_attempts`
- optional `last_delivered_at`
- optional `acked_at`

`message_id` is stable and unique. Reusing the same id with the same canonical
message data is idempotent. Reusing the same id with different data is rejected
as a message conflict.

`correlation_id` is for request-response or workflow correlation only. It is not
an authority id.

## 7. Data vs Authority Boundary

IPC can carry:

- JSON domain data
- strings that look like resource references
- strings that look like capability names
- grant-like JSON objects

IPC cannot grant:

- tool execution authority
- resource read/stat authority
- ResourceHandle ownership
- delegated capability
- namespace access

The receiver must still pass the existing ResourceService and CapabilityEvaluator
checks before accessing resources or executing tools.

## 8. Delivery State Machine

The durable message state machine is:

```text
PENDING -> DELIVERED -> ACKED
```

`PENDING` means the send envelope is durable and unacked.

`DELIVERED` means the receiver has observed the envelope at least once, but has
not acknowledged completion.

`ACKED` means the receiver has durably acknowledged the envelope. KernelIPC no
longer actively delivers acked messages.

Invalid transitions, such as ack before delivery, are rejected during live
operation and replay.

## 9. Durable IPC Persistence

IPC persistence is append-only. Record types are:

- `ipc/channel_created`
- `ipc/message_sent`
- `ipc/message_delivered`
- `ipc/message_acked`

KernelIPC reconstructs channels, message ordering, delivery attempts, ack state,
and live queue occupancy from these records. It does not persist Python queues,
Process objects, Scheduler objects, or Session pointers.

## 10. Send Semantics

Send performs:

1. Channel lookup.
2. Sender Process lookup.
3. Sender Agent derivation from Process.
4. Payload and resource reference validation.
5. Duplicate message id check.
6. Live channel bounds check.
7. Envelope creation with next channel sequence.
8. Append durable `message_sent`.
9. Update live runtime state.
10. Append sender Session `ipc/send` audit fact if a session is bound.

Send becomes durable when `message_sent` is appended to IPC persistence.

## 11. Receive Semantics

Receive performs receiver validation and returns the first unacked message in
channel order. It appends `message_delivered`, increments `delivery_attempts`,
updates the envelope to `DELIVERED`, and appends receiver Session `ipc/receive`
audit if a session is bound.

Delivery is observable, not a business commit.

## 12. Ack Semantics

Ack requires receiver validation and a delivered message. It appends
`message_acked`, updates the envelope to `ACKED`, appends receiver Session
`ipc/ack` audit if a session is bound, and releases IPC backpressure for that
channel.

Receiver Session `ipc/receive` is not equivalent to ack. The IPC envelope is the
durable source of ack truth.

## 13. Delivery Guarantee

Phase 4 provides at-least-once observable delivery until ack.

It does not claim exactly-once delivery. Receivers must use `message_id` as the
foundation for de-duplication if their policy treats repeated observation as a
duplicate.

## 14. Ordering

Phase 4 guarantees per-channel observable FIFO for the implemented
point-to-point channel. Later messages are not delivered ahead of earlier
unacked messages.

No global total order is claimed.

## 15. Backpressure

Each channel has:

- `max_messages`
- `max_bytes`

Only unacked live messages count against occupancy. Byte accounting uses
canonical JSON encoding of payload and resource references via
`canonical_message_bytes`.

When a channel is full, send fails with `IPCBackpressureError`. If the sender
Process is currently running under a bound scheduler, KernelIPC moves it to
`BLOCKED` with an `ipc_backpressure:<channel>:<reason>` blocked reason.

Ack releases live occupancy. KernelIPC then unblocks sender Processes blocked on
that channel using the scheduler's existing unblock mechanism.

## 16. Session Audit Facts

KernelIPC may append Session-local audit events:

- sender Session: `ipc/send`
- receiver Session: `ipc/receive`
- receiver Session: `ipc/ack`

The audit payload contains identity, sequence, and correlation fields. It does
not duplicate the full message payload.

Recovery accepts these facts outside any active turn or step. They do not mutate
turn, step, tool, durable operation, compaction, Agent tree, or Process tree
recovery state.

## 17. Recovery

`KernelIPC.reconstruct(...)` rebuilds live IPC state from `IPCPersistence`.

Crash behavior:

- after send: message reappears as `PENDING`
- after delivery before ack: message reappears as `DELIVERED` and may be
  delivered again with a higher attempt count
- after ack: message remains `ACKED` and is not redelivered

Cross-journal windows are explicit. IPC persistence is envelope truth. Session
audit facts are evidence for a local Agent journal, not queue state.

## 18. Compatibility

Phase 4 does not modify:

- Capability authority or delegation semantics
- ResourceService authorization
- DurableToolExecutor or WAL schema
- Context VM ownership
- Process tree parent relation
- Scheduler priority, budget, pause, or cancellation semantics

The only Session vocabulary change is adding local IPC audit event types.

## 19. Limitations

This phase does not implement:

- Resource Sharing
- `ResourceShareGrant`
- ownership transfer
- implicit ResourceHandle permission
- full confused-deputy mitigation
- budget hierarchy
- parent aggregate budget
- cancellation propagation
- retry or restart supervision policy
- full multi-Agent recovery integration
- namespace, RBAC, IAM, or revocation
- memory
- distributed IPC or remote transport
- broker semantics
- exactly-once delivery
- Multi-Agent RuntimeBench or B8

## 20. Tests

`tests/test_kernel_ipc.py` covers:

- channel creation and participant validation
- sender Agent derivation from Process
- forged payload sender fields remaining data
- receiver validation for receive and ack
- JSON payload validation
- resource references remaining inert
- grant-like payloads not granting authority
- stable message ids and conflict detection
- PENDING, DELIVERED, ACKED lifecycle
- redelivery before ack
- no redelivery after ack
- same-channel FIFO
- message and byte bounds
- sender BLOCKED on backpressure
- ack unblock behavior
- Session-local IPC audit facts
- replay after send, delivery, and ack
- corrupt transition rejection
- Process tree and capability authority remaining independent
