# V0.8 Phase 5 - Resource Sharing Grants

## 1. Scope

V0.8 Phase 5 adds explicit cross-Agent Resource sharing grants.

The phase implements exact Resource sharing only:

- one durable `resource_id`
- one owner Agent
- one grantee Agent
- a narrow set of read-only Resource actions

It does not implement ownership transfer, namespace sharing, wildcard sharing,
revocation, Resource mutation sharing, RBAC, IAM, or Phase 6 features.

## 2. Security Invariants

The implementation preserves these invariants:

- `ResourceStore` is byte and metadata storage, not an authorization authority.
- `ResourceService` remains the Resource authorization boundary.
- `ResourceHandle` reference != Resource authority.
- IPC `resource_refs` are data, not authority.
- `CapabilityGrant` is action and scope authority, not owner consent.
- `ResourceShareGrant` is explicit owner consent, not ownership transfer.
- Agent is the authorization principal.
- Process is runtime attribution only.
- Agent lineage, Process lineage, and Capability delegation do not imply Resource
  sharing.

## 3. Resource Ownership Model

Resource ownership continues to come from `ResourceMetadata.owner`.

`ResourceOwner` contains:

- `agent_id`
- `session_id`

Only the Agent recorded as the Resource owner can create a share for that
Resource. The share fact must be recorded in the owner Session. Sharing does not
mutate `ResourceMetadata.owner`.

## 4. ResourceShareGrant

`ResourceShareGrant` is an immutable owner-consent fact.

Shape:

```text
share_id
resource_id
owner_agent_id
grantee_agent_id
allowed_actions
created_at
correlation_id
expires_at
```

The grant stores durable authorization metadata only. It does not contain
Resource bytes, handle ids, filesystem paths, Process state, Capability
snapshots, or store-specific data.

## 5. Share Request / Decision

`ResourceShareRequest` is the Kernel request to create a share:

```text
owner_agent_id
grantee_agent_id
resource_id
allowed_actions
share_id
correlation_id
expires_at
```

`ResourceShareDecision` returns:

```text
allowed
reason
grant
```

Expected deny cases return a denied decision. Durable replay corruption raises
`ResourceShareCorruptionError`.

## 6. Owner Validation

Share creation validates:

- Resource exists.
- Owner Agent exists when an Agent registry is provided.
- Grantee Agent exists when an Agent registry is provided.
- Request owner matches `ResourceMetadata.owner.agent_id`.
- Recording Session matches `ResourceMetadata.owner.session_id`.
- Owner and grantee are different Agents.

Self-share is denied with `self_share_denied`.

## 7. Exact Resource Sharing

Phase 5 binds a share to the exact `resource_id`.

It does not share:

- a handle id
- an artifact URI pattern
- a directory
- a subtree
- a namespace prefix
- future Resources that might later match a prefix

This keeps Resource sharing focused on owner consent. Capability scope matching
remains the job of `CapabilityEvaluator`.

## 8. Allowed Actions

The only shareable actions are:

- `resource.read`
- `resource.stat`

Unknown actions are denied at share creation and never match at access time.
Write, delete, transfer, publish, owner mutation, and wildcard actions are not
implemented.

## 9. Capability + Share Composition

The core rule is:

```text
Cross-Agent Resource Access
=
Capability Authorization
AND
Active Resource Share
```

Capability answers:

```text
May this Agent perform this action on this Resource scope?
```

Resource sharing answers:

```text
Did the Resource owner consent to this Agent accessing this exact Resource?
```

Both must be true for cross-Agent read or stat.

## 10. ResourceService Enforcement

`ResourceService.stat()` and `ResourceService.read()` resolve the Resource,
then authorize the caller.

For owner access:

- existing V0.5 behavior is preserved
- owner access without a capability evaluator remains compatible
- owner access with a capability evaluator still respects capability denial

For cross-Agent access:

- missing capability denies
- missing share denies
- capability-only denies
- share-only denies
- capability plus matching share allows

`ResourceService.share()` is the narrow creation API for owner consent. It
records the durable `resource/shared` fact through the owner Session.

## 11. ResourceStore Boundary

`ResourceStore` and `LocalResourceStore` remain storage-only. They do not accept
Agent ids, Process ids, Capability evaluators, share ids, or authorization
objects.

Authorization is performed above the store by `ResourceService`.

## 12. Handle != Authority

`ResourceHandle` and `artifact://res_*` URIs remain opaque references. Possessing
a handle string does not grant access.

A grantee that receives a Resource URI through IPC, logs, user input, or copied
text still needs both:

- Resource capability for the requested action
- an active exact Resource share

## 13. IPC != Share

Kernel IPC remains independent from Resource sharing.

Sending `resource_refs` over IPC does not create a share. Sending a payload that
looks like a `ResourceShareGrant` does not create a share. The only durable share
fact is `resource/shared`, recorded by the Resource sharing path.

## 14. Delegation != Share

Capability delegation does not create owner consent.

A parent Agent may delegate `resource.read` capability to a child Agent, but that
child still cannot read another Agent's Resource until the Resource owner
creates an explicit share for the exact Resource.

## 15. No Re-share

Grantees cannot re-share.

Only the Resource owner can create `ResourceShareGrant` facts. A grantee with a
capability and an active share remains a grantee; it does not become the owner
and cannot authorize a third Agent.

## 16. Durable resource/shared Fact

Share creation records one Session event:

```text
resource/shared
```

Canonical payload:

```json
{
  "share_id": "share_...",
  "resource_id": "res_...",
  "owner_agent_id": "agent-owner",
  "grantee_agent_id": "agent-grantee",
  "allowed_actions": ["resource.read", "resource.stat"],
  "created_at": 100.0,
  "correlation_id": "share_...",
  "expires_at": null
}
```

The owner Session is authoritative for the share fact.

## 17. Recovery

`ResourceShareRegistry.reconstruct()` rebuilds active share state by replaying
durable `resource/shared` events from Sessions.

When a Resource lookup is provided, replay validates that:

- the Resource exists
- Resource metadata owner matches `owner_agent_id`
- the share fact was stored in the owner Session

After restart, cross-Agent access still requires the same dual authorization
rule: capability plus active share.

## 18. Replay / Corruption Rules

Replay is idempotent for the same canonical share fact.

Replay rejects:

- malformed `resource/shared` payloads
- non-canonical payloads
- one `share_id` reused for different grant content
- one `share_id` appearing across multiple Sessions
- missing owner or grantee Agent when an Agent registry is provided
- missing Resource when a Resource lookup is provided
- owner mismatch between share fact and Resource metadata
- owner Session mismatch

## 19. Confused Deputy Boundary

Phase 5 prevents the most direct ownership-based re-share path:

```text
A owns X
A shares X to B
B cannot share X to C
```

Full data-flow control and full confused-deputy mitigation remain deferred.

## 20. Backward Compatibility

V0.5 Resource owner access remains compatible.

Existing Resources do not need share metadata. Without a configured
`ResourceShareRegistry`, cross-Agent access fails closed.

## 21. Tests

`tests/test_resource_sharing.py` covers:

- canonical grant payload round trip
- owner-created exact share
- ownership unchanged
- invalid owner, unknown Resource, unknown grantee, self-share, unknown action
- capability-only denial
- share-only denial
- capability plus share allow
- stat/read action narrowness
- IPC Resource reference is inert
- grant-like IPC payload is inert
- Agent lineage does not share
- Process lineage does not share
- Capability delegation does not share
- no re-share by grantee
- replay idempotency
- replay conflict detection
- restart reconstruction
- old V0.5 owner compatibility
- fail-closed cross-Agent access
- `LocalResourceStore.read` remains storage-only

## 22. Limitations

Phase 5 does not implement:

- ownership transfer
- Resource write/delete sharing
- general `ResourceScope` sharing
- namespace sharing
- wildcard Resource sharing
- share revocation
- wall-clock expiry enforcement
- re-share or delegation of share
- full confused-deputy mitigation
- data-flow control
- IPC response authorization
- budget hierarchy
- cancellation propagation
- retry/restart supervision policy
- integrated Multi-Agent recovery
- Multi-Agent RuntimeBench

`expires_at` is reserved metadata in this phase. It is persisted and replayed,
but not enforced against wall-clock time.

## 23. Deferred to Phase 6+

Future phases may add:

- `resource/share_revoked` facts keyed by `share_id`
- Resource group or namespace sharing after a separate namespace design
- integrated Multi-Agent recovery semantics
- budget hierarchy and cancellation propagation
- broader confused-deputy controls

Historical `resource/shared` facts remain durable facts. Future authorization
should evaluate current active share state rather than deleting history.
