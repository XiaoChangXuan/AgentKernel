# V0.8 Phase 6 - Budget / Fault / Cancellation Isolation

## 1. Scope

V0.8 Phase 6 adds runtime isolation primitives for budget enforcement, child fault observation, and structured cancellation. The implementation stays inside the existing Process runtime boundary and does not redesign Capability, IPC, Resource Sharing, Durable Tool WAL, Agent identity, or Process Tree semantics.

This phase is a Kernel mechanism layer. Host policy may choose budgets, retries, restarts, fail-fast behavior, or budget increases, but the Kernel only validates limits, blocks at cooperative safe points, records runtime fault observations, and propagates cancellation over the Process tree.

## 2. Frozen Runtime Invariants

- Agent = capability principal.
- Process = schedulable runtime identity.
- Session = durable truth.
- Scheduler = Kernel mechanism, not Host policy.
- Agent Tree != Process Tree.
- Process Tree = supervision and cancellation lifetime relation.
- Runtime accounting = observation and enforcement input, not billing truth.
- Cancellation != rollback.
- Cancellation != revocation.
- Durable Tool WAL still owns reconciliation after dispatch.

## 3. Existing V0.7 Runtime Accounting

Phase 6 extends the V0.7 `UsageCollector` instead of adding a second accounting subsystem. The existing per-process snapshot remains `ProcessUsageSnapshot` with token usage, model cost, tool calls, resource reads, resource bytes, and wall time.

The collector now also supports aggregate views:

- `usage_for_agent(agent_id, processes)` aggregates live process usage by `ProcessControlBlock.agent_id`.
- `host_usage(processes)` aggregates live process usage across the current Kernel runtime.
- `aggregate_usage_snapshots(...)` provides deterministic aggregation for snapshots.

These counters are runtime-only. They are not persisted as a usage ledger and are not reconstructed as billing truth during recovery.

## 4. Budget Hierarchy

The runtime budget hierarchy is:

```text
Host
  -> Agent
      -> Process
```

The hierarchy is enforced in two ways:

- explicit child ceilings are validated against their parent ceiling where both sides define a local limit;
- aggregate usage is checked at cooperative safe points for Process, Agent, and Host scopes.

`None` means no local limit. It does not override a parent limit. A Process budget with `max_token_usage=None` can still be blocked by its Agent aggregate budget or the Host budget.

## 5. Host Budget

`HostBudget` represents a runtime ceiling for the current Kernel host process. It supports the dimensions already observable by the runtime:

- `max_token_usage`
- `max_model_cost`
- `max_total_tool_calls`
- `max_resource_reads`
- `max_resource_bytes`
- `max_wall_time_seconds`

`HostBudget` is not an Agent, account, Capability, IAM object, cgroup, or billing ledger.

## 6. Agent Aggregate Budget

Agent aggregate budget uses the existing `AgentBudget` shape. The Scheduler records Host-supplied Agent budgets and also remembers an Agent's own budget when creating processes.

Agent usage aggregation is by `ProcessControlBlock.agent_id`. It is not calculated from Process Tree descendants. If process `B1` is a child process of `A1` but `B1.agent_id == "agent-b"`, its usage is charged to Agent B, not Agent A.

When Agent aggregate usage exceeds its budget, the currently checked Process is moved to `BLOCKED` at the safe point. The Kernel does not kill a random process, retry work, or reset counters.

Blocked reason format:

```text
budget:agent:<agent_id>:<dimension>
```

## 7. Process Budget

Process-local budget also uses `AgentBudget` as the existing budget limit container. `ProcessControlBlock.create(...)` and `ProcessManager.create_process(...)` now accept an optional Process budget; if omitted, the Agent budget remains the default.

Explicit Process ceilings are validated against the owning Agent ceiling. If a Process limit is larger than a finite Agent limit for the same dimension, the runtime rejects creation or budget update with `ProcessTreeError`.

Blocked reason format:

```text
budget:process:<process_id>:<dimension>
```

Budget exhaustion blocks the Process. It is not treated as Process failure and does not set an exit status.

## 8. Usage Attribution

Runtime usage is attributed by Process id for local enforcement and by Agent id for aggregate Agent enforcement. Host usage aggregates all live processes.

This preserves the Phase 6 invariant:

```text
Process Tree supervision lineage != Agent accounting principal
```

The Process Tree does not define budget ownership. The Agent Tree also does not create budget inheritance in Phase 6.

## 9. Runtime Accounting != Ledger

Runtime accounting remains an in-memory observation mechanism. `UsageCollector.reset_process(...)` exists for Host-controlled runtime recovery and tests, but it does not delete durable Session facts or Durable Tool WAL facts.

Phase 6 does not add:

- persistent usage ledger
- billing database
- monetary invoice semantics
- recovery reconstruction of usage counters

## 10. Enforcement Safe Points

Budget, pause, and cancellation checks remain cooperative. The Scheduler safe point order is:

1. cancellation request
2. pause request
3. budget check

No Python thread interruption, async exception injection, signal kill, or OS preemption is introduced.

The existing safe point names remain the enforcement boundary:

- `turn.before`
- `step.before`
- `llm.before`
- `llm.after`
- `tool.before`
- `tool.after`
- `durable_dispatch.before`
- `durable_dispatch.after`

## 11. Budget Blocking

`UsageLimitExceeded` now records:

- `scope`: `process`, `agent`, or `host`
- `subject`: Process id for Process scope, Agent id for Agent scope, and `None` for Host scope
- `limit`, `usage`, and `maximum`

The Scheduler formats blocked reasons as:

```text
budget:process:<process_id>:<dimension>
budget:agent:<agent_id>:<dimension>
budget:host:<dimension>
```

When Host aggregate usage exceeds the Host budget, the checked Process is blocked. The Kernel does not terminate all processes or choose a business policy.

## 12. Budget Update / Unblock

The Scheduler exposes mechanism-level operations:

- `update_host_budget(...)`
- `update_agent_budget(...)`
- `update_process_budget(...)`
- `reset_usage(process_id)`
- existing `unblock(process_id)`

These operations are mechanisms. The authority to approve a budget increase, reset usage, or unblock a process belongs to Host policy.

## 13. Fault Model

Phase 6 distinguishes normal exit, cancellation, and failure using existing Process exit state plus runtime fault notification.

`ProcessFaultNotification` is a runtime-only observation containing:

- `process_id`
- `agent_id`
- `parent_process_id`
- `reason`
- `exit_status`

The Process is moved to `EXITED` with an exit status such as `failed:<reason>`.

## 14. Child Fault Isolation

`CooperativeScheduler.record_process_fault(...)` records a child Process fault without mutating the parent or siblings. A parent can observe direct child failures through `child_faults_of(parent_process_id)`.

Child fault != parent fault. Sibling processes remain schedulable unless Host policy separately chooses to cancel or block them.

## 15. Supervision Notification

Fault notifications are held by the Scheduler as runtime observations. They are not a retry engine, restart engine, fail-fast policy, or durable workflow state.

Phase 6 intentionally does not implement automatic retry, automatic restart, automatic fail-fast, or detached child lifetime policy.

## 16. Mechanism vs Fault Policy

Kernel mechanism:

- classify a reported fault as a Process exit observation;
- preserve parent and sibling state;
- expose supervisor-visible notification;
- keep scheduling data structures consistent.

Host policy:

- decide whether to retry;
- decide whether to restart;
- decide whether to cancel a Process subtree;
- decide whether a parent should fail.

## 17. Structured Cancellation

`ProcessControlBlock` now carries `cancel_reason`. `request_cancel(reason)` is sticky and idempotent for exited processes.

`CooperativeScheduler.request_cancel_subtree(process_id, reason)` propagates cancellation through Process Tree descendants only. It does not follow Agent Tree ownership and does not cancel unrelated processes from the same Agent.

RUNNING processes observe cancellation at the next safe point. Non-running descendants are moved to `EXITED` immediately so cancellation does not strand `CREATED`, `READY`, `WAITING`, `BLOCKED`, or `PAUSED` processes.

## 18. Process Tree Propagation

Cancellation traversal is deterministic:

```text
root process
  then descendants in ProcessManager descendant order
```

Cross-Agent child Processes are cancelled when they are Process Tree descendants. This is a Process lifetime mechanism, not an Agent authority mutation.

## 19. Cancellation Safe Points

At a safe point, a cancelled RUNNING process exits with the stored cancellation reason and raises `ProcessCancelled`. The exception exposes:

- `process_id`
- `safe_point`
- `reason`

Cancellation is cooperative. Code between safe points is not preempted.

## 20. WAITING / BLOCKED / PAUSED Cancellation

Structured cancellation immediately exits non-running subtree members, including:

- WAITING
- BLOCKED
- PAUSED
- READY
- CREATED

This keeps a cancelled subtree from remaining stuck in scheduler registries.

## 21. Durable Fact Preservation

Cancellation does not delete Session events or Durable Tool WAL facts. A Session remains the durable truth, while Process cancellation is a runtime lifecycle fact.

Cancel before durable dispatch can prevent a side effect when the safe point is reached before dispatch. Cancel after prepare preserves the prepared WAL fact. Cancel after dispatch preserves the dispatch fact and keeps reconciliation required.

## 22. Cancellation + IPC

Phase 6 does not change `KernelIPC`. Cancellation does not delete IPC durable messages or change channel authority. Existing IPC envelopes remain retrievable after a sender Process is cancelled.

IPC cancellation protocols, distributed cancellation, and multi-Agent runtime recovery are deferred.

## 23. Cancellation + Capability

Phase 6 does not change Capability semantics. Cancellation does not revoke an Agent's authority, Capability grants, or a Process capability snapshot.

Capability remains Agent-owned. Budget, fault, and cancellation are runtime controls, not authorization controls.

## 24. Cancellation + Resource Sharing

Phase 6 does not change `ResourceShareGrant` semantics. Cancellation does not revoke resource shares, mutate Resource ownership, or make `ResourceStore` an authorization boundary.

Resource Sharing remains enforced by the Resource Service path defined in V0.8 Phase 5.

## 25. Cancellation + Durable Tool WAL

Durable Tool WAL semantics are preserved:

- no cancellation path deletes `TOOL_PREPARE`;
- no cancellation path deletes `TOOL_DISPATCH`;
- cancel after dispatch still requires reconciliation;
- operation identity and WAL facts remain authoritative for side-effect recovery.

Phase 6 does not redesign `DurableToolExecutor`, operation ids, reconciliation classification, or WAL schema.

## 26. Mandatory Reconciliation

If a durable operation has crossed the external dispatch boundary, cancellation cannot pretend the side effect vanished. Recovery analysis must continue to classify dispatched-but-uncommitted operations as requiring reconciliation.

Budget exhaustion also cannot strand a WAL reconciliation obligation. Host policy may block future work, but durable facts remain visible for recovery and reconciliation.

## 27. Scheduler Integration

Scheduler changes are limited to runtime mechanism:

- Host and Agent budget inputs;
- budget hierarchy validation;
- Process, Agent, and Host budget checks at safe points;
- budget update/reset hooks;
- fault notification recording;
- structured subtree cancellation;
- cancellation reasons.

Scheduler policy is unchanged. It remains cooperative and does not decide business retry, restart, or fail-fast policy.

## 28. Backward Compatibility

Existing Process creation remains compatible because Process budget is optional and defaults to the Agent budget.

Existing V0.7 blocked budget tests were updated to the more precise reason format:

```text
budget:<scope>:...
```

Existing IPC, Resource Sharing, Capability Delegation, Agent Registry, Durable Tool, WAL, and reconciliation tests continue to pass.

## 29. Tests

`tests/test_runtime_isolation.py` covers:

- Host / Agent / Process budget hierarchy;
- `None` local limit semantics under aggregate Agent limits;
- Process, Agent, and Host budget blocking;
- usage attribution by `ProcessControlBlock.agent_id`;
- Process Tree not being the Agent budget tree;
- Agent budget isolation until Host exhaustion;
- budget update, reset, and unblock;
- child fault notification without parent or sibling failure;
- structured subtree cancellation;
- cancellation preserving Capability, ResourceShareGrant, and IPC messages;
- Durable Tool WAL behavior before dispatch, after prepare, and after dispatch.

Regression coverage includes V0.7 accounting/scheduler and V0.8 Agent Registry, Process Tree, Capability Delegation, Kernel IPC, Resource Sharing, Durable Tool, WAL, and reconciliation tests.

## 30. Limitations

Phase 6 does not implement:

- persistent usage ledger;
- billing or invoicing;
- preemptive scheduling;
- OS cgroups;
- detached child Processes;
- automatic retry;
- automatic restart;
- automatic fail-fast;
- persistent supervision policy;
- capability revocation;
- resource share revocation;
- IPC cancellation protocol;
- distributed cancellation;
- integrated Multi-Agent recovery;
- Multi-Agent RuntimeBench;
- RuntimeBench B8.

## 31. Deferred to Phase 7+

Future work may define integrated multi-Agent recovery, persisted supervision facts, richer recovery policies, detached child lifetime policy, and a dedicated benchmark for multi-Agent runtime behavior.

Those features should build on the current separation:

```text
Session durable truth
Process runtime state
Agent authority
Scheduler mechanism
Host policy
```

## 32. Validation

Phase 6 validation includes:

- focused runtime isolation tests;
- focused regressions for accounting, scheduler, Agent Registry, Process Tree, Capability Delegation, Kernel IPC, Resource Sharing, Durable Tool, WAL, and reconciliation;
- full pytest;
- RuntimeBench B1-B7;
- compileall;
- process runtime example;
- git diff whitespace check.

## 33. Decision

V0.8 Phase 6 is implemented as runtime isolation mechanism only. It preserves the frozen Kernel boundaries and is ready for review after validation.
