# V0.6 Capability Durable Implementation

Status: Phase 2 Part 2 implementation.

This slice connects the minimal V0.6 capability core to the durable side-effect
lifecycle. It does not implement delegation, revocation, namespaces, RBAC, IAM,
or a policy engine.

## WAL Integration

Durable mutation execution now records the authorization context that allowed
the operation to enter the WAL:

```text
authorization
tool/prepare
dispatch authorization
tool/dispatch
external effect
tool/commit or tool/abort
```

`tool/prepare` and `tool/dispatch` may include an `authorization` object with:

- `agent_id`
- `action`
- `resource_scope`
- `reason`
- optional `matched_grant`

The `operation_id` remains the durable operation identity. The authorization
context is bound to that identity by being recorded in the same WAL event. Replay
checks that a dispatch authorization context matches the prepare context when
both are present.

## Authorization Lifecycle

The durable executor performs two checks for mutation tools:

| Boundary | Behavior |
|---|---|
| Before `tool/prepare` | A missing capability returns `EACCES` and creates no durable operation. |
| Before `tool/dispatch` | A missing capability records `authorization/denied`, aborts the prepared operation with `EACCES`, and does not call the handler. |

Authorized prepare and dispatch boundaries record `authorization/granted`.
Denied durable mutation attempts record `authorization/denied`. These are
minimal audit events, not a full audit subsystem.

Read-only tool execution keeps the existing non-WAL path. Resource
authorization remains owned by `ResourceService`.

## Recovery Semantics

Replay remains compatible with old V0.3-V0.5 WAL records. Historical
`tool/prepare` and `tool/dispatch` events without authorization metadata are
accepted.

For new records:

- malformed authorization metadata corrupts replay;
- dispatch metadata must match prepare metadata on `agent_id`, `action`, and
  `resource_scope`;
- a crash after prepare and before dispatch remains safe to retry;
- a crash after dispatch for a reconcilable mutation still requires reconcile;
- durable facts already in the log are preserved.

If dispatch authorization fails after prepare, the operation is aborted before
any external effect is attempted. This records a terminal no-effect fact for the
prepared operation.

## Compatibility

Legacy `required_capability` remains supported. It is still adapted into:

```text
action: tool.execute
resource_scope: tool://<required_capability>
```

Structured tool definitions keep using `required_action` and
`required_resource`.

## Limitations

This phase intentionally does not implement:

- delegation;
- revocation;
- namespace normalization;
- constraint evaluation;
- policy decisions such as human approval;
- resource mutation capabilities beyond existing read/stat checks;
- durable authorization storage outside the session event log.

Reconciliation still resolves the registered tool and current agent through the
existing registry path. A future revocation-aware phase should decide whether
reconciliation of an already-dispatched operation uses the original authorization
context or a new explicit recovery capability.
