# AgentKernel V0.9D Shared Memory Authority

Status: implemented as a shared-memory authority boundary on top of V0.9,
V0.9B, and V0.9C.

V0.9D answers one narrow question:

```text
If Memory is shared across Agents, what actually authorizes access?
```

The frozen answer is:

```text
Only current Capability evaluation authorizes Memory access.
```

Everything else is data:

- memory URI
- memory id
- IPC payload
- ResourceHandle-style reference
- ResourceShare payload
- historical Context observation
- historical Session observation

None of those are authority.

## Core Claim

Memory is an Agent-scoped semantic durable object. Access to it is authorized
through existing Agent capability machinery:

```text
CapabilityGrant
      |
      v
CapabilityDelegator
      |
      v
CapabilityEvaluator
      |
      v
MemoryService
```

V0.9D deliberately does not add a separate memory authority subsystem.

## Authority Vocabulary

V0.9D reuses the existing Memory capability actions:

| Action | Meaning |
| --- | --- |
| `memory.read` | Read/search/list active memory and explicit audit views. |
| `memory.write` | Create trusted/legacy memory or lifecycle updates requiring write authority. |
| `memory.propose` | Create durable MemoryProposal audit state. |
| `memory.admit` | Admit, quarantine, or reject a proposal. |
| `memory.forget` | Forget or supersede memory. |

Scope remains URI-shaped:

```text
memory://<owner-agent-id>/<namespace>/<memory-id>
memory://<owner-agent-id>/<namespace>/**
```

Direct object reads authorize against the exact memory URI. Enumerations such as
`list`, `search`, `list_proposals`, and `admission_history` now filter each
candidate object by the caller's current evaluator instead of pre-authorizing a
broad namespace and leaking metadata.

## Agent, Process, and Session

Authority subject is always Agent identity.

```text
Agent      = capability principal
Process    = runtime identity
Session    = durable observation/history
```

A Process id that happens to equal an owner Agent id does not grant authority.
A Session event that contains memory content does not restore future authority.
Recovery can preserve historical observations, but future Memory reads still ask
the current `CapabilityEvaluator`.

## Delegation

Shared Memory uses the existing delegation semantics from V0.8:

```text
Parent Agent has CapabilityGrant(memory.read, memory://agent-a/public/**)
          |
          v
CapabilityDelegator attenuates grant to child Agent
          |
          v
Child Agent can read only the delegated scope
```

Delegation cannot broaden scope. A parent with
`memory://agent-a/public/**` cannot delegate `memory://agent-a/**`.

## Revocation

V0.9D revocation is current-evaluator revocation:

```text
old evaluator included grant -> read allowed
new evaluator omits grant    -> future read denied
```

This does not rewrite history. Old Session observations remain durable facts.
Fresh search, list, Context projection, and Memory reads must use the current
evaluator and exclude unauthorized memory.

## IPC Is Data

IPC can carry a memory URI:

```json
{"memory_uri": "memory://agent-a/private/mem_0001"}
```

That payload grants nothing. Receiver Agent must still have a current
`memory.read` grant for the referenced Memory scope.

## ResourceShare Is Not Memory Authority

ADR: V0.9D does not use `ResourceShare` for Memory.

Reason:

- ResourceShare governs Resource/Artifact handles and byte payload access.
- Memory is semantic durable state addressed by Memory capability scopes.
- Mixing them would make Resource payloads look like Memory authority.

Therefore:

```text
ResourceShareGrant != Memory grant
Memory CapabilityGrant != ResourceShare
```

Cross-Agent Resource access still requires current Resource capability plus an
active ResourceShare. Cross-Agent Memory access requires current Memory
capability. The two mechanisms stay separate.

## Trust and Lifecycle Orthogonality

V0.9C trust/admission state is not authority.

`TOOL_DERIVED` or `USER_EXPLICIT` provenance changes how a proposal should be
reviewed, but it does not create a read grant.

V0.9B lifecycle state is also not authority.

`ACTIVE`, `STALE`, `SUPERSEDED`, and `FORGOTTEN` control retrieval semantics.
They do not grant or remove access by themselves; `MemoryService` still checks
the current evaluator first.

## Threats Covered

| Threat | V0.9D Boundary |
| --- | --- |
| Agent receives a memory URI over IPC | Denied unless current evaluator grants memory.read. |
| Agent guesses memory id | Denied unless current evaluator grants the exact/scope URI. |
| Agent has read grant and attempts mutation | Denied unless write/forget/admit authority exists. |
| Agent sees old Session observation after revoke | Observation remains, future reads/search/context are denied. |
| Enumeration across owner namespace | Each returned object is individually authorized. |
| Process identity confusion | Request subject remains Agent id. |
| ResourceShare payload reused as Memory grant | Denied; ResourceShare is not Memory authority. |

## Non-Goals

V0.9D does not implement:

- `MemoryACL`
- `MemoryPermissionStore`
- `MemoryRole`
- `MemoryShareCapabilityStore`
- new policy engine
- namespace system beyond existing memory scopes
- cryptographic secrecy
- secure deletion
- full information-flow control
- distributed memory sharing protocol
- automatic revocation propagation service

V0.9D also does not claim that old observations disappear. It only guarantees
that future Memory access through current runtime APIs is denied when current
capability evaluation denies it.

## Review Questions

1. 为什么 Memory URI 不是 authority？

   因为 URI 只是对象地址。Kernel authority 来自当前
   `CapabilityEvaluator` 对 `AuthorizationRequest` 的判断。

2. 为什么 revocation 不删除旧 Session observation？

   Session 是 durable history。撤销只影响未来访问判断，不重写已经发生过的
   观察事实。

3. 为什么 list/search 需要逐对象授权？

   否则一个 broad enumeration request 可能泄露未授权 namespace 中存在多少
   Memory、Proposal 或 AdmissionRecord。

4. 为什么不用 ResourceShare 管 Memory？

   ResourceShare 是 artifact/byte payload sharing 机制。Memory 是语义持久对象，
   已经有 capability URI scope。混用会让 Resource payload 看起来像 Memory 权限。

5. V0.9D 是否解决了所有多 Agent 记忆安全问题？

   没有。它只冻结并验证 Shared Memory authority boundary：未来 Memory 访问必须
   经由当前 Capability evaluation。
