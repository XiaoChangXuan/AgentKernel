# AgentKernel V0.9 Persistent Memory

Status: implemented as a Kernel mechanism for durable, agent-scoped semantic
memory.

V0.9 adds Persistent Memory to AgentKernel without turning Memory into Session,
Context, ResourceStore, objective truth, or a product policy engine.

## Core Claim

Memory is a durable, cross-session, agent-scoped semantic substrate with
provenance, explicit lifecycle, capability enforcement, deterministic retrieval,
and bounded Context VM projection.

One `MemoryRecord` means:

```text
Kernel durably recorded that this proposition was remembered.
```

It does not mean:

```text
The proposition is objectively true in the outside world.
```

## Architecture

```text
Session A
    |
    | explicit memory proposal
    v
MemoryService
    |
    +-- append-only durable MemoryEvents
    |       memory/remembered
    |       memory/superseded
    |       memory/forgotten
    |
    +-- active MemoryRecord projection
    |
    +-- rebuildable lexical search index

            retrieve/select
                 |
                 v
Context VM bounded projection
                 |
                 v
Model-visible context

Session B can retrieve the same Memory only through current capability checks.
```

## Boundaries

| Boundary | V0.9 decision |
| --- | --- |
| Session != Memory | Session records what happened in one task. Memory stores cross-session remembered propositions. |
| Memory != Context | Memory enters model context only through retrieve -> select -> project. |
| Memory != Resource | Memory is semantic state, not blob/artifact storage. |
| Memory != Objective Truth | Provenance is preserved, but content is not certified as true. |
| Memory ID != Permission | Knowing `memory_id` or `memory://...` does not grant read authority. |
| Index != Durable Truth | The lexical index is rebuildable from durable memory events. |

## Data Model

`MemoryRecord` includes:

- `memory_id`
- `owner_agent_id`
- `namespace`
- `content`
- `created_at`
- `provenance`
- `metadata`
- lifecycle projection fields such as `active`, `supersedes_memory_id`,
  `superseded_by_memory_id`, and `forgotten_at`

`MemoryProvenance` records a small source envelope:

- `source`
- `source_session_id`
- `source_event_id`
- `source_agent_id`
- `source_tool_name`
- `note`

The provenance model is intentionally small. It answers where the remembered
proposition came from, not whether the proposition is globally true.

## Lifecycle

V0.9 supports:

- `remember`: append a `memory/remembered` fact.
- `read`: read by id or URI after current authorization.
- `list`: list active records for an owner/namespace.
- `search`: deterministic lexical retrieval over active records.
- `supersede`: append a new remembered record and an explicit old -> new
  supersession fact.
- `forget`: append a semantic inactive marker.

`forget` is not secure physical deletion. It makes the memory inactive for
default retrieval while keeping durable history explainable.

## Storage

V0.9 provides:

- `InMemoryMemoryStore` for deterministic tests.
- `JsonlMemoryStore` for local durable persistence across Python runtimes.

Durable truth is the append-only event stream. Active records and indexes are
projections.

## Capability Enforcement

V0.9 uses the existing V0.6/V0.8 capability system.

Actions:

```text
memory.read
memory.write
memory.forget
```

Resource URI:

```text
memory://<owner-agent-id>/<namespace>/<memory-id>
```

Namespace scope:

```text
memory://<owner-agent-id>/<namespace>/**
```

There is no silent owner bypass in `MemoryService`. The Host must pass a
`CapabilityEvaluator` with current authority. Existing V0.8 delegation can derive
narrowed read authority for another Agent.

## Retrieval And Context Projection

Search is deterministic and offline:

- namespace filtering
- active filtering
- current capability check
- lexical score
- stable sort

Projection is explicit:

```text
MemoryService.search(...)
    -> selected MemoryRecord values
    -> project_memories_to_context_pages(...)
    -> bounded ContextPage values
```

Creating 1000 durable memories does not put 1000 memories into model context.
Only selected records are projected.

## Recovery Semantics

Memory writes are durable JSONL appends. Fresh `MemoryService(JsonlMemoryStore(...))`
rebuilds projected state from the event stream.

V0.9 does not claim universal exactly-once semantics for every future backend.
It claims that the provided local append-only store can survive restart and
rebuild active state from durable facts.

## API Sketch

```python
memory = MemoryService(JsonlMemoryStore("memory.jsonl"))

record = memory.remember(
    agent_id="agent-a",
    namespace="preferences",
    content="Preferred language is Chinese.",
    provenance=MemoryProvenance(source="user", source_agent_id="agent-a"),
    capability_evaluator=CapabilityEvaluator([
        CapabilityGrant("agent-a", "memory.write", "memory://agent-a/preferences/**"),
    ]),
)

results = memory.search(
    agent_id="agent-a",
    owner_agent_id="agent-a",
    namespace="preferences",
    query="language",
    limit=5,
    capability_evaluator=CapabilityEvaluator([
        CapabilityGrant("agent-a", "memory.read", "memory://agent-a/preferences/**"),
    ]),
)
```

## Non-Goals

V0.9 does not implement:

- vector database
- embedding service
- LangChain/LlamaIndex/RAG framework
- knowledge graph
- automatic memory extraction policy
- autonomous reflection agent
- secure physical deletion
- cloud sync
- distributed memory database
- V1.0 planner

## Review Questions

1. Memory and Session differ because Session is per-task durable event truth,
   while Memory is cross-session semantic state derived from explicit memory
   events.
2. A `MemoryRecord` is not objective truth because Kernel preserves provenance
   and lifecycle, not real-world verification.
3. The search index is not source of truth because it is rebuildable from durable
   `MemoryEvent` records.
4. Forget is semantic inactive state, not physical deletion.
5. Memory survives across Sessions because `JsonlMemoryStore` persists append-only
   events and `MemoryService` reconstructs projection in a fresh runtime.
6. Knowing `memory_id` is not enough because every read passes through current
   `CapabilityEvaluator` authority.
7. 1000 memories do not enter Context automatically because Context projection is
   explicit and bounded.
8. A future vector database may replace the rebuildable retrieval index, but not
   durable event truth, provenance, capability checks, lifecycle, or bounded
   projection.
9. V0.9 implements mechanism: store, service, lifecycle, authorization, retrieval,
   projection. Policy remains outside Kernel: what to remember, when to forget,
   and how to rank semantically.
10. V0.9 adds a memory module without rewriting V0.1-V0.8 abstractions.
