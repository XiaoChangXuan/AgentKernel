# V0.6 Capability Implementation

Status: Phase 1 implementation.

This document describes the minimal Kernel Capability Core added after the
V0.6 Capability Architecture Freeze Review. It intentionally does not implement
a full permission system.

## Current Implementation Scope

Phase 1 adds four Kernel primitives:

| Primitive | Purpose |
|---|---|
| `CapabilityGrant` | Positive authority assigned to one subject. |
| `AuthorizationRequest` | A proposed action by one agent against one resource. |
| `AuthorizationDecision` | Allow/deny result plus the matched grant when allowed. |
| `CapabilityEvaluator` | Minimal evaluator for exact action matching and resource-scope matching. |

The implemented grant shape is:

```text
CapabilityGrant
  subject
  action
  resource_scope
  constraints
```

The implemented request shape is:

```text
AuthorizationRequest
  agent_id
  action
  resource
```

The implemented decision shape is:

```text
AuthorizationDecision
  allowed
  reason
  matched_grant
```

## Matching Semantics

Phase 1 supports only:

1. exact subject match;
2. exact action match;
3. exact resource match;
4. suffix `/**` prefix scope match.

Example:

```text
grant:
  subject: agent-a
  action: resource.read
  resource_scope: artifact://project-a/**

request:
  agent_id: agent-a
  action: resource.read
  resource: artifact://project-a/file.txt

decision:
  allowed: true
```

The same grant does not authorize:

```text
resource: artifact://project-b/file.txt
```

## Legacy Compatibility

The existing V0.1-V0.5 capability string model remains supported.

`ToolDefinition.required_capability` is not removed. `ToolRegistry` now adapts
the legacy string check through `CapabilityEvaluator` by mapping a string such
as:

```text
math.add
```

to:

```text
action: tool.execute
resource: tool://math.add
```

This keeps existing tool authorization behavior compatible:

- authorized tools remain visible through `model_schemas`;
- unauthorized tools remain hidden from schema projection;
- unadvertised or unauthorized tool calls are still denied at execution time;
- `AgentControlBlock.capabilities` and `capability_bounding_set` are preserved.

## Not Implemented In Phase 1

Phase 1 does not implement:

- full namespace resolution;
- delegated child-agent grants;
- revocation;
- RBAC;
- IAM;
- users, groups, roles, or tenants;
- policy persistence;
- audit events;
- approval flows;
- argument-level constraints;
- time-based expiration;
- durable WAL phase-specific authorization;
- resource-service structured scope enforcement.

The `constraints` field is currently preserved as immutable metadata on a
grant. It is not evaluated yet.

## Kernel Boundary

The implementation keeps the authority boundary in Kernel-owned code.

The LLM remains an untrusted proposer. It can propose a tool call, but
`ToolRegistry` still decides whether that tool is visible and executable. Tools
do not authorize themselves, and resource drivers are not exposed to model
text.

## Phase 2 Direction

Phase 2 should add structured authorization at more Kernel boundaries:

- resource read/stat checks in `ResourceService`;
- durable action checks for prepare, dispatch, and reconcile;
- stable denial reason codes;
- optional authorization audit events;
- tests for cross-session and cross-resource denial.

## Phase 3 Direction

Phase 3 should add multi-agent capability semantics:

- child-agent grant derivation;
- delegation lineage;
- revocation;
- namespace roots;
- recovery-safe revocation behavior;
- IPC and memory scopes for future V0.8/V0.9 work.

Phase 3 should not begin until Phase 2 has stable evaluator semantics and
compatibility tests for legacy `required_capability`.
