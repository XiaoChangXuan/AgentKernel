# V0.7 RuntimeBench Implementation

Status: RuntimeBench V0.7 implementation phase 1.

Command:

```text
python -m benchmarks.runtimebench
```

Output:

```text
benchmarks/results/runtimebench_v0.7.json
```

## 1. Scope

This phase implements the unified RuntimeBench runner described in
`docs/RUNTIMEBENCH_V0.7_DESIGN.md`.

Implemented:

- `benchmarks/runtimebench/schema.py`
- `benchmarks/runtimebench/environment.py`
- `benchmarks/runtimebench/fixtures.py`
- `benchmarks/runtimebench/adapters.py`
- `benchmarks/runtimebench/runner.py`
- `python -m benchmarks.runtimebench`

The runner is offline and deterministic with respect to external services. It
does not call model providers, external APIs, or network services. It reuses
the existing deterministic benchmark fixtures.

## 2. RuntimeBench Architecture

The first implementation uses this structure:

```text
python -m benchmarks.runtimebench
  -> runner.py
  -> environment.py
  -> adapters.py
  -> existing leaf benchmark runners
  -> schema.py
  -> benchmarks/results/runtimebench_v0.7.json
```

Existing leaf benchmarks remain runnable:

```text
python -m benchmarks.recovery.runner
python -m benchmarks.durable_tool.runner
python -m benchmarks.resource_handle.runner
python -m benchmarks.context_vm.runner
python -m benchmarks.capability_runtime_benchmark
python -m benchmarks.v0_7_runtime_benchmark
```

RuntimeBench does not replace them. It normalizes their output into a stable
family-oriented schema and preserves leaf observations in `raw_records`.

## 3. Implemented Families

The current V0.7 implementation emits B1 through B5 and B7.

| Family | Status | Source benchmarks |
| --- | --- | --- |
| B1 Fault Tolerance | Implemented | `recovery`, selected `v0_7_runtime` process recovery record |
| B2 Side Effect Safety | Implemented | `durable_tool` |
| B3 Context Efficiency + Truth Preservation | Implemented | `resource_handle`, `context_vm` |
| B4 Capability Isolation | Implemented | `capability_runtime` |
| B5 Resource Governance | Implemented | RuntimeBench budget pressure cases |
| B7 Boundary Isolation | Implemented | RuntimeBench boundary invariant cases |

Deferred:

- B6 Long-Horizon Runtime Stability.
- B8 Scheduler Scalability.

B6 and B8 remain intentionally unimplemented in this phase. Some existing
V0.7 runtime records already provide source material for later adapters.

## 4. Output Schema

The top-level document contains:

- `runtimebench_version`
- `runtime_version`
- `commit`
- `generated_at`
- `environment`
- `summary`
- `benchmarks`

Each benchmark family record contains:

- `benchmark_id`
- `category`
- `description`
- `runtime_version`
- `fixture`
- `mechanism_under_test`
- `baseline`
- `failure_injection`
- `metrics`
- `result`
- `success`
- `limitations`
- `raw_records`

The `raw_records` field preserves the existing module-level benchmark records:

```json
{
  "benchmark": "recovery",
  "case": "after_tool_dispatch",
  "strategy": "agentkernel_replay",
  "metrics": {
    "success": true
  }
}
```

This keeps the migration reversible and avoids losing detail while the unified
RuntimeBench schema matures.

## 5. Family Semantics

### B1 Fault Tolerance

Uses the existing recovery crash prefixes and the V0.7 process recovery mapping
case.

Primary metrics:

- `recovery_success_rate`
- `lost_durable_fact_count`
- `duplicate_effect_count`
- `recovery_latency_ms`
- `process_recovery_mapping_success`

### B2 Side Effect Safety

Uses the fake payment durable tool fixture.

Primary metrics:

- `baseline_duplicate_effect_count`
- `duplicate_effect_count`
- `ordinary_operation_count`
- `agentkernel_operation_count`
- `reconciliation_success_rate`
- `operation_identity_stable`

### B3 Context Efficiency + Truth Preservation

Uses the Resource Handle and Context VM fixtures.

Primary metrics:

- `max_full_context_bytes`
- `max_artifact_context_bytes`
- `artifact_context_stable`
- `durable_bytes_preserved`
- `full_history_tokens`
- `context_vm_tokens`
- `context_vm_recovery_ability`

### B4 Capability Isolation

Uses the existing capability runtime fixture.

Primary metrics:

- `unauthorized_execution_count`
- `unauthorized_access_count`
- `unauthorized_dispatch_count`
- `false_deny_rate`
- `audit_metadata_complete`
- `legacy_compatibility_passed`

### B5 Resource Governance

Uses deterministic RuntimeBench pressure cases for token, tool-call,
resource-byte, wall-time, usage snapshot, and unblock recovery checks.

Primary metrics:

- `budget_overshoot`
- `blocked_correctness`
- `resource_usage_accuracy`
- `usage_snapshot_accuracy`
- `safe_point_blocking_success`
- `unblock_correctness`
- `budget_recovery_success`

### B7 Boundary Isolation

Uses deterministic RuntimeBench invariant checks to validate that runtime object
boundaries remain separated.

Primary metrics:

- `boundary_invariant_passed`
- `authority_leak_count`
- `durable_truth_mutation_count`
- `object_identity_confusion_count`
- `regression_count`

## 6. Boundaries Preserved

This implementation does not modify:

- `agentkernel/`
- Capability authority
- Resource Layer
- Durable WAL schema
- Context VM behavior
- Process runtime behavior

This implementation does not add:

- V0.8
- Process Tree
- IPC
- Multi-Agent
- Delegation
- Namespace
- Memory
- RBAC/IAM
- external API calls

## 7. Current Limitations

- RuntimeBench V0.7 emits B1 through B5 and B7.
- B6 and B8 are still design-only in this phase.
- The result includes local latency measurements, so exact timings vary by
  machine.
- B3 still uses marker-based correctness rather than human answer quality.
- B2 uses a fake payment service and does not prove universal exactly-once
  semantics.
- B4 does not include delegation, revocation, namespace, RBAC, IAM, or
  production sandbox security.
- B5 uses cooperative safe points only; it does not prove preemptive resource
  enforcement.
- B7 is an object-model regression benchmark; it does not test V0.8 IPC,
  process trees, namespaces, or multi-agent ownership.
