# V0.5 Resource Architecture Review

## 1. Purpose

This review checks whether the V0.5 Virtual Resource / Artifact Handle layer is
a stable architectural base for later Kernel work, specifically:

- V0.6 Capability / Namespace
- V0.7 Agent Process / Scheduler
- V0.8 Subagent / IPC
- Long-term Memory

The review is intentionally limited to architecture. It does not start V0.6 and
does not implement garbage collection, namespaces, remote drivers, distributed
stores, or resource write transactions.

The central question is whether V0.5 contains a mistake that would force a
future version to overturn public or kernel-facing interfaces. The answer is no:
there is no blocker before V0.6. There are, however, lifecycle and resource
journal issues that should be designed before resource deletion, sharing, or
multi-agent garbage collection become real features.

## 2. Current Resource Architecture

Current implementation locations:

- `agentkernel/resources/model.py` defines resource identity, handle projection,
  host metadata, limits, read result values, and process-local metrics.
- `agentkernel/resources/store.py` defines the replaceable `ResourceStore`
  Protocol and `LocalResourceStore` driver.
- `agentkernel/resources/service.py` owns kernel identity generation,
  validation, authorization, store access, and orphan detection.
- `agentkernel/resources/externalization.py` defines the replaceable Tool Result
  externalization policy and processor.
- `agentkernel/resources/tools.py` exposes model-facing `resource_stat` and
  `resource_read` tools.

There is no separate `resource.py`, `handle.py`, or `drivers/` package in the
current tree. The current physical split is smaller but still expresses the
right boundaries: model values and host metadata are in `model.py`, store driver
behavior is in `store.py`, and trusted semantics are in `service.py`.

The real Tool Result flow is:

```text
Tool handler returns ToolResult
  -> DurableToolExecutor._process_result()
  -> ToolResultExternalizer.process()
  -> ResourceService.create_artifact()
  -> ResourceStore.commit()
  -> ToolResult output becomes preview + ResourceHandle
  -> mutation tools append tool/commit with projected output
  -> DefaultAgentLoop appends tool/result
  -> ContextProjector projects only Session events
```

`ResourceStore` stores bytes and metadata. `Session` stores the model-visible
preview and handle. `ContextProjector` only sees `Session` events and never
depends on the resource store. This is the correct separation for V0.5:
Resource Truth is durable bytes plus host metadata; Context Projection is the
bounded representation used for model calls.

## 3. Resource Identity Review

Rating: GREEN.

V0.5 keeps identity concepts separate:

- `resource_id` is kernel-generated by `ResourceService`.
- `handle_id` is kernel-generated by `ResourceService`.
- `artifact://res_...` is the opaque model-facing resource URI.
- `tool_call_id` remains model protocol identity.
- `operation_id` remains durable Tool WAL identity.

The current `ResourceService` default factories use UUID-backed `res_...` and
`hdl_...` values. Validation requires the expected prefixes and alphanumeric
payloads. The URI is derived from `resource_id`, not from a path,
`tool_call_id`, or `operation_id`.

Source tool name, tool call ID, and operation ID are stored as metadata for
correlation, audit, and recovery. They are not resource identity. This is
important: a resource created by a retried or reconciled tool can still have its
own object identity, while the operation identity continues to describe the Tool
side effect.

Future remote object stores, databases, memory stores, and content-addressed
stores can preserve this contract. The driver can map `resource_id` to its own
backend key. The Kernel API does not need to expose a file path or remote URL.

## 4. Resource Lifecycle Review

Rating: YELLOW, but not a blocker before V0.6.

Current lifecycle APIs are intentionally minimal:

- create through `ResourceService.create_artifact`
- stat through `ResourceService.stat`
- bounded read through `ResourceService.read`
- metadata listing through the store for host-side scans
- orphan identification through `ResourceService.orphaned_resources`

Missing lifecycle states and actions:

- delete
- expire
- retain
- archive
- transfer
- tombstone

This does not block V0.6 Capability / Namespace because current resources are
append-only artifacts with stable handles. It will matter before automatic
cleanup, large-scale artifact generation, long-running sessions, or cross-agent
sharing. If an agent creates many artifacts, V0.5 retains them unless the host
deletes the backing store externally. That is safe for correctness and unsafe
for unbounded storage growth.

Recommended future direction:

- Keep V0.5 create/read stable.
- Add explicit lifecycle metadata before delete/GC ships.
- Prefer retained-by-default semantics until reference tracking is authoritative.
- Treat session end as a policy input, not an implicit destructive cleanup.

OS analogy, without copying Linux mechanics: process exit closes file
descriptors because the kernel owns descriptor tables. AgentKernel currently has
no equivalent per-session resource table with delete policy, so session end
cannot safely imply resource cleanup yet.

## 5. Ownership Review

Rating: YELLOW, small-to-medium extension.

Current ownership is exact:

```text
ResourceOwner(agent_id, session_id)
```

`ResourceService._resolve` loads metadata and requires an exact owner match
before returning a handle or bytes. This is simple, enforceable, and enough for
single-agent V0.5.

Future parent agents, child agents, subagents, and cross-session work require
more than exact owner equality:

- delegation from parent to child
- transfer between sessions
- revocation of previously granted handles
- read-only versus write/delete/share rights
- possibly group or namespace scoped grants

This does not require a major rewrite if `ResourceService` remains the
authorization boundary. It is a medium refactor if callers have already encoded
exact ownership assumptions everywhere. Today they mostly do not: model-facing
tools route through `ResourceService`, and the store driver is not exposed to the
model.

Recommendation: keep `ResourceOwner` as creation provenance, and add a separate
authorization decision layer for future sharing rather than replacing owner with
namespace semantics.

## 6. Capability Compatibility

Rating: GREEN for V0.6 entry, YELLOW for full policy expressiveness.

Current tools use a coarse capability:

```text
resource.read
```

`ToolRegistry` checks `ToolDefinition.required_capability` before invocation.
`resource_stat` and `resource_read` then call `ResourceService`, which enforces
URI validation, byte limits, and owner checks.

This gives V0.6 a clean seam: capability checks can become structured without
making the model aware of store internals. Future policy can evaluate:

- action: `read`, `write`, `delete`, `share`
- resource: `artifact://res_...`
- scope: session, namespace, workspace prefix, media type, or owner group
- caller: agent, parent, child, or delegated principal

The V0.5 gap is that the coarse capability cannot express per-resource or
per-scope authorization. That is expected. The important point is that the
resource tools already pass through one trusted service, so V0.6 can extend
policy at that service/tool boundary.

## 7. Tool WAL Compatibility

Rating: GREEN with one future caution.

V0.5 does not create a second transaction system. It reuses the existing Tool
execution path:

- read-only tools execute without `TOOL_PREPARE`.
- mutation tools append `TOOL_PREPARE`.
- mutation dispatch appends `TOOL_DISPATCH`.
- handler result is processed by `ToolResultExternalizer`.
- if successful, mutation output is appended to `TOOL_COMMIT`.
- the loop appends `TOOL_RESULT` after executor return.

When a mutation result is externalized, `TOOL_COMMIT.output` contains the same
preview and handle projection later written in `TOOL_RESULT`; it does not store
the large raw output. That preserves the V0.3 WAL contract while avoiding a
large durable session log.

Future Resource mutation should continue to reuse operation IDs, WAL events,
and reconciliation concepts. A separate resource transaction mechanism would
create duplicate recovery semantics. The resource layer should instead add
resource-specific journal or reference events only where the Tool WAL cannot
represent resource lifecycle facts.

Future caution: `ResourceService.create_artifact` commits the resource before
`TOOL_COMMIT` and `TOOL_RESULT` are durable. A crash in that window creates a
retained orphan. Retention is acceptable now. Deletion or GC must not be added
until reference tracking accounts for this window.

## 8. Context VM Compatibility

Rating: GREEN.

The current design correctly preserves:

```text
Resource Truth != Context Projection
```

`ContextProjector` projects only the session event log and the host system
prompt. It has no dependency on `ResourceService` or `ResourceStore`. It sees a
Tool Result containing preview text and a handle dictionary, not the raw bytes.

Context pruning and compaction can shrink or summarize model-visible pages, but
they do not mutate resource payloads, metadata, or checksums. The tests cover
this separation by pruning the visible Tool Result projection and then reading
the original bytes back from the resource service.

Future Memory, Skill, Rule, and Artifact projections can enter the Context VM
as pages without turning the Context VM into a resource store. They should carry
provenance and controlled references, while truth stays in their respective
stores.

## 9. Driver Boundary

Rating: GREEN for local, file, memory, database, and object-store drivers.

The driver seam is small:

```text
commit(metadata, bytes)
stat(resource_id)
read(resource_id, offset, limit)
list_metadata()
```

`LocalResourceStore` is one driver. It stages payload and metadata in a temporary
directory, fsyncs them, atomically publishes the final resource directory, and
syncs the root when possible. It never exposes that path through
`ResourceHandle`.

Adding a file driver, S3 driver, database driver, or memory driver should not
change model-facing APIs. A driver may have different durability mechanics, but
it can still implement commit/stat/read/list over kernel-generated IDs.

The boundary will need extension for lifecycle operations such as delete,
archive, retention, and tombstones. That is a store/service contract extension,
not evidence that V0.5 chose the wrong identity or handle model.

## 10. Event Model

Rating: YELLOW.

The current Session event log records projected resource references inside
Tool outputs. It does not record independent resource lifecycle events such as:

- resource/create
- resource/delete
- resource/read
- resource/share
- resource/revoke
- resource/retain
- resource/expire

The current resource metadata is stored in `ResourceStore`, not in Session
events. Session events contain the handle projection as part of `TOOL_COMMIT`
and `TOOL_RESULT` payloads when a tool result is externalized.

Two possible future directions:

| Option | Summary | Strengths | Weaknesses |
|---|---|---|---|
| A. Session events remain the lifecycle record | Resource references continue to live only inside Session events | Simple, no second log | Weak for cross-session sharing, audit, deletion, and GC |
| B. Add a Resource Journal | Resource lifecycle has its own append-only facts, correlated to Session and operation IDs | Strong recovery, audit, sharing, revocation, and GC | Requires another replay/index path |

Option B is more appropriate once resources become shared, revocable, or
collectable. Session events should continue to record what the model saw and
what a Tool returned. A Resource Journal should record host-side lifecycle facts
that are not model conversation facts.

Near-term recommendation: before implementing deletion/GC or cross-agent
sharing, formalize session-resource reference indexing. At minimum,
reference scans must decide whether `TOOL_COMMIT` references count in addition
to `TOOL_RESULT` references. Today `orphaned_resources(session)` intentionally
scans only `TOOL_RESULT`, which is safe because V0.5 does not delete, but too
weak for future automatic cleanup.

## 11. Persistence Compatibility

Rating: GREEN for restart, YELLOW for migration and lifecycle history.

Session persistence and resource persistence are separate:

- `JsonlSessionPersistence` stores Session headers and append-only events.
- `LocalResourceStore` stores one directory per resource with `metadata.json`
  and `payload.bin`.
- A handle in a durable Tool Result can be resolved after restart if the new
  `ResourceService` points at the same resource root.

This is compatible with V0.5 restart behavior and with future backend drivers.
The resource metadata has `format_version=1`, so there is already a place for
metadata evolution.

Persistence gaps to address later:

- no Resource Journal for lifecycle replay
- no migration tool for resource metadata versions
- no tombstone for deleted resources
- no explicit store ID in `artifact://` URIs
- no policy for moving resources between durable roots

None of these block V0.6 Capability / Namespace as long as V0.6 does not add
destructive lifecycle actions.

## 12. Resource Accounting

Rating: YELLOW, future scheduler work.

Current accounting is intentionally process-local and reconstructable:

- resources created
- resource bytes stored
- resource reads
- resource bytes read
- externalized Tool Results
- preview bytes
- model-visible bytes saved

These metrics are useful operational evidence. They are not Session truth and
are not persisted.

V0.7 Scheduler will likely need a unified `ResourceUsage` model covering:

- context tokens
- resource bytes
- tool calls
- network bytes
- elapsed time
- money or provider cost

That abstraction is not needed in V0.5. Adding it now would be speculative. The
right future shape is a scheduler-facing accounting layer that consumes
resource metrics, context metrics, and tool execution facts without changing
the handle or store interface.

## 13. Crash Recovery

| Case | Current behavior | Future risk | Recommendation |
|---|---|---|---|
| A. Crash before resource create/commit | No handle is returned. `LocalResourceStore` temporary state is ignored or removed on ordinary failure. | A backend driver with weaker atomicity could leak partial objects. | Keep commit atomic from the service perspective; drivers must hide partial writes. |
| B. Resource durable before Tool Result | Resource remains durable but may be absent from `TOOL_COMMIT` or `TOOL_RESULT`. It can be identified by owner/source metadata. | Automatic cleanup could delete a resource needed by recovery if references are incomplete. | Retain by default; add Resource Journal or stronger reference index before GC. |
| C. Handle saved, then restart | A restarted service over the same root can stat/read the resource for the same owner. | Store migration or root changes could strand handles. | Keep opaque URI stable; add store migration policy later if needed. |
| D. Resource deleted while Session references it | V0.5 has no delete API, so this only occurs by external store tampering. Reads fail as unknown/unavailable. | Future delete can make old sessions unreplayable or misleading. | Add tombstones and deletion policy before exposing delete. |
| E. Two agents access the same resource | Exact owner match denies other agent/session, even with `resource.read`. | Subagent and IPC workflows need controlled sharing. | Add delegation/capability checks at `ResourceService`, not direct store access. |

Crash review conclusion: V0.5 chooses retention over unsafe cleanup. That is the
right default for this stage.

## 14. OS Design Mapping

This design maps to OS concepts only as a guide, not as an implementation goal:

| OS concept | AgentKernel mapping | Limit of the analogy |
|---|---|---|
| Filesystem/object store | `ResourceStore` keeps durable bytes and metadata | Resource is not a file; path semantics are not model API |
| Device driver | `LocalResourceStore` and future store implementations | Drivers implement storage, not authorization policy |
| File descriptor | `ResourceHandle` is a controlled model-facing reference | Handle is not the resource and is not currently a lease |
| Kernel syscall boundary | `ResourceService` plus `resource_read`/`resource_stat` tools | Future structured capability checks belong here |
| Process exit closes descriptors | Future session/agent lifecycle may trigger resource policy | V0.5 has no descriptor table or automatic cleanup |

The important design principle is separation of authority:

- Resource is not File.
- File is only one possible Resource driver.
- Handle is not Resource.
- Preview is not truth.
- ResourceStore is not ContextStore.

## 15. Compatibility Matrix

| Future area | Compatibility rating | Assessment |
|---|---|---|
| V0.6 Capability / Namespace | SMALL EXTENSION | Add structured action/resource/scope checks at `ToolRegistry` and `ResourceService`; current handle identity can remain. |
| V0.7 Agent Process / Scheduler | MEDIUM REFACTOR | Process state can use current owner and metrics, but scheduler-grade unified usage accounting and cleanup policy are still missing. |
| V0.8 Subagent / IPC | MEDIUM REFACTOR | Exact owner checks need delegation, transfer, and revocation, but direct store exposure has been avoided. |
| Long-term Memory | MEDIUM REFACTOR | Resource concepts can back artifacts or memory blobs, but memory needs indexing, retention, privacy, and projection policy outside V0.5. |
| Remote Object Store | SMALL EXTENSION | Add a driver implementing the existing store Protocol, plus deployment configuration. |
| Database Store | SMALL EXTENSION | Same identity and handle model works; transactions must preserve commit/stat/read semantics. |
| Resource Delete / GC | MEDIUM REFACTOR | Requires lifecycle metadata, tombstones, and stronger reference tracking or Resource Journal. |
| Resource Sharing | MEDIUM REFACTOR | Requires delegated grants and revocation at service boundary. |
| Resource Write Transactions | MEDIUM REFACTOR | Should reuse Tool WAL operation IDs and reconciliation rather than create a parallel transaction model. |
| Full VFS semantics | MAJOR REWRITE if forced into V0.5 API | Directories, paths, rename, glob, and mounts are intentionally absent and should be a separate layer if ever needed. |

## 16. Blockers

### BLOCKER BEFORE V0.6

None.

No current issue requires changing the V0.5 public resource identity, handle
projection, store seam, or Tool Result externalization interface before V0.6
Capability / Namespace work starts.

### SHOULD FIX

- Design a Resource Journal or equivalent reference index before implementing
  resource deletion, GC, sharing, or revocation.
- Decide whether host-side reference scans include `TOOL_COMMIT` as well as
  `TOOL_RESULT`. Current `orphaned_resources(session)` scans only
  `TOOL_RESULT`, which is acceptable for retained V0.5 artifacts but not enough
  for automatic cleanup.
- Add lifecycle metadata such as retained, expired, archived, deleted, and
  tombstoned states before exposing destructive operations.

### FUTURE CONCERN

- Structured resource capabilities by action, URI, scope, and caller.
- Delegation, transfer, and revocation for parent/child agents and subagents.
- Unified scheduler accounting for context tokens, bytes, calls, network, time,
  and cost.
- Store migration, store identity, and remote backend configuration.
- Binary/media-native projections and parsers.

## 17. Recommendation

Proceed to V0.6 after this review. Do not modify core code for V0.5.

V0.5 has the right architectural center:

- durable resource truth is separate from model projection;
- handles are opaque and path-free;
- resource identity is independent of tool calls and WAL operations;
- the store is replaceable;
- authorization and validation pass through `ResourceService`;
- Context VM remains independent from ResourceStore.

The future work is additive if it is placed at the right boundaries. V0.6 should
extend capability and namespace policy at the existing tool/service seam. V0.7
and V0.8 should add scheduler accounting, lifecycle policy, and delegation only
after resource lifecycle facts are made explicit.
