# V0.6 Capability Security Review

Status: architecture validation for V0.6 Capability Core Phase 1.

This review validates the minimal capability core. It does not define Phase 2
implementation work and does not implement namespace resolution, delegation,
revocation, RBAC, IAM, resource-service authorization, or durable WAL
phase-specific authorization.

## 1. Scope

Implemented Phase 1 primitives:

- `CapabilityGrant`
- `AuthorizationRequest`
- `AuthorizationDecision`
- `CapabilityEvaluator`
- legacy `ToolDefinition.required_capability` compatibility through
  `ToolRegistry`

Phase 1 security objective:

```text
LLM = untrusted proposer
Kernel = authority
```

The evaluator validates only exact action matches and simple resource-scope
matches. The purpose is to establish the Kernel-owned authorization shape before
larger namespace, delegation, and revocation work begins.

## 2. Threat Model

| Threat | Impact | Mitigation |
|---|---|---|
| LLM generates fake capability text in a prompt or tool argument | The model may try to claim authority, request a broader scope, or include text such as `capability: admin` in a tool call. | Capabilities are Kernel-owned Python objects derived from trusted runtime state. `AuthorizationRequest.agent_id`, action, and resource are constructed by Kernel code, not accepted from model text as authority. |
| LLM emits a hidden or unauthorized tool call | A model/provider may produce a tool call even when the schema was not projected. | `ToolRegistry` re-authorizes during execution. Schema hiding is not the only enforcement point. Unauthorized calls return `EACCES` before handler invocation. |
| Tool bypasses Kernel authorization | A tool implementation could try to perform a side effect or access a driver directly. | Phase 1 preserves the existing syscall boundary: tools are invoked only after `ToolRegistry.resolve_for_execution`. Future side-effect and resource drivers must remain behind Kernel services. Host code must not hand raw privileged drivers to untrusted tools. |
| Resource access crosses project/session scope | An agent allowed to read `artifact://project-a/**` could try `artifact://project-b/file.txt`. | Phase 1 evaluator denies mismatched prefix scopes. Phase 2 should wire structured resource checks into `ResourceService`; V0.5 owner/range checks still apply today for resource handles. |
| Child agent expands parent authority | A child could receive broader actions or scopes than the parent had. | Not implemented in Phase 1. The frozen design requires delegation by intersection and `child privilege <= parent privilege`. Phase 3 must persist delegation lineage and deny empty or broader intersections. |
| Constraint bypass | A grant constraint such as max bytes or approval required may be ignored if it is only metadata. | Phase 1 intentionally preserves constraints but does not evaluate them. This must remain documented as a limitation. Phase 2 should add deterministic evaluation for the first required constraint subset. |
| Legacy capability alias over-grants | Mapping `required_capability="payment"` too broadly could authorize tools that should differ by action or effect. | Phase 1 maps each legacy string to `tool.execute` on `tool://<string>`, preserving exact legacy behavior. Hosts should use narrow legacy strings until structured tool metadata exists. |
| Namespace spelling bypass | Alternate URI spelling or wildcard ambiguity could bypass a prefix check. | Phase 1 supports only exact and suffix `/**` prefix matching. Full namespace normalization is deferred and must be Kernel-owned before broad namespaces are enabled. |
| Authorization audit leaks secrets | Persisting full authorization requests could expose arguments, credentials, or resource contents. | Phase 1 does not add audit events. Future audit should record stable metadata and matched grant identifiers without raw secrets by default. |

## 3. Capability Core Validation

The Phase 1 evaluator has the correct minimal semantics for the requested
architecture checkpoint:

| Property | Validation |
|---|---|
| Positive grants only | Absence of a matching grant denies the request. |
| Agent identity bound | Grant `subject` must equal request `agent_id`. |
| Action isolation | Grant `action` must equal request `action`. |
| Scope isolation | Grant `resource_scope` must match the requested resource exactly or through a suffix `/**` prefix. |
| Constraint placeholder | Grant constraints are preserved immutably but are not evaluated in Phase 1. |
| Legacy compatibility | `required_capability` continues to hide schemas and deny unauthorized execution. |

## 4. Authorization Flow Freeze

The following flows are frozen as architecture direction. Phase 1 implements
only the Tool flow through the legacy compatibility adapter.

### Tool Flow

```text
LLM
  |
ToolRegistry
  |
CapabilityEvaluator
  |
Execute
```

Rules:

- LLM proposes a tool call.
- `ToolRegistry` owns schema projection and execution resolution.
- `CapabilityEvaluator` decides whether the agent has matching authority.
- Tool handlers run only after Kernel authorization.

### Resource Flow

```text
Tool
  |
ResourceService
  |
Capability Check
```

Rules:

- Resource tools remain model-facing syscall wrappers.
- `ResourceService` remains the trusted resource boundary.
- V0.5 owner, URI, byte range, and read-limit checks remain active.
- Structured resource capability checks are a future phase and must be added
  inside the trusted service boundary.

### Mutation Flow

```text
Tool
  |
Capability Check
  |
WAL
  |
External Side Effect
```

Rules:

- Mutation authority must be checked before durable intent is created.
- WAL ordering remains `prepare -> dispatch -> commit/abort`.
- External side effects must not run without Kernel authorization.
- Future phases should distinguish prepare, dispatch, and reconcile authority.

## 5. Benchmark Validation

`benchmarks/capability_benchmark.py` validates five deterministic cases:

| Case | Expected result |
|---|---|
| Basic Authorization | `ALLOW` for `artifact://project-a/file.txt` under `artifact://project-a/**`. |
| Scope Isolation | `DENY` for `artifact://project-b/file.txt` under a project-a grant. |
| Action Isolation | `DENY` when request action is `resource.write` but grant action is `resource.read`. |
| Multiple Grant Project A | `ALLOW` when one of two grants matches project-a. |
| Multiple Grant Project B | `ALLOW` when the other grant matches project-b. |

The benchmark is offline, deterministic, and does not call a model or network
API. It is a validation benchmark, not a performance comparison with other
agent frameworks.

## 6. Architecture Decision

Decision: `VALIDATED_FOR_PHASE_1`.

The Capability Core is consistent with the V0.6 freeze review because it keeps
authorization in Kernel-owned code, preserves legacy `required_capability`
behavior, and proves the minimum subject/action/scope shape without adding a
full policy engine.

Do not proceed directly to namespace, delegation, or revocation implementation
from this branch. Those require separate Phase 2/Phase 3 design acceptance
criteria and tests.

## 7. Remaining Limitations

- Constraints are immutable metadata only.
- Scope matching has no full URI canonicalization.
- Prefix matching is intentionally simple.
- ResourceService does not yet consume structured `AuthorizationRequest`.
- DurableToolExecutor does not yet distinguish prepare, dispatch, and reconcile
  capability actions.
- Delegation and revocation remain design-only.
- No audit event is written for authorization decisions.
